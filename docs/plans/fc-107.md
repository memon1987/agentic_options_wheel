## Context

Both bot services deploy with `--timeout=300` (`cloudbuild.yaml:413` wheel, `:583` covered-call), pinned by the frozen fixture `tests/fixtures/cloudbuild_contract.json` (`deploy_flags.deploy-bot-canary` / `deploy-cc-canary`). Live-verified 2026-09-08 via `gcloud run services describe` on both: `timeoutSeconds: 300`, `containerConcurrency: 10`, no `run.googleapis.com/cpu-throttling` annotation (default = throttled), `startup-cpu-boost: 'true'`. The roller's cycle budget is `_CYCLE_BUDGET_SECONDS = 1500` with `_PER_POSITION_BUDGET_SECONDS = 600` (`src/strategy/wheel_engine.py:30-31`), sized against the daily scheduler's `attemptDeadline: 1800s` (`options-wheel-roll-daily`, live-verified, retries 0). FC-078 rollout step 3 said "must be ≥ 1800 s; raise it if lower" and it never stuck: the deploy flag was never changed, so any manual raise was reset at the next merge. FC-100 §Found while planning item 1 re-found it and filed FC-107.

**Why 300 s is not merely tight — the mechanism of the failure.** The server is Flask's dev server, `threaded=True`, no gunicorn (`deploy/cloud_run_server.py:2137`, `deploy/Dockerfile:38`). When Cloud Run's request timeout fires it returns 504 to the caller; it does **not** kill the handler thread. Under request-based billing (the default; no `--no-cpu-throttling` on these services) the container's CPU is throttled to near-zero whenever no request is in flight, so the orphaned `/roll` thread stalls inside `_poll_order_fill`'s `time.sleep` / `get_order_by_id` loop (`call_roller.py:1109-1124`) — and **resumes** the next time any request lands on the instance (`activities-ingest-market-hours` every 15 min until 16:00 ET, `portfolio-history-ingest-daily` 16:30, `stock-history-ingest-daily` 17:00), placing STO rungs whose limits were priced before the cut. Rungs 1 and 2 carry the pre-BTC price (`_rungs`, `call_roller.py:952-975`); after 16:00 ET an STO placed as a DAY limit queues for the next open. If instead the instance is scaled in during the stall (no request for ~15 min), the thread dies with the process: BTC filled, no STO, and — because `call_roll_naked_exposure` is emitted at the *end* of the ladder — **no terminal event and no alert**. That is the "worst seam" FC-078 §4 built the budget guard for, defeated by a deploy flag the guard cannot see.

**The arithmetic.** Per leg: 120 s fill poll (`rolling.btc_fill_timeout_seconds`, used for STO rungs too — `_poll_order_fill` default, `:1102`) + 15 s cancel settle (`_CANCEL_SETTLE_TIMEOUT_SECONDS`, `:84`) = 135 s. Ladder: rung 1 (primary), rung 2 (floor, conditional), rungs 3+ up to `fallback_strike_attempts` = 2 → up to **4 rungs**. Shortest path across 300 s with a filled BTC: BTC fills instantly (paper) → rung 1 times out (135 s) → rung 2 times out (135 s) → rung 3 is placed at ~270 s plus evaluation, quote and cold-start overhead (~30–70 s) and is cut mid-poll at 300 s. Any two consecutive 120 s timeouts anywhere in a cycle cross the line; two ITM positions each needing one timeout cross it with certainty. Unbitten so far because paper fills are instant.

Intended outcome: a `/roll` request survives to the scheduler's deadline on both services, enforced by the contract fixture and an invariant test, and named as a real-money precondition.

## Design decisions

### D1 — The value is 1800 s, on both bot services

**Chosen: `--timeout=1800`.** Equal to the scheduler's `attemptDeadline` (1800 s is also Cloud Scheduler's HTTP-target maximum), and 300 s above `_CYCLE_BUDGET_SECONDS`.

Why the margin is needed: `run_rolling_cycle`'s clock starts *after* the request is admitted, `Config` loads and `WheelEngine` is constructed, and the guard only bounds when a position may *start*; a position started at 899 s may run its full worst case. The honest worst case is 675 s not 600 (see §Found while planning 1), so a cycle can end at 1575 s; cold start and the pre-loop position/order fetches sit outside the budget. 1800 − 1575 = 225 s covers them.

Rejected:
- **A smaller value (1575–1620 s, "budget + overrun").** Buys nothing: the only reason for a *smaller* service timeout would be to bound a hung non-roll request, and a Cloud Run cut does not stop a thread (see Context), so the number does not bound anything real; it only decides when the client sees a 504. The scheduler is already at 1800 and equality is the simplest invariant to pin.
- **3600 s (Cloud Run's max).** Exceeds the scheduler deadline: the scheduler would report DEADLINE_EXCEEDED on a cycle still running, and the test's `service ≤ scheduler` leg would be violated. Nothing in the system needs > 1800.
- **A separate short timeout for `/scan`, `/run`, `/monitor`.** Cloud Run has one request timeout per service. What the endpoints actually get is bounded elsewhere: every `/scan`/`/run`/`/monitor` scheduler job carries a 180 s `attemptDeadline` (live list), so the scheduler gives up at 180 s regardless of the service timeout, as it does today. Splitting `/roll` onto its own service is a real option but is a new service, new scheduler target, new canary chain and new fixture deviations — a Size-M answer to a Size-S problem.

**The trade-off, stated plainly.** A hung `/run` now holds its thread for up to 30 min before Cloud Run returns 504, instead of 5 min. With `--concurrency=10` and `--max-instances=1`, the four lock-holding routes (`/scan:375`, `/run:537`, `/monitor:986`, `/roll:1305` — the ingest and `/regression` routes do not take `strategy_lock`) queue behind it; the cadence is ≤ 4 lock-taking requests per hour, so at most ~2 more can queue inside 30 min and the 10-slot concurrency is never approached. Ingest requests keep flowing. What *does* change is that a stalled lock-holder now blocks the following `/monitor` or `/run` for up to 30 min rather than 5 — but under the old value the thread stalled anyway (throttled, not killed) and still held the lock, so the practical difference is when the queued caller's scheduler reports the miss, not whether it happens. The real bound on a hung request is a socket timeout on the Alpaca calls — FC-089's domain, unchanged by this plan.

### D2 — `--no-cpu-throttling` is NOT added to the bot services

**Chosen: leave request-based billing.**

Rough cost of the alternative. Instance-based billing charges for the instance's whole lifetime, including the ~15 min idle before scale-in. The wheel service receives a request at least every 15 min from 09:00 to 16:00 ET (`activities-ingest-market-hours`) plus hourly off-hours ingests, so the instance would be alive ~7–8 h continuous on market days plus ~16 × 15 min = 4 h of off-hours wakes ≈ 12 h/day; the CC service similarly (hourly `cc-activities-ingest` alone keeps it alive ~24 × 15 min = 6 h/day, plus market hours). At us-central1 tier-1 instance-based rates (≈ $0.018/vCPU-min → ~$0.065/h for 1 vCPU + ~$0.004/h for 512 MiB) that is ≈ $0.07/h × ~12 h × ~22 market days + off-hours ≈ **$20–25/month per service, ~$40–50/month for the pair**, less the instance-based free tier (~$5). Today's request-based bill for ~75 + ~50 short requests/day sits inside the free tier (~$0). The sim service pays this rate deliberately because a 202 response *by design* leaves work running with no request in flight; the bot services have no such design — every unit of their work is supposed to complete inside a request.

More important than cost: it does not address the failure. `--no-cpu-throttling` changes what a *cut* thread does (keeps running immediately instead of stalling and resuming later), but D1 makes a cut inside the budget impossible by construction; the only way to be cut at 1800 s is a poll that ignores its own timeout — a hung socket (FC-089) — and a thread that then keeps trading on its own after the scheduler and Cloud Run have both given up is not obviously better than one that stalls. Cloud Run scales the instance in after idle under either billing mode, so it does not protect the residual FC-078 accepted (instance death mid-ladder) either. If a future finding wants the cut-thread behaviour changed, the right lever is in the roller (a deadline check inside `_poll_order_fill`), not a billing flag.

### D3 — The fixture re-freeze is the ELEVENTH deviation

`test_every_deploy_flag_matches_frozen_fixture` compares flag *sets*; `--timeout=300` → `--timeout=1800` is one missing + one added with a name (`--timeout`) not in `ALLOWED_NEW_DEPLOY_FLAGS`, so the test fails until the fixture is re-frozen. That mechanism forgives a new flag NAME, never a changed VALUE — the same reason every env-string change was re-frozen. This is the first non-env VALUE change to a bot service's flags in the ledger's history. Ledger text is in §Critical files.

### D4 — The invariant test pins the documented scheduler value, not the live one

The scheduler's `attemptDeadline` is live config with no file in the repo. The test carries `ROLL_SCHEDULER_ATTEMPT_DEADLINE_SECONDS = 1800` as the documented value (FC-078 DD, FC-100 DD-3 recipe both say `--attempt-deadline 1800s`), asserts the service timeout against it, and the rollout verifies the live value. A live-reading test was rejected: the suite is hermetic by conftest rule (nine ambient-env defects and counting).

## Risks & mitigations

- **Risk: the fixture is edited in one step and not the other (split-brain).** Mitigation: `test_bot_service_timeout_covers_the_roll_cycle_budget` is parametrized over both bot services and asserts they are equal; the confirmation pass checks both `describe` outputs.
- **Risk: a reader raises `--timeout` and thinks the serialize-builds budget moved.** Mitigation: the two are different resources; `timeout: 1500s` (Cloud Build) and `test_gate_deadline_tracks_the_build_timeout` / `test_build_timeout_matches_frozen_fixture` are untouched and must stay green; the fixture's top-level `timeout` key is unchanged. A deploy step's wall time does not depend on the request-timeout value, so the measured ~975 s single / ~1335 s waiting-pair budget is unaffected.
- **Risk: a hung `/run` or `/monitor` holds `strategy_lock` for up to 30 min.** See D1's trade-off — the thread held the lock anyway; the scheduler's 180 s deadline already reports the miss; FC-089 (socket timeouts) is the bound.
- **Risk: `gcloud run deploy --timeout=1800` is rejected.** Cloud Run's maximum is 3600 s (60 min) for services; 1800 is inside it. The dashboard chain does not change, so a rejection would fail at `deploy-bot-canary` before any traffic moves (canary/promote design).
- **Residual (accepted, as in FC-078):** an instance crash or scale-in mid-ladder inside the budget still strands a BTC; the alert on `call_roll_naked_exposure` plus the next `/scan → /run` re-cover is the backstop. This plan removes the *deterministic* cut, not the crash.

## Found while planning (not fixed here)

1. **`_PER_POSITION_BUDGET_SECONDS = 600` under-counts the per-position worst case by 75 s.** `wheel_engine.py:26` says "BTC 120 s poll + cancel/verify + up to four STO rungs × 120 s" = 600, but each of the five legs also carries the 15 s `_CANCEL_SETTLE_TIMEOUT_SECONDS` on timeout, so the honest figure is 5 × 135 = **675 s**; a position started at 899 s can end at 1574 s, past the 1500 s budget. Harmless under this plan's 1800 s (225 s remain), and today's 300 s dwarfs it — but the constant is asserted as "the contract" in `test_wheel_engine.py:373-379`. **FC to file (shared, S):** raise to 675 (or 700) with the comment corrected.
2. **`startup-cpu-boost: 'true'` is live on both bot services but is not in `cloudbuild.yaml`.** It persists from hand provisioning the way the secret bindings do (the `--set-secrets` note on the bot steps); a `gcloud run deploy` without `--cpu-boost`/`--no-cpu-boost` leaves it alone. Not a defect; worth a line in the deploy docs so a future "why is this annotation here" has an answer, and worth knowing that recreating a bot service from cloudbuild alone would drop it.
3. **Scheduler `attemptDeadline`s are inconsistent with the service timeout today**, in both directions: `stock-history-ingest-daily` is 600 s against a 300 s service (the scheduler waits for a response Cloud Run can no longer send); `execute-*`/`scan-*`/`monitor-*` are 180 s (scheduler gives up before the service does — fine, retries are 0). The 600 s one becomes consistent after this plan. No action; noted so the FC-108 `roll_freshness` check does not inherit the assumption that a scheduler deadline bounds the server-side work.
4. **`SCREEN_REQUEST_TIMEOUT_S = 300` (`cloud_run_server.py:1438`) and its "no synchronous request can complete even ONE symbol inside the 300s timeout" comments mirror the old service value.** The endpoint is disabled and the constant still bounds it, so it is doc drift, not a bug; fold into whichever FC next touches the screen endpoint.
5. **`regression-hourly` targets the `…-799970961417.us-central1.run.app` URL form while every other wheel job uses `…-omnlacz6ia-uc.a.run.app`.** Both resolve to the service; cosmetic, but a URL-form audit belongs with FC-108's "a 404 after a URL change is invisible" concern.
6. **FC-100 is still Draft and no `cc-roll-daily` job exists** (live scheduler list 2026-09-08), so the "resume the CC roll job" language in the FC-107 entry is forward-looking; this plan's rollout step 4 is phrased accordingly.
