## Context

Both bot services deploy with `--timeout=300` (`cloudbuild.yaml:413` wheel, `:583` covered-call), pinned by the frozen fixture `tests/fixtures/cloudbuild_contract.json` (`deploy_flags.deploy-bot-canary` / `deploy-cc-canary`). Live-verified 2026-09-08 via `gcloud run services describe` on both: `timeoutSeconds: 300`, `containerConcurrency: 10`, no `run.googleapis.com/cpu-throttling` annotation (default = throttled), `startup-cpu-boost: 'true'` (persists from hand provisioning, like the secret bindings — not in `cloudbuild.yaml`). The roller's cycle budget is `_CYCLE_BUDGET_SECONDS = 1500` with `_PER_POSITION_BUDGET_SECONDS = 600` (`src/strategy/wheel_engine.py:30-31`), sized against the daily scheduler's `attemptDeadline: 1800s` (`options-wheel-roll-daily`, live-verified, retries 0). FC-078 rollout step 3 said "must be ≥ 1800 s; raise it if lower" and it never stuck: the deploy flag was never changed, so any manual raise was reset at the next merge. FC-100 §Found while planning item 1 re-found it and filed FC-107.

**What the cut actually does (corrected in rev 2 — the rev-1 "stalls and resumes on the next ingest request" story was wrong).** The server is Flask's dev server, `threaded=True`, no gunicorn (`deploy/cloud_run_server.py:2137`, `deploy/Dockerfile:38`). When Cloud Run's request timeout fires it returns 504 to the caller and does **not** kill the handler thread. Evidence from the wheel's own logs, 2026-08-13: `/scan` got its 504 at 17:05:38 (latency 300.0 s) and the orphaned thread kept emitting on schedule with **no request in flight** from 17:00:41 to 17:15:09 — `positions_error` 17:06:21 and 17:09:12, `put_scan_skipped_existing_position` 17:11:58–17:13:42, `put_scan_completed` 17:13:56, `call_scan_completed` 17:15:25. CPU throttling slows an I/O-bound loop (microseconds of CPU per 5 s sleep + one API call); it does not park it. So after a cut the ladder **keeps running roughly on schedule**: its terminal events — `call_roll_completed`, `call_roll_naked_exposure`, the rest — still fire *if the instance lives*, and the "at most one live STO" invariant holds through the continuation. What is lost: the scheduler records a silent 504 (a job failure no policy watches), and the `/roll` response (`duration_seconds`, `results`) never reaches anyone. The dangerous residual is **instance scale-in mid-ladder** (~15 min with no request): the thread dies with the process, BTC filled, STO never placed, no terminal event. Unlikely in the roll window given the 15-min `activities-ingest-market-hours` cadence until 16:00 ET and the 16:30 / 17:00 ingests after it, but real — and real money in that seam is *uncovered long stock*, not a naked call (see §Risks, LOW-money framing).

**Measured, not assumed.** Last 22 wheel `roll_cycle_completed.duration_seconds`: 0.3, 187, 11, 10, 0.4, 18, 4.6, 137, 6.8, 0.6, 0.3, 16, 199, 133, 259, 0.8, 14, 141, 140, 150, 124, 26. STO rung 1 timed out in **4 of 8 executed rolls since 08-28** (08-28 AAPL and AMZN: rung 1 timed out → rung 2 filled; 09-03 IWM; 09-04 AAPL). 09-07 IWM: `call_roll_btc_timeout_canceled` — a genuine BTC timeout, on paper (placed into a closed market on Labor Day; §Found while planning 7 / FC-114). Paper fills are *not* instant on this book.

**The arithmetic.** Per leg: 120 s fill poll (`rolling.btc_fill_timeout_seconds`, used for STO rungs too — `_poll_order_fill` default, `call_roller.py:1102`) + 15 s cancel settle (`_CANCEL_SETTLE_TIMEOUT_SECONDS`, `:84`) = **135 s**. Ladder: rung 1 (primary), rung 2 (floor, conditional), rungs 3+ up to `fallback_strike_attempts` = 2 → up to 4 rungs; with the BTC, **5 legs × 135 = 675 s** per position worst case (not the 600 s the constant says — FC-113). Against 300 s: with 4 short calls on the book, a 3-ITM day has roughly even odds of two 120 s timeouts (~270 s with settles) plus ~35 s/position of chain fetch and evaluation — i.e. ≈ 300 s. One measured cycle already ran 259 s.

Intended outcome: a `/roll` request survives to the scheduler's deadline on both services, enforced by the contract fixture and a seam-invariant test derived from the roller's own constants and each profile's config, and named as one real-money gate among several.

## Design decisions

### D1 — The value is 1800 s, on both bot services (DECIDED)

**Chosen: `--timeout=1800`.** Equal to the scheduler's `attemptDeadline` (1800 s is also Cloud Scheduler's HTTP-target maximum), and 300 s above `_CYCLE_BUDGET_SECONDS`.

**Where the 300 s goes, honestly.** 75 s is the FC-113 under-count (675 s true per-position worst vs the 600 s constant: a position started at the latest permitted 900 s ends at 1575 s). The remaining 225 s covers the preamble (`strategy_config()`, `WheelEngine` construction and the pre-loop position/order fetches all run *before* `run_rolling_cycle`'s clock starts at `wheel_engine.py:721`; the 15:30 instance is warm from the 15:15 `/run`, so this is seconds, not a cold start) and the roller's **RTT blindness**: `_poll_order_fill` counts only `elapsed += poll_interval` (`call_roller.py:1124`), so the 24 `get_order_by_id` round-trips per 120 s poll, the settle polls, the cancel and the place calls are all unaccounted. Per-position worst ≈ **730 s at 0.3 s RTT, ≈ 825 s at 1 s, ≈ 960 s at 2 s**; margin under 1800 ≈ 160 s at normal RTT, ~65 s at 1 s, and **negative at ≥ ~1.7 s RTT**. So 1800 is enough for today's book and today's latency; it is not "impossible to cut by construction", and the RTT/deadline accounting that would make it so is FC-113 (a real-money precondition).

Rejected:
- **A smaller value (1575–1620 s, "budget + overrun").** Buys nothing: the only reason for a *smaller* service timeout would be to bound a hung non-roll request, and a Cloud Run cut does not stop a thread (Context), so the number does not bound anything real; it only decides when the client sees a 504 — and eats the RTT margin above. The scheduler is already at 1800 and equality is the simplest invariant to pin.
- **3600 s (Cloud Run's max).** Exceeds the scheduler deadline: the scheduler would report DEADLINE_EXCEEDED on a cycle still running, and the test's `service ≤ scheduler` leg would be violated. Nothing in the system needs > 1800.
- **A separate short timeout for `/scan`, `/run`, `/monitor`.** Cloud Run has one request timeout per service. What the endpoints actually get is bounded elsewhere: every `/scan`/`/run`/`/monitor` scheduler job carries a 180 s `attemptDeadline` (live list), so the scheduler gives up at 180 s regardless of the service timeout, as it does today. Splitting `/roll` onto its own service is a real option but is a new service, new scheduler target, new canary chain and new fixture deviations — a Size-M answer to a Size-S problem.

**The trade-off, stated plainly.** A hung `/run` now holds its thread for up to 30 min before Cloud Run returns 504, instead of 5 min. With `--concurrency=10` and `--max-instances=1`, the four lock-holding routes (`/scan:375`, `/run:537`, `/monitor:986`, `/roll:1305` — the ingest and `/regression` routes do not take `strategy_lock`) queue behind it; the cadence is ≤ 4 lock-taking requests per hour, so at most ~2 more can queue inside 30 min and the 10-slot concurrency is never approached. Ingest requests keep flowing. Under the old value the hung thread was not killed either and still held the lock, so what changes is when the queued caller's scheduler reports the miss, not whether it happens. **The lock-wait blind spot, which this plan does not fix:** Cloud Run's clock starts at admission (`cloud_run_server.py:1305` takes the lock *before* anything else), the cycle's clock starts after the lock (`wheel_engine.py:721`). A `/roll` queued N s behind a slow `/run` or `/monitor` (observed lock-holders: 63 s, 79 s, 300 s) has 1800 − N platform seconds while believing it has 1500 — at N = 300 the margin above is gone. FC-113 (an admission-time deadline passed into `run_rolling_cycle`, or a lock-acquire timeout on `/roll`) closes it; after this plan lands, FC-089's lock-timeout/abandon guard is the **only** RTH bound on a hung lock-holder, since Cloud Run's 1800 s cut is not one.

### D2 — `--no-cpu-throttling` is NOT added to the bot services (DECIDED)

**Chosen: leave request-based billing.**

Rough cost of the alternative. Instance-based billing charges for the instance's whole lifetime, including the ~15 min idle before scale-in. The wheel service receives a request at least every 15 min from 09:00 to 16:00 ET (`activities-ingest-market-hours`) plus hourly off-hours ingests, so the instance would be alive ~7–8 h continuous on market days plus ~16 × 15 min = 4 h of off-hours wakes ≈ 12 h/day; the CC service similarly (hourly `cc-activities-ingest` alone keeps it alive ~24 × 15 min = 6 h/day, plus market hours). At us-central1 tier-1 instance-based rates — **$0.000018/vCPU-s (= $0.065/vCPU-h)** for 1 vCPU + ~$0.004/h for 512 MiB — that is ≈ $0.07/h × ~12 h × ~22 market days + off-hours ≈ **$20–25/month per service, ~$40–50/month for the pair**, less the instance-based free tier (~$5). Today's request-based bill for ~75 + ~50 short requests/day sits inside the free tier (~$0). The sim service pays this rate deliberately because a 202 response *by design* leaves work running with no request in flight; the bot services have no such design.

More important than cost: it addresses nothing. Per Context, a cut thread already keeps running under throttling — the flag would buy it a little more CPU for an I/O-bound loop that barely uses any — and Cloud Run scales the instance in after idle under either billing mode, so it does not protect the scale-in residual either. If a future finding wants the cut-thread behaviour changed, the lever is in the roller (a wall-clock deadline in `_poll_order_fill` — FC-113), not a billing flag.

### D3 — The fixture re-freeze is the ELEVENTH deviation

`test_every_deploy_flag_matches_frozen_fixture` compares flag *sets*; `--timeout=300` → `--timeout=1800` is one missing + one added with a name (`--timeout`) not in `ALLOWED_NEW_DEPLOY_FLAGS`, so the test fails until the fixture is re-frozen. That mechanism forgives a new flag NAME, never a changed VALUE — the same reason every env-string change was re-frozen. This is the first non-env VALUE change to a bot service's flags in the ledger's history. Ledger text is in §Critical files.

### D4 — The covering test pins the seam invariant from the actual constants, per profile

Not a number. The test derives, for each bot service and its profile:

- `latest_start = _CYCLE_BUDGET_SECONDS − _PER_POSITION_BUDGET_SECONDS` (the last elapsed second at which `run_rolling_cycle` will still *start* a position — `wheel_engine.py:818`);
- `legs = 1 (BTC) + 2 (rung 1 + the conditional floor rung) + rolling.fallback_strike_attempts`;
- `per_position_worst = legs × (rolling.btc_fill_timeout_seconds + _CANCEL_SETTLE_TIMEOUT_SECONDS)`;
- `rolling.*` read with `yaml.safe_load` from the profile the service deploys (`deploy-bot-canary` → `config/settings.yaml`; `deploy-cc-canary` → `config/covered_call.yaml` via its `STRATEGY_CONFIG` env). A profile with no `rolling` block (`covered_call.yaml` until FC-100 lands) falls back to the wheel's values, and the test says so in its message;

and asserts `latest_start + per_position_worst + PREAMBLE_ALLOWANCE_SECONDS ≤ service_timeout ≤ ROLL_SCHEDULER_ATTEMPT_DEADLINE_SECONDS`, plus equality of the two bot services' timeouts. With today's values: 900 + 5 × 135 + 60 = **1635 ≤ 1800 ≤ 1800**. Mutation `fallback_strike_attempts: 4` in either yaml → 7 legs → 900 + 945 + 60 = 1905 → **fails**; `btc_fill_timeout_seconds: 180` → 900 + 975 + 60 = 1935 → fails; either service at 300 → fails; a future `_CYCLE_BUDGET_SECONDS` raise without the flag → fails. `PREAMBLE_ALLOWANCE_SECONDS = 60` is a named test constant (warm-instance preamble; docstring says it does *not* cover RTT blindness or lock wait — FC-113).

The scheduler's `attemptDeadline` is live config with no file in the repo. `ROLL_SCHEDULER_ATTEMPT_DEADLINE_SECONDS = 1800` is the documented value (FC-078, FC-100 DD-3; Cloud Scheduler's HTTP maximum) and the rollout verifies it live. A live-reading test was rejected: the suite is hermetic by conftest rule.

**Import hermeticity.** `src.strategy.wheel_engine` (`_CYCLE_BUDGET_SECONDS`, `_PER_POSITION_BUDGET_SECONDS`) and `src.strategy.call_roller` (`_CANCEL_SETTLE_TIMEOUT_SECONDS`) are module-level constants; importing either module pulls the Alpaca SDK and the `Config` *class* but instantiates nothing — no `Config()`, no network — and `tests/test_wheel_engine.py` already imports `wheel_engine` under the same conftest guards. Import inside the test function (precedent: `cli.BATTERY_MAX_SECONDS` in `test_the_battery_wall_cap_fits_inside_the_backfill_jobs_timeout`).

## Risks & mitigations

- **Risk: the fixture is edited in one step and not the other (split-brain).** Mitigation: the seam-invariant test is parametrized over both bot services and asserts they are equal; the confirmation pass checks both `describe` outputs.
- **Risk: a reader raises `--timeout` and thinks the serialize-builds budget moved.** Mitigation: the two are different resources; `timeout: 1500s` (Cloud Build) and `test_gate_deadline_tracks_the_build_timeout` / `test_build_timeout_matches_frozen_fixture` are untouched and must stay green; the fixture's top-level `timeout` key is unchanged. A deploy step's wall time does not depend on the request-timeout value, so the measured ~975 s single / ~1335 s waiting-pair budget is unaffected.
