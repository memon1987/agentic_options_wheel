## Context

The 2026-05-07 senior-trader strategy review ([docs/investigations/strategy-review-2026-05-07.md](docs/investigations/strategy-review-2026-05-07.md)) found that the wheel achieved 54% of buy-and-hold dollar P&L ($21,016 vs $39,200) across 7 symbols, with 5 of 7 symbols lagging B&H. The shortfall concentrates in **3 cycles that share one parameterizable failure mode**: stock dropped 5–16% between assignment and called-away, bot got called away below acquisition strike. Those 3 cycles cost **$9,000** in share-side losses (40% of total option-side P&L).

Loss attribution (from the review):

| Cycle | Strike drop | Share P&L | Cycle P&L |
|---|---:|---:|---:|
| AMD 2025-11-17 → 11-24 | −16.3% | −$3,750 | **−$1,925** |
| AMZN 2025-11-04 → 11-28 | −14.1% | −$3,500 | −$443 |
| UNH 2025-10-30 → 11-15 | −5.3% | −$1,750 | −$532 |

Three structural causes identified:

1. **Call delta range [0.30, 0.70] is structurally aggressive** — 30–70% assignment probability per call, vs 10–20% on puts. Forces near-ATM strike selection, especially in down moves.

2. **Cost-basis floor is non-functional** — validated 2026-05-08 ([docs/investigations/cost-basis-floor-validation-2026-05-08.md](docs/investigations/cost-basis-floor-validation-2026-05-08.md)). Alpaca's `cost_basis` field returns 0 for stock acquired via option assignment; both safety guards (`market_data.py:435` and `call_seller.py:211`) are gated on `> 0`, so the floor is effectively bypassed across every covered-call sale to date. The bot DOES correctly capture the put strike at OPASN time (in `wheel_engine.py:924` and persists to `wheel_state.symbol_states[symbol]['stock_cost_basis']`) but then never reads from that source — `call_seller.py:63` reads from Alpaca instead.

3. **No drawdown pause** — when shares are deeply underwater, the cost-basis floor (when working) blocks all suitable calls. AMZN cycle 2 had a 62-day gap (Feb 6 → Apr 10) where the bot scanned but found nothing because every qualifying delta-range call was below cost basis. Better to make this an explicit decision (skip with reason logged) than rely on side-effect-of-broken-filter.

Phase 1 of the strategy review is the minimum recommended action: ship R1 + R2 + R3 together. They are complementary — they collectively prevent the failure mode.

## Goals

- Eliminate the structural near-ATM call exposure that drove the 3 loss cycles.
- Restore the cost-basis floor by reading from `wheel_state` (the canonical source), with a BQ fallback for silent-assignment / cold-start cases.
- Make "stop selling calls when shares are underwater" an explicit, observable decision rather than a side-effect.
- Preserve put-side income (this plan does not touch put parameters — separate evaluation).

## Non-goals

- **Per-symbol delta tuning (R5).** Future FC after Phase 1 baseline.
- **DTE extension to 14 (R4).** Pairs naturally with R1 but adds another tunable variable; defer to FC-030.
- **Profit-target floor changes (R6).** Defer to FC-030.
- **Universe pruning (R7 / FC-001).** Independent; can ship in parallel.
- **Adaptive learning (R9), 30-day-high filter (R10), assignment cooldown (R8).** Phase 3+.
- **Per-lot cost basis tracking** (FC-020 territory). The single-strike model with `wheel_state` works given current `max_positions_per_stock=1`. If `max_positions_per_stock` ever increases or overlapping share lots become common, revisit.
- **Fixing Alpaca's broken `cost_basis` field upstream.** Out of our control; treat the field as advisory/fallback only.

## Proposed approach

Three independent but complementary changes, shipped in one PR.

### R1 — Tighten call delta range

`config/settings.yaml`:
```yaml
strategy:
  call_delta_range: [0.15, 0.25]   # was [0.30, 0.70]
```

Lowers call assignment probability from 30–70% to 15–25%. Pushes call strikes 2–4% further OTM. The ranking function `annual_return * (1 - abs(delta))` ([market_data.py:462](src/api/market_data.py#L462)) within the new range still prefers lower delta — same ranking semantics, tighter floor.

### R2 — Read cost basis from `wheel_state` (canonical), not Alpaca's broken field

The put strike of the assigning OPASN is the deterministic cost basis of the resulting share lot. The bot already captures this correctly:

```
Alpaca OPASN activity                         (source: /v2/account/activities)
    ↓
wheel_engine.py:924 — per_share_cost = strike_price
    ↓
wheel_state_manager.handle_put_assignment(symbol, shares, cost_basis=strike)
    ↓
wheel_state.symbol_states[symbol]['stock_cost_basis'] = strike
    ↓
GCS persistence (_save_state)                 (survives cold starts)
```

The `call_seller` simply reads from the wrong source.

**Code changes** in `src/strategy/call_seller.py`:

1. Replace the read at line 63:

3. Add a private method `_resolve_cost_basis_floor`:

```python
def _resolve_cost_basis_floor(self, symbol: str, stock_position: dict, shares_owned: int) -> float:
    """Cost basis = strike of the assigning put. Always.

    Source order (deterministic, with self-healing fallbacks):
      1. wheel_state.symbol_states[symbol]['stock_cost_basis']
         — populated at OPASN time from put strike, persisted to GCS
      2. Most recent OPASN-put strike for this symbol from
         options_wheel.trades_from_activities (handles silent assignments,
         cold starts, and synthetic-row corrections like FC-021/FC-025)
      3. Alpaca's reported cost_basis (broken for assigned positions in
         paper trading, but works for non-wheel positions like manual buys)

    Returns 0 only if no source resolves — caller is expected to treat
    that as "no floor" (current behavior preserved for backwards compat).
    """
    if self.wheel_state:
        state = self.wheel_state.get_position_summary(symbol)
        cb = state.get('stock_cost_basis', 0)
        if cb > 0:
            return cb

    cb = self._lookup_last_opasn_put_strike(symbol)
    if cb > 0:
        # Backfill wheel_state so future reads hit the fast path
        if self.wheel_state:
            self.wheel_state.set_stock_cost_basis(symbol, cb)
        return cb

    alpaca_cb = float(stock_position.get('cost_basis', 0)) / max(shares_owned, 1)
    return alpaca_cb
```

4. Add `_lookup_last_opasn_put_strike` (BQ query):

```python
def _lookup_last_opasn_put_strike(self, symbol: str) -> float:
    """Return the strike of the most recent OPASN-put for this symbol.

    Returns 0 if no assigning put found or BQ unavailable.
    """
    try:
        from google.cloud import bigquery
        client = bigquery.Client()
        query = """
        SELECT strike_price
        FROM `options_wheel.trades_from_activities`
        WHERE underlying = @symbol
          AND activity_type = 'OPASN'
          AND option_type = 'put'
          AND transaction_time <= CURRENT_TIMESTAMP()
        ORDER BY transaction_time DESC
        LIMIT 1
        """
        job = client.query(query, job_config=bigquery.QueryJobConfig(
            query_parameters=[bigquery.ScalarQueryParameter('symbol', 'STRING', symbol)]
        ))
        for row in job.result(timeout=10):
            return float(row['strike_price'] or 0)
        return 0
    except Exception as e:
        logger.warning("OPASN-strike lookup failed; falling back to Alpaca cost_basis",
                       event_category="risk",
                       event_type="opasn_strike_lookup_failed",
                       symbol=symbol, error=str(e))
        return 0
```

5. Add `WheelStateManager.set_stock_cost_basis(symbol, value)` (line ~250 region):

```python
def set_stock_cost_basis(self, symbol: str, cost_basis: float) -> None:
    """Backfill cost basis for a position when it's missing from state.

    Used by call_seller after a BQ lookup recovers the assigning put strike.
    """
    if symbol not in self.symbol_states:
        self.symbol_states[symbol] = {
            'stock_shares': 0,
            'stock_cost_basis': 0.0,
            ...
        }
    self.symbol_states[symbol]['stock_cost_basis'] = float(cost_basis)
    self._save_state()
```

6. Tighten the gate in `find_suitable_calls` ([market_data.py:435](src/api/market_data.py#L435)) — the existing `if min_strike_price > 0 and ...` check is correct but emit a warning when min_strike_price is 0 AND a position is being evaluated, so future regressions are loud:

### R3 — Drawdown pause

Add an explicit skip in `evaluate_covered_call_opportunity` (call_seller.py, after the cost-basis read at line 63):

```python
# Drawdown pause (R3): skip call writes when shares are deeply underwater.
# Below the threshold, every delta-range strike is either ITM or below cost
# basis (R2's floor). Better to log the skip explicitly than rely on R2
# returning empty.
try:
    current_price = self.market_data.get_stock_quote(symbol).get('mid', 0)
except Exception:
    current_price = 0

threshold = self.config.call_drawdown_pause_threshold  # default 0.05 = 5%
if current_price > 0 and stock_cost_basis > 0:
    drawdown_pct = (stock_cost_basis - current_price) / stock_cost_basis
    if drawdown_pct >= threshold:
        log_trade_event(
            logger,
            event_type="covered_call_drawdown_pause",
            symbol=symbol,
            success=False,
            skip_reason="drawdown_pause",
            cost_basis=stock_cost_basis,
            current_price=current_price,
            drawdown_pct=round(drawdown_pct, 4),
            threshold_pct=threshold,
        )
        return None
```

`config/settings.yaml`:
```yaml
strategy:
  call_drawdown_pause_threshold: 0.05   # NEW (R3): skip call writes if shares > 5% below cost basis
```

`src/utils/config.py` — add the new property (mirroring existing pattern).

## Risks & mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| BQ tertiary lookup fails (network, IAM) → call_seller falls back to Alpaca's broken value | M | Logged at WARNING with `event_type=opasn_strike_lookup_failed`; bot continues with degraded protection rather than failing the cycle. The wheel_state primary path covers ~all positions in normal operation. |
| Tightening call delta to [0.15, 0.25] reduces premium income 30–40% | M (expected) | This is the intended tradeoff — strategy review §6 documents the expected outcome. Validate post-deploy on premium-per-day-deployed metric. |
| Drawdown pause causes long idle periods on a held name in a sustained drawdown | L | Explicit logging makes the behavior observable. The 5% threshold is empirical; tune if it triggers too often or too rarely. |
| `wheel_state` cold start with empty GCS → falls through to BQ lookup → succeeds | L | This is the design. Tested in unit test §Verification. |
| Position acquired via manual buy (no OPASN) → tertiary fallback to Alpaca | L | Alpaca's `cost_basis` works correctly for manual buys. Fallback path is correct. |
| `find_suitable_calls` warning at min_strike_price=0 fires noisily during put-only scans (no shares held) | L | Only emit when `min_strike_price <= 0` AND a stock position is being evaluated for covered calls. Put scans use `min_strike_price=0.0` legitimately. |

## Open questions

- **Should we cache the BQ lookup with a TTL?** First-time on a cold start is fine. If we hit BQ on every call evaluation it adds ~100ms latency × N cycles. The wheel_state backfill (step 3 in the helper) makes this a one-time cost per symbol-cycle. Defer optimization.
- **Should the OPASN-strike lookup also handle synthetic FC-021/FC-025 rows specially?** Current query already includes them (they have `activity_type='OPASN'`, `option_type='put'`, `synthetic-` prefix on activity_id). The lookup naturally finds them. Verified.
- **Is 5% the right drawdown threshold?** Empirical. Could be 3% (more pause) or 7% (less pause). Will tune based on first 30-day observation. Could also make it per-symbol (AMD's volatility wants tighter pause than IWM's).

## Cutover analytics note (peer review MEDIUM 7)

The `stock_cost_basis` field in `call_sale_executed` BQ events changes meaning across this PR's deploy boundary:
- **Pre-FC-029:** value was `float(stock_position['cost_basis'])` from Alpaca — for assigned positions in paper trading this returned 0; for non-wheel manual buys it returned the real total dollar cost basis.
- **Post-FC-029:** value is `stock_cost_basis * shares_covered` where `stock_cost_basis` is the per-share value resolved from `wheel_state` (canonical) → BQ → Alpaca. For assigned positions the value steps from 0 → real (e.g., 24750 for AMZN @ $247.5); for non-wheel positions unchanged.

Any analytics view aggregating this field across the cutover boundary will show a step change that looks like a data anomaly (cf. FC-021 silent-exercise lessons). Document in the cutover commit message and any release notes. No corrective action needed; the field semantics are now correct, the historical data was just wrong.
