## Context

Two surfaces on the per-symbol drilldown show realized-P&L numbers that disagree, and neither is the truth.

**Trace evidence (UNH, full hand-reconcile against raw `trades_from_activities`):**

| Surface | Currently displays | Truth | Status |
|---|---:|---:|---|
| Top-of-page "Realized P&L" card | $4,334 | $2,584 | option-leg only — share-side silently dropped |
| Wheel-vs-B&H "Wheel" total | $10,222 | $2,584 | bug: `realized_pnl + total_premium` double-counts gross premium |
| Wheel-vs-B&H "Δ Wheel − B&H" | +$9,224 | +$1,586 | propagates the same bug; overstates wheel advantage |

**Root cause for the double-count:** `realized_pnl` per row in `trades_with_outcomes` is already net of buyback cost (`premium_total − close_price × |close_qty| × 100` for early-closes; `premium_total` for assignments/expirations). Summing `realized_pnl` across rows and then adding `total_premium = SUM(premium_total)` adds the gross premium a second time. Bug lives in `dashboard/frontend/src/components/v2/VsBuyAndHoldCard.tsx:18-19` and mirrored in `docs/bigquery/fc018_views.sql:312-313` inside `wheel_minus_bh`.

**Root cause for the option-only display:** The top card reads `summary.realized_pnl` (option leg). FC-019 introduced `total_realized_pnl = realized_pnl + share_side_pnl` on the scorecard view, but the per-symbol drilldown header was never migrated to the new field — it predates FC-019.

**Why now:** the user opened a series of dashboard accuracy investigations; #1 on the list is "the realized P&L at the top doesn't reconcile with wheel return — accurate numbers are paramount for reporting." This FC closes that gap.

## Goals

- Both the top-of-page "Realized P&L" card and the Wheel-vs-B&H "Wheel" total display the same canonical number: `total_realized_pnl = realized_pnl + share_side_pnl`.
- The "Δ Wheel − B&H" delta on Wheel-vs-B&H reflects the corrected wheel total.
- Display affordance: subtitle on the top card breaks the total down as `option {realized_pnl} + share {share_side_pnl}` so the option vs. share split stays visible.
- View `fc018_vs_buy_and_hold_per_symbol` exposes `total_realized_pnl` and `share_side_pnl` so frontend can compute / display without joining back to the scorecard view.
- After fix: UNH renders $2,584 on both surfaces; AMZN renders $26,206; UNH "Δ vs B&H" renders +$1,586 instead of +$9,224.

## Non-goals

- **B&H comparison fidelity beyond price-only.** `bh_dollar_pnl` doesn't reinvest dividends. Worth flagging in the UI label, but adding a real dividend ingest is a separate FC.
- **Unrealized P&L on open positions.** `total_realized_pnl` is realized-only by design (FC-019 closed this question). For symbols with `open_count > 0` the displayed number is closed-position-only; we do not fold unrealized into "Realized P&L."
- **Renaming `realized_pnl`.** Keep the field semantics as option-only across the codebase. Do not rename to e.g. `option_realized_pnl` even though the label would be clearer; FC-019's existing scorecard table on the Overview page uses "Option P&L" / "Share P&L" / "Total P&L" headers and it'd be churn to rename the underlying field.
- **Other observations on the per-symbol page.** ACB walk (#2), Decision Quality (#3), Phase Timing (#4) are separate FCs.

## Proposed approach

1. Add `total_realized_pnl` and `share_side_pnl` to the `ws` CTE (pulled from `fc018_per_symbol_scorecard`).
2. Replace `(realized_pnl + total_premium)` in the `wheel_minus_bh` formula with `total_realized_pnl`.
3. Add `total_realized_pnl` and `share_side_pnl` to the final `SELECT`.
4. Re-deploy via `bq query --use_legacy_sql=false < docs/bigquery/fc018_views.sql` (idempotent `CREATE OR REPLACE VIEW`).

**Frontend types** — `dashboard/frontend/src/types/v2.ts`:

## Risks & mitigations

- **Risk:** View change is global — `wheel_minus_bh` semantics change for every consumer (`SymbolUniverseTable`, `SymbolScorecard` on Overview, `VsBuyAndHoldCard`).
  - *Mitigation:* This is intentional. All current consumers display the same broken number; correcting the view fixes them all uniformly. Verified via grep: 3 consumer surfaces, all reading `wheel_minus_bh` with no offsets/transforms applied frontend-side.
- **Risk:** `share_side_pnl` could be NULL on the vs-buy-and-hold view if the scorecard's left-join shape ever changes.
  - *Mitigation:* `COALESCE(share_side_pnl, 0)` in the `wheel_minus_bh` formula and in the final SELECT. Frontend treats NULL as `—` for display.
- **Risk:** Symbols with open positions show `total_realized_pnl` that excludes the still-open premium. Could read as "lower than I expected" for someone tracking gross.
  - *Mitigation:* Subtitle explicitly says "option $X + share $Y" — gross premium remains visible on the parallel "Total Premium" KPI card already present at the top of the page (it shows `summary.total_premium`).
- **Risk:** AMD's synthetic FC-021 rows interact with `total_realized_pnl`.
  - *Mitigation:* They're already accounted for in the scorecard view (verified — AMD `total_realized_pnl = $5,309` matches FC-021 closeout note). No change in behavior for AMD; this FC just makes the per-symbol page consistent with the scorecard table on Overview.

## Rollout

1. **Deploy the view first.** `bq query --use_legacy_sql=false < docs/bigquery/fc018_views.sql`. Idempotent. After deploy, query `bq query 'SELECT underlying, total_realized_pnl, wheel_minus_bh FROM options_wheel.fc018_vs_buy_and_hold_per_symbol ORDER BY underlying'` and confirm UNH `wheel_minus_bh ≈ +1,586`, AMD `total_realized_pnl ≈ +5,309`.
2. **Land the frontend PR.** Backend `get_vs_buy_and_hold` already does `SELECT *` so the new fields flow through automatically — no Python change required.
3. **Verify locally.** `npm run dev` in `dashboard/frontend`, navigate to `/symbol/UNH`, confirm top card $2,584 with subtitle, Wheel-vs-B&H "Wheel" $2,584, "Δ" +$1,586. Check 2-3 other symbols (AMD, AMZN, NVDA).
4. **PR merge.** Cloud Run frontend redeploy on merge. No backfill needed (views are recomputed on every read).

**Rollback plan:** revert the PR. View is idempotent — re-running the prior `fc018_views.sql` content from the parent commit restores prior behavior.
