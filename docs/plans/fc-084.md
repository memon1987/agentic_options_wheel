## Context

Every `smoke-test-*` step in `cloudbuild.yaml` identifies "the canary I just deployed" as
`gcloud run revisions list --limit=1`, and every `promote-*` runs `update-traffic --to-latest`.
Two builds 60 s apart on 2026-08-28 (`95d5b28` → `9aaf7d27`, `67b22d1` → `a7c941ff`) collided:
the first died at `deploy-bot-canary` with `ABORTED: Conflict for resource 'options-wheel-strategy':
version 'X' was specified but current version is 'Y'`. The build-failure alert fired (noise), and
by luck the newer commit ended up serving.

**Why rev 1 was rejected** (PR #95, two REQUEST_CHANGES; findings verified against live gcloud
source and build logs — read them before changing this plan again):

1. `gcloud run deploy --format=value(status.latestCreatedRevisionName)` is **not** "the revision
   this build created": gcloud re-reads the service after its Ready wait, and if another build's
   write landed during that 100–190 s wait, it returns *that* build's revision. **Proven live** on
   2026-08-27: build `046fd075` printed `revision [00530-wab]` — the revision created by the
   *other* build `0d9756c0`. gcloud's own source calls the field "slightly racy".
2. Ordering by revision `creationTimestamp` is write-race order, not commit order. The build that
   loses the deploy race is the one that retries 20 s later and therefore creates the *newest*
   revision — so a "newest revision wins" guard promotes the **older** commit, green build, no
   alert. Replaying 08-28 under rev 1 ends with `95d5b28` serving instead of `67b22d1`.
3. Pinning traffic with `update-traffic --to-revisions=REV=100` removes `latestRevision: true`
   from the service's traffic spec permanently. Cloud Run then keeps that split for every later
   revision, so **`gcloud run services update --update-env-vars ROLLER_ENABLED=false` creates a
   revision serving 0%** — every documented kill switch (`ROLLER_ENABLED`, `ROLLER_DRY_RUN`,
   `EARNINGS_ENABLED`, docs/CLAUDE.md §Development Notes) silently stops working.
4. The check-then-act superseded guard had a 5–10 s TOCTOU window, and `update-traffic` is
   itself an unretried optimistic-concurrency write exposed to the same Conflict.

**The insight both reviewers converged on:** "which revision is mine" and "which build is newer"
are both *known before the deploy runs* — from `$BUILD_ID` and Cloud Build's own build list — and
should not be inferred from Cloud Run state afterwards. Serialize builds per trigger up front,
and the deploy/promote steps never race at all.

## Scope

1. **A `serialize-builds` gate step** before any deploy: this build exits early as `SUPERSEDED`
   (exit 0) if a **newer** build of the same trigger exists; **waits** while an **older** build of
   the same trigger is still QUEUED/WORKING; proceeds when it is the newest and alone.
2. **Deterministic revision names** via `--revision-suffix` so each smoke test polls exactly the
   revision this build created, and the promote step verifies `latestReadyRevisionName` is that
   revision before promoting.
3. **Promote stays `update-traffic --to-latest`** (kill-switch semantics preserved; server-side,
   atomic; with serialization, "latest" is always this build's revision).
4. **Deploy retry** on `Conflict for resource` is kept as defense against *out-of-band* writes
   (an operator `services update` during a build) — it can no longer race another build.
5. Contract tests that pin all of the above and the full deploy flag set.

Out of scope: FC-081's `GIT_COMMIT` env var — **FC-081 (PR #94) now merges first**; this branch
rebases onto it and carries `GIT_COMMIT=$COMMIT_SHA` in all three env lists and in the fixture.

## Design decisions (made — do not relitigate in the build)

**Serialization gate** (`id: serialize-builds`, `waitFor: ['-']` so it runs alongside tests;
every `deploy-*-canary` adds it to `waitFor`):

- `ME=$(gcloud builds describe $BUILD_ID --format='value(createTime,buildTriggerId)')`.
  `$BUILD_ID` is a built-in substitution; it needs no escaping in `args`, but inside a `bash -c`
  script the shell must not see `$BUILD_ID` as a Cloud Build substitution *unless* that is
  intended — pass it via the step's `env: ['BUILD_ID=$BUILD_ID']` and read `$${BUILD_ID}` in the
  script. Same for `SHORT_SHA`.
- Loop (max 20 min, 20 s interval):
  `OTHERS=$(gcloud builds list --filter="buildTriggerId=<mine> AND status:(QUEUED,WORKING) AND id!=<mine>" --format='value(id,createTime)')`.
  - If any other build has `createTime > mine` → `echo "SUPERSEDED by <id> (<createTime>)"`,
    write `/workspace/superseded` and **exit 0**.
  - Else if any other build has `createTime < mine` → sleep 20 s, repeat (older build finishes
    first).
  - Else proceed (`exit 0`, no marker).
  - On loop timeout → `exit 1` (loud; a build stuck >20 min is a real problem, and the 1200 s
    build timeout would hit first anyway — set the loop to 15 min so this message wins).
- **Every subsequent deploy/smoke/promote step starts with**
  `[ -f /workspace/superseded ] && { echo "skip: superseded"; exit 0; }`. Cloud Build has no
  conditional steps; the marker is the mechanism. `run-tests`/`build-*`/`push-*` are unaffected
  (a superseded build still validates and pushes its image — harmless, and useful for rollback).
- Cloud Build SA `799970961417@cloudbuild.gserviceaccount.com` holds `roles/cloudbuild.builds.builder`,
  which includes `cloudbuild.builds.get/list`. **Builder must verify** with
  `gcloud projects get-iam-policy` (SA key at `~/.config/gcloud-agent/claude-operator-key.json`
  has read access) and record it; if absent, the plan's Rollout step 0 grants
  `roles/cloudbuild.builds.viewer` (operator).
- **Deliberate rollback story:** re-running an older commit's trigger creates the *newest build*,
  so it wins the gate and deploys the older code on purpose. A forward build racing it is
  superseded. This is the plan's intended semantics; document it in `docs/CLAUDE.md`.
- `gcloud builds list` `createTime` is RFC3339 with fixed-width fractional seconds → string
  compare is valid; the builder must assert the format on one real value in the PR body.

**Revision identity:**

- `SUFFIX="$${SHORT_SHA}-$${BUILD_ID:0:8}"` (lowercase, ≤ 63 chars total with the service name;
  Cloud Run revision names are `<service>-<suffix>`, DNS-label rules — `SHORT_SHA` is 7 hex and
  `BUILD_ID` prefix is 8 hex, both lowercase, so this is safe). `REV="<service>-$${SUFFIX}"` is
  known **before** deploy.
- Deploy adds `--revision-suffix=$${SUFFIX}`. After deploy: `gcloud run revisions describe $${REV}`
  must succeed, else `exit 1`. Write `REV` to `/workspace/rev-<svc>.txt` for the later steps.
- A retried deploy after a Conflict re-uses the same suffix: if the first attempt actually created
  the revision before erroring, the retry fails with "already exists" — treat **that** string as
  success (the revision exists, proceed to the describe check). Builder: test this path in the
  contract test by asserting the script handles both strings.
- Smoke: poll `revisions describe $${REV} --format=json`, parse the condition with
  `type == "Ready"` (not `[0]`), `True` → pass, `False` → fail, else sleep 5 s, 30 attempts.
- Promote: `LATEST=$(gcloud run services describe <svc> --format='value(status.latestReadyRevisionName)')`;
  `[ "$${LATEST}" = "$${REV}" ] || { echo "FAIL: latest ready is $${LATEST}, expected $${REV}"; exit 1; }`
  then `update-traffic <svc> --to-latest`. With serialization this can only fail on an
  out-of-band deploy — and then it must fail loudly, not promote.

**Flags preserved byte-for-byte**: image, region, memory/cpu, concurrency, instances, timeout,
the three `--set-env-vars` lists (now including `GIT_COMMIT=$COMMIT_SHA` from FC-081),
`--no-traffic`, `--tag=canary`. `entrypoint: bash` + `-c` for the deploy steps (needed for
the marker check and the suffix); shell variables `$${…}`; only `$PROJECT_ID`/`$COMMIT_SHA`
remain bare.

## Behavior contract

- Single build: identical outcome to today (deploy → ready → `--to-latest` → 100%).
- Two overlapping builds: the older one waits for nothing — **the newer one waits for the older
  to finish if the older started deploying first; otherwise the older exits SUPERSEDED before
  deploying**. Precisely: whichever build reaches the gate second sees the other; if the other is
  newer → exit SUPERSEDED; if older → wait. End state: the newest commit's revision serves.
  Replaying 2026-08-28: `9aaf7d27` (older) sees `a7c941ff` (newer) → SUPERSEDED; `a7c941ff` sees
  `9aaf7d27` still WORKING (in tests) → waits ≤ its remaining runtime → deploys. Only `67b22d1`
  ever serves.
- Deliberate rollback re-run: newest build → wins.
- `gcloud run services update --update-env-vars …` keeps shifting traffic immediately (traffic
  spec still `latestRevision: true`).
- SUPERSEDED is exit 0 with the literal line `SUPERSEDED` in the log — not a failure, no alert.
- Must NOT change: step ids for existing steps, existing `waitFor` edges (only additions), image
  names/tags, env lists (except FC-081's addition), 1200 s timeout, `serviceAccount`.
