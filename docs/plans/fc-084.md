# Plan: FC-084 — Pin every canary/promote step to the revision this build created

**Status:** Published — build-ready

## Context

Every `smoke-test-*` step in `cloudbuild.yaml` identifies "the canary I just deployed" as
`gcloud run revisions list --limit=1` (newest-first), and every `promote-*` step runs
`update-traffic --to-latest`. Neither is bound to the revision *this build* created.

**Reproduced 2026-08-28, not hypothetical.** Two pushes to `main` 60 s apart (`95d5b28`,
`67b22d1`) produced builds `9aaf7d27` and `a7c941ff`. The first failed at `deploy-bot-canary`
with `ABORTED: Conflict for resource 'options-wheel-strategy': version '…852178' was specified
but current version is '…310951'` — the second build had modified the service between the
first build's read and write. The build-failure alert fired (noise). Had the first build got
past the deploy, its smoke test would have polled the *second* build's revision and its
promote would have moved traffic with `--to-latest`, whichever that was.

This matters now because the FC program starting 2026-08-28 (`docs/plans/program-2026-08-28.md`)
merges several PRs per day. Merge spacing is a discipline, not a guarantee; this makes overlap
safe.

## Scope

In scope:
1. Each `deploy-*-canary` step captures the revision name it created into a workspace file.
2. Each `smoke-test-*` step polls **that** revision's `Ready` condition by name.
3. Each `promote-*` step routes 100% to **that** revision by name — never `--to-latest`.
4. A **superseded guard** on promote: if the currently-serving revision was created *after*
   this build's canary, skip the promote (exit 0, log `SUPERSEDED`). Newer code stays serving.
5. A retry on the deploy step for Cloud Run's optimistic-concurrency `Conflict` error (the
   exact failure seen today) — up to 3 attempts, 20 s apart.
6. A contract test that pins 2–4 so a future edit cannot quietly reintroduce `--to-latest`.

Out of scope (deliberately): serializing builds at the trigger level (Cloud Build has no
first-class per-trigger concurrency limit worth depending on); changing the dashboard's
`TRADING_BOT_URL` env or any other deploy flag; FC-081's `GIT_COMMIT` env var (separate PR,
touches the same `--set-env-vars` lines — **FC-081 must rebase onto this after merge**).

## Design decisions (made — do not relitigate in the build)

- **Revision identity via `gcloud run deploy --format='value(status.latestCreatedRevisionName)'`**,
  written to `/workspace/rev-<svc>.txt`. Cloud Build steps share `/workspace`; this is the
  documented hand-off mechanism. Alternative rejected: resolving the `canary` tag — a tag is
  also "whoever deployed last", i.e. the same race.
- **Readiness via `gcloud run revisions describe $REV --format=json`** parsed for the
  condition with `type == "Ready"` (not `conditions[0]` — Ready-first is observed, not
  contractual; FC-084 entry notes this). Parse with `python3` from the cloud-sdk image (present).
  Keep the existing poll shape: `True` → pass, `False` → fail immediately, otherwise sleep 5 s,
  30 attempts.
- **Promote via `update-traffic --to-revisions=$REV=100`.**
- **Superseded guard compares `metadata.creationTimestamp`** of the serving revision
  (`services describe --format='value(status.traffic[0].revisionName)'`, then
  `revisions describe`) against this build's revision. Newer-serving → `echo SUPERSEDED …; exit 0`.
  Timestamp ordering, not git ancestry: Cloud Build's checkout is shallow, and a deliberate
  rollback (re-running an older commit's trigger) creates a *newer* revision and should win —
  which this rule gives. Exit 0, not 1: a superseded build is not a failure and must not
  trip the build-failure alert.
- **Deploy retry** wraps only the `gcloud run deploy` call, matches on the literal string
  `Conflict for resource`, and re-runs the identical command. A retried deploy creates one
  more revision; harmless.
- **All three chains change identically**, including the CC chain (`deploy-cc-canary` /
  `smoke-test-cc` / `promote-cc`), which the FC entry lists.

- `tests/test_cloudbuild_contract.py` — new (see Tests).
- `docs/CLAUDE.md` — one paragraph under the deploy/CI section describing the pinned chain

## Behavior contract

- A single build's outcome is unchanged: deploy → ready → 100% traffic on the new revision.
- Two overlapping builds: each promotes only its own revision; the later-*created* revision
  is what serves at the end, regardless of which build *finishes* last.
- A build whose deploy hits the Cloud Run version conflict retries and succeeds instead of
  failing.
- Must NOT change: image names/tags, env var sets, memory/CPU/timeout flags, step ids,
  `waitFor` graph, the 1200 s build timeout, `serviceAccount`.

## Tests

`tests/test_cloudbuild_contract.py` (parse `cloudbuild.yaml` with `yaml.safe_load`):

1. No step's args/script contains `--to-latest`. *(Regression: someone restores the race.)*
2. No `smoke-test-*` step contains `revisions list` with `--limit=1`. *(Same.)*
3. For each service in {`options-wheel-strategy`, `covered-call-engine`, `options-wheel-dashboard`}:
   the deploy step writes `/workspace/rev-<svc>.txt`, and both its smoke and promote steps
   read the same path. *(Regression: a chain edited inconsistently.)*
4. Every promote step contains `--to-revisions=` and the string `SUPERSEDED`. *(Regression:
   guard removed.)*
5. Every deploy step contains `Conflict for resource`. *(Regression: retry removed.)*
6. Step ids, `waitFor` edges and `--set-env-vars` values are identical to a frozen fixture
   captured from the pre-change file. *(Regression: an accidental flag change while
   restructuring — this is the must-not-change list, pinned.)*

Mutation check before opening the PR: change one promote back to `--to-latest` → test 1 and
4 fail; delete the retry → test 5 fails.

   logs `SUPERSEDED` and exits 0 while traffic ends on the later-created revision.
