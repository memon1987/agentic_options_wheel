## Context

`BacktestBroker` has one fill model: every order fills at `mid ∓ fill_haircut × half-spread` (`broker.py:138-144`), and `BacktestAlpacaClient.place_option_order` *records* the strategy's `limit_price` and ignores it (`alpaca_adapter.py:329-343`). The live `CallRoller` is credit-only **at its placed limits**: base mode BTC at `round(ask, 2)` of the old contract and STO at `round(bid, 2)` of the candidate; imminence mode (the old contract's extrinsic ≤ `rolling_imminence_extrinsic_threshold`, `call_roller.py:343`) rests both legs at `round(mid ± 0.05, 2)` (`_IMMINENCE_PAD`, `:60`, `:352-353`, `:526-544`); the credit invariant is tested on those limits before placement and again per ladder rung (`:952-999`), each leg polled 120 s then cancel-and-settled (`:1085-1127`). The FC-100 §Phase C hand-off required the replay to fill at those limits ("filling at mid would manufacture credit the live roller never sees"); Phase C could not, because the wheel golden was byte-bound, and instead labelled BOTH roll biases in `ROLL_REACH_BIAS` (`report.py:297-332`): credits UP (haircut fills), counts/credits DOWN (21-DTE reach vs a 28-DTE need).

Two opposing, unmeasured biases on one metric is the honest interim, not the answer — and FC-112 (the wheel's 0.98-vs-1.00 trigger study) reads exactly that metric. This plan replaces the roll-leg fill model, re-baselines deliberately, and hands FC-112 an honest number.

**What the data can and cannot support (decisive for D1).** The chain lake stores `mark`, modeled `bid`/`ask`, `delta`, `iv`, `volume` per contract-day (`chain_store.py:97-127` `_COLUMNS`); it does **not** store the option bar's `high`/`low`, and `ChainQuote` (`chain_builder.py:126-144`) has no field for them. A "did the day's range cross the limit" test is therefore not available without a lake schema change and a cold re-fetch of every symbol-year (a file missing a quote column is discarded on read — `chain_store.py:766-768`). The replay has one modeled book per decision day and no intraday tape.

## Goals

1. Roll legs (BTC and STO, both profiles) fill at the **placed limit against the day's modeled book**, or do not fill — so a replayed roll captures the credit the live roller's own invariant would have booked, never more.
2. Entry legs and the CC monitor leg keep the haircut model (FC-072 measured entry fills against it; `strategy.*_limit_spread_fraction` is refused as a sweep key for that reason — `BACKTEST_ENGINE.md:658`).
3. The mode is an **arm field** `roll_fill_mode: limit | haircut` (default `limit`), in `scenario_arm_hash`, so a haircut-vs-limit pair can run in one sweep and the before/after is one submission.
4. The wheel is **re-baselined in this PR, once**: `ENGINE_VERSION` bumped, frozen fixtures regenerated, the diff explained in the PR body (roll credits move; nothing else should).
5. `ROLL_REACH_BIAS` loses the "credits UP" clause; a new `ROLL_FILL_RULE` states the rule on both strategies' footers; both byte-pinned copies and the parity test move together.
6. Roll legs that would not have filled live are **counted** (`roll_skips` gains the roller's post-placement terminals), never silently converted into fills.
7. FC-112 gets a per-row roll-credit metric it can read on WHEEL rows.

## Non-goals

- Modelling fill *probability* (quote motion between quote and placement, partial fills, queue position). The replay models **price**, not probability; the residual is named in the footer, not estimated.
- Adding option OHLC to the lake / a range-touch fill test (follow-up FC — see §Found while planning 1).
- Widening the WHEEL's roll reach (7 + 14 = 21 against a 7-DTE materialisation — `runner.py:519-527`). It moves wheel numbers for a *different* reason and must be its own re-baseline so this PR's golden diff stays attributable (§Open questions Q4).
- Any change to `src/strategy/call_roller.py`. The roller is the live twin; the replay adapts to it.
- Tick snapping of roller limits (FC-088). Under the rule below a through-the-book limit fills at the book, so FC-088 cannot later overpay the replay.
- The wheel's `/monitor` leg (FC-086 / a later FC), CC re-seed posture, FC-117's CC battery set.

## Proposed approach

### D1 — The roll-leg fill rule (`roll_fill_mode: limit`)

Implemented in `BacktestAlpacaClient.place_option_order` when the adapter's **order intent** is `roll` (D1b); the broker gains an explicit-fill entry point (D1c). Against the contract's quote on the decision day (`_find_quote` → `bid`, `ask`; `mark` unused on this path):

| leg | condition | fill | order status |
|---|---|---|---|
| buy (BTC) | `limit ≥ ask` | **`ask`** (marketable; Alpaca fills at the best offer, never at a worse limit) | `filled` |
| buy | `bid ≤ limit < ask` | **`limit`** (resting inside the spread — assumed touched within the leg's 120 s window; see the approximation below) | `filled` |
| buy | `limit < bid` | none | `expired`, `filled_qty 0`, `filled_avg_price None` |
| sell (STO) | `limit ≤ bid` | **`bid`** | `filled` |
| sell | `bid < limit ≤ ask` | **`limit`** | `filled` |
| sell | `limit > ask` | none | `expired`, `filled_qty 0` |
| either | `limit_price is None` (a market order under roll intent) | far quote (`ask` buy / `bid` sell) | `filled` |

- **Order-error precedence (E7):** the pre-fill checks run first and unchanged — `no_quote`, then `no_position`/qty on a BTC, `insufficient_shares` on an STO, then `insufficient_cash` on a BTC — and only a leg that clears them reaches the fill rule. Live Alpaca rejects those at placement, so the roller sees `btc_rejected`/`stc_rejected`, never `expired`; the table's `expired` rows are reached only by a limit outside the book. The `insufficient_cash` message (`alpaca_adapter.py:399`, today `buy_fill(mark, ask) · 100 · qty`) quotes the cost at the RULE price under roll intent, so the message and the ledger agree. Fees (`fees_per_contract`) unchanged. `_order_intent` is initialised in `__init__` (`alpaca_adapter.py:70-95`): the adapter's `__getattr__` raises on any missing attribute (`:505`), so a lazily-set attribute would turn the first haircut-mode read into `UnsupportedBacktestCall`.
- **Cent rounding (T5/E2):** every roller limit is `round(·, 2)` (`call_roller.py:352-353`, `:539-543`, `:970`); modeled quotes are not rounded (no `round(` in `spread_model.py`/`chain_builder.py`; `spread_model.py:73` only clips the bid at 0). A base-mode BTC limit therefore lands within ±$0.005 of the ask: rounded up → marketable → fills at `ask`; rounded down → resting → fills at the limit. Either way `|fill − ask| ≤ $0.005`, so the delta laws below hold to ≤ $0.01/share/leg and T5/T7 assert the per-leg RULE on the scripted quotes (`min(limit, ask)` / `max(limit, bid)`), not an exact algebraic identity.
- An unfilled leg returns `success: True` with a **terminal** order record (`status: "expired"`), so `CallRoller._poll_order_fill` returns on its first `get_order_by_id` read (`_TERMINAL_ORDER_STATUSES` includes `expired`, `call_roller.py:77`) with **no `time.sleep`**, and the roller's own dispositions apply unmodified: BTC → `call_roll_btc_timeout_canceled` with `disposition=terminal_no_fill` and reason `btc_timeout_canceled`; an STO rung → `call_roll_stc_unfilled` then the next rung of `_rungs`; ladder exhausted after a BTC fill → `call_roll_naked_exposure` / reason `stc_failed_naked_exposure` (shares stay uncovered in the sim exactly as live; the next day's scan re-covers through the entry gates). `_cancel_and_settle`/`cancel_order` are never reached. That is NOT pinned by the adapter's `__getattr__` raise: `_safe_cancel` swallows every exception (`call_roller.py:1149-1157`), so a reached cancel would silently return `False` and settle. The guard is (a) the adapter only ever returns terminal statuses (`filled`/`expired`) under roll intent, and (b) T3's `time.sleep` raise — a non-terminal status is the only way the roller sleeps, and the only way it reaches the cancel path (T4).
- **The honest approximation, stated per pricing mode (D4):** the roller runs once per replay day against that day's single modeled book, so "within 120 s" collapses to "against the book at the decision". Modeled half-spread `hs = max(0.02, (0.05 + 0.10·|1 − K/S| [+ 0.05 if mark < 0.50]) · mark)` (`spread_model.py:43-63`) — "5% of mark" is the base term only; the OTM and cheap-contract widenings are part of `hs` and the footer must not quote the base term as if it were the spread.
  - *Base mode* (BTC at the ask, STO at the bid): both legs are marketable within a half-cent and fill at the book — the price the live invariant was computed on. **No residual.**
  - *Imminence mode* (`mid ± 0.05`): the pad rests inside the book whenever `hs > 0.05` (ATM mark ≳ $1) and the leg is assumed to fill at its limit. The residual vs the far quote is **`hs − 0.05` per leg** — NOT "bounded at $0.05" as rev 1 claimed: it grows with mark (a GOOGL/UNH-priced chain with `hs ≈ $0.40–1.00` rests $0.35–0.95/share/leg on the assumption). When `hs ≤ 0.05` the pad is through the book and the leg fills at the far quote (no residual). This is the ONLY residual of the model and it is **measured, not estimated**: every roll-leg ledger event carries `fill_rule ∈ {limit_marketable, limit_resting, haircut}` + `limit_price` (D1c), and the per-cell counters `roll_legs_resting` / `roll_legs_marketable` (D6) say how much of a row's roll credit rests on it.
- **Net effect vs today's haircut fill (`mid ∓ 0.25·hs`), per pricing mode, per roll that fills:**
  - *Base:* **`−0.75 · (hs_old + hs_new) · 100 · contracts`** — always DOWN (each leg moves from `mid ∓ 0.25·hs` to the far quote).
  - *Imminence:* **`(0.25·hs − 0.05) · 100 · contracts` per leg**, i.e. `(0.25·(hs_old + hs_new) − 0.10) · 100 · contracts` per roll — **either sign**: UP whenever `hs > $0.20` (a resting BTC at `mid + 0.05` PAYS LESS than today's `mid + 0.25·hs`, and the STO mirror RECEIVES MORE), DOWN below it. Imminence rolls on high-mark chains carry MORE credit under `limit` than under the haircut model; `ROLL_FILL_RULE` says so (D4).
  - `execute_roll`'s success dict (`call_roller.py:818-826`) carries no `pricing_mode` (only the `call_roll_*` events do), so the sim segments the two laws by the ledger tag, not the record: a roll whose legs are `limit_marketable` followed base mode; `limit_resting` is imminence (or a rung ≥ 2 floor).
  - Counts do not move on model-built chains: a base BTC limit `round(ask) ≥ ask − 0.005 > bid` (spread ≥ $0.04); an imminence BTC limit `mid + 0.05 > bid`; the STO mirrors hold. **No rung-1 roll leg ever expires on a lake/model-built chain**, so the `expired` branch, the D5 post-placement terminals and rungs ≥ 2 are exercised only by hand-built or real-quote chains (T3) — on the battery they read 0, and a non-zero there is a finding, not a re-baseline.

**Rejected fill rules, with the evidence:**
- *Full-day high/low range test* ("a limit inside the day's range fills"). Not available: the lake stores no option OHLC (Context); adding it is a lake schema change and a cold re-fetch of every symbol-year. Also wrong-shaped even if available: a 6.5 h range is not a 120 s window at 15:30, and a real range against a *modeled* book is self-inconsistent (a close at the day's high would fail a marketable buy at the modeled ask). Filed as a follow-up (§Found 1).
- *Fill at the placed limit unconditionally.* Never worse than live and overpays whenever a limit is through the book (FC-088 will snap BTC limits UP to a tick, above the ask); never expires. The book-capped rule above is strictly more faithful at no extra cost.
- *Resting legs never fill* (pessimistic). Converts EVERY imminence-mode roll into `btc_timeout_canceled` by construction, because the modeled half-spread exceeds the $0.05 pad for any mark above ~$1 — the replay would say "imminence mode never works", a model artefact, not a market fact.
- *Stochastic fill probability* (e.g. from a measured fill rate). Non-deterministic or needs a seed in the identity; and there is no roll-leg fill-rate data yet (the CC roller has not run; the wheel's `call_roll_btc_filled` vs `_timeout_canceled` events could inform a later FC).
- *Keep the haircut.* The FC's premise; rejected by the operator ("proceed").

**Entry legs keep the haircut** (FC-072 measured entry fills against it and re-priced the live limits off a fresh mid; `strategy.*_limit_spread_fraction` is refused as a sweep key because the replay cannot honour it — that refusal and its measured evidence stand). The CC monitor leg (`_run_monitor_leg`, `simulator.py:1245`, a market order) stays on the haircut path.

**D1b — how the adapter knows a roll leg.** The adapter gains an intent context, `BacktestAlpacaClient.order_intent(kind)` (a `contextmanager`; attribute `_order_intent: Optional[str]`, default `None`), and the simulator wraps the roll seat: `with client.order_intent("roll"): rolls = engine.run_rolling_cycle() or {}` (`simulator.py:975`). Inside that window the roller is the only order placer (the scan/execute phase ran before it; the monitor leg runs elsewhere in the loop). Rejected: (i) a new kwarg on `place_option_order` threaded through `CallRoller` — changes the live `AlpacaClient` surface for a replay concern; (ii) inferring "roll" from `side == "buy"` on a call — the CC monitor leg buys to close too and must stay on the haircut path. The adapter sees no order KIND today (only symbol/qty/side/type/limit) — the intent context is the minimal way to give it one.

**D1c — broker entry point.** `BacktestBroker.sell_call_to_open(...)` and `buy_to_close(...)` gain a keyword `fill: Optional[float] = None`; `None` → today's `sell_fill`/`buy_fill` (byte-identical for every existing caller); a float → that price is the fill, everything else (fees, cash/collateral checks, `_record`) unchanged. The adapter computes the price per the table and passes it. The `_record` detail gains `fill_rule` on EVERY `buy_to_close`/`sell_call_open` event: roll-intent legs under `limit` carry `"limit_marketable"` (limit at/through the far quote, filled at the book) or `"limit_resting"` (limit inside the spread, filled at the limit); every other leg — entry, monitor, and roll legs under `roll_fill_mode: haircut` — carries `"haircut"`. Every roll-intent leg (both modes) also carries `"limit_price": <placed>`; non-roll legs do not. A stored ledger therefore shows fill-vs-limit per leg AND which legs rest on the imminence assumption (Q5, decision ii). The adapter, not the broker, chooses the tag (it is the only party that knows the limit and the intent) and passes it to the broker as `fill_detail: Optional[dict]` beside `fill`. Rejected: a second broker class or a mode flag on the broker — the broker would then need to know order intent, which is the adapter's concept; one price-in keyword keeps the broker a pure ledger.

**Under `roll_fill_mode: haircut`** the adapter ignores the intent and behaves exactly as today (regression path; the before/after arm).

### D4 — Footer prose (both byte-pinned copies + the parity test)

- `ROLL_REACH_BIAS` (`report.py:297-332`): title → `"Covered-call ROLL candidates are truncated at 21 DTE, so roll counts and credits are biased DOWN"`; the second paragraph ("In the OPPOSITE direction … combined into a single number") is deleted; the reach, wheel-truncation and `roll_skips` paragraphs stay. The FC-112 sentence stays.
- New `ROLL_FILL_RULE = ("Roll legs fill at the placed limit against the day's modeled book, or not at all", "...")` — the detail states, in this order: (1) BTC fills at the ask when its limit is at/through it, STO at the bid (base mode); a limit resting inside the modeled spread (imminence mode, `mid ± $0.05`) is assumed to fill at its limit within the leg's window — the replay has one book per day and no intraday tape; a limit outside the book expires and the roller's own ladder/terminals apply (`roll_skips` carries them). (2) **Roll credits now pay the FULL modeled spread on both legs** — base-mode `credit = (mark_new − mark_old) − (hs_new + hs_old)` — and the spread model measures **~2.46× wider than the real book** (`docs/BACKTEST_ENGINE.md:125`; `report.py:289`), so replayed roll credits AND roll counts (an invariant tested on wider spreads fails more often) are biased DOWN vs live. `MODEL_SPREAD_BIAS` says this today only for a CC run with `spread_gate_suspended` (`report.py:392-393`); the wheel gets the statement here. (3) The one residual: an imminence-mode leg rests `hs − 0.05`/share inside the far quote, which is NOT small on high-mark chains, and it cuts BOTH ways against the old model — an imminence roll on a chain with `hs > $0.20` carries MORE credit under this rule than the haircut model gave it; `roll_legs_resting` on the row counts how many legs rest on the assumption. (4) On lake/model-built chains no roll leg expires (every rung-1 limit lies inside the book by construction), so a zero in `roll_skips`' post-placement terminals is the model, not evidence that live rolls always fill; and the replay attempts every roll the roller wants, whereas live's per-position and cycle budgets (`wheel_engine.py:819-827`, FC-113) can truncate a ladder. ### D6 — FC-112 as the consumer: the metric and why it is honest now

FC-112 compares `rolling.itm_trigger_ratio ∈ {0.98, 1.00}` (+ `rolling.enabled: false`) on the wheel's standing set and needs, per row: `rolls_executed`, the ITM/OTM split, and the **roll credit** split the same way. Today: (i) the split is `None` on wheel rows (`runner.py:674-675`) and printed only in the CC table (`report.py:488`); (ii) **no roll-credit aggregate exists anywhere** (`grep net_credit` over `runner.py`/`report.py`/`artifact.py`/`evaluate.py`: none; `count_rolls` in `metrics/cycles.py:257` is a ledger-derived count). This PR adds, on both strategies:
- `SimulationResult.roll_net_credit`, `itm_roll_credit`, `otm_roll_out_credit` (Σ `record['net_credit']` by `roll_kind`, from the stamped records the simulator already builds). **All three are PRE-FEE (T7):** the roller's `net_credit = (stc − btc) · replaced · 100` (`call_roller.py:748`) excludes `fees_per_contract`; the ledger's `cash_delta` is post-fee. Defined that way on purpose — it is the number the live invariant guards and the number `call_roll_completed` reports — and the definition is in the column docs and the footer.
- `SimulationResult.failed_roll_btc_debit` (FLOAT, ≥ 0, post-fee cash paid on BTC legs of rolls that did NOT complete — `stc_failed_naked_exposure`, `partial_naked_exposure`, `stc_disposition_unknown`): a failed roll's BTC is real money in the ledger and contributes 0 to `roll_net_credit`, which would otherwise silently mis-state the roll programme's cost. Kept SEPARATE rather than folded into the aggregate so `roll_net_credit == Σ roll_records.net_credit` (T11) stays an exact reconciliation and the FC-112 reader can choose to net it. 0 on every model-built chain (D1: no leg expires).
- `SimulationResult.roll_legs_resting` / `roll_legs_marketable` (INT; decision ii): counts of roll-intent legs filled with `fill_rule == limit_resting` / `limit_marketable`, both profiles, read off the ledger detail at result build. `roll_legs_resting` is the measurability of the one residual — a row whose roll credit is mostly resting legs is the row to distrust first. Under `haircut` both are 0.
- all of the above on the artifact `counters` (plus per-leg `fill_rule`/`limit_price` in the ledger, D1c), on `ScenarioResult` rows and the `_row_from_report` stamp (drop the `None if report.is_wheel` gating at `runner.py:674-675`), and on `scenario_runs` as **additive columns via `_ensure_table` (decision iv)** — NONE of the roll fields is a column today (`persist.py` schema list, `:404` neighbourhood, carries `fill_haircut` and no `rolls_executed`/`roll_skips`/`itm_rolls`/`otm_roll_outs`, though all four are on `ScenarioResult`, `runner.py:246-272`): `rolls_executed` INT, `roll_skips` STRING (JSON, the merged dict), `itm_rolls` INT, `otm_roll_outs` INT, `roll_net_credit` / `itm_roll_credit` / `otm_roll_out_credit` / `failed_roll_btc_debit` FLOAT, `roll_legs_resting` / `roll_legs_marketable` INT, `roll_fill_mode` STRING (resolved) — and in the sweep markdown as a `rolls itm/otm · credit` column on the per-symbol table for both strategies (one of the labelled wheel-markdown changes in the re-baseline).

Why honest: under `limit` a replayed roll's `net_credit` is `(stc_fill − btc_fill) × 100 × contracts` (pre-fee) at the book prices the live invariant was computed on — the same arithmetic `execute_roll` books live (`call_roller.py:748`). **D6 ships in this PR (decision iii; FC-112 is queued behind it), but the PR body keeps two labelled sections — "re-baseline diff" (the T5 table, fill-rule only) and "D6 additive fields" — so a reviewer can attribute every moved number to one or the other.** Under haircut every roll — and OTM re-writes in particular, which are the whole question of FC-112 — was flattered by `1.5 × half-spread` per share, i.e. the cost of crossing the spread twice is exactly the number that decides whether a same-day re-write is defence or churn. With `roll_skips` carrying the terminals (D5), FC-112 can also see rolls that would not have completed. FC-112 waits for this PR (its plan reads `roll_net_credit`, `itm_roll_credit`, `otm_roll_out_credit`, `roll_skips`).

## Behaviour contract

- **Unchanged (byte-identical, both profiles):** every non-roll fill (put STO, entry call STO, CC monitor BTC), fees, collateral/cash checks, assignment/expiry/dividend/early-assignment settlement, coverage buckets, `itm_rolls`/`otm_roll_outs` semantics, `roll_records` shape, legacy `canonical_spec` JSON, the roller's code and event vocabulary, the CC synthetic-lot chain, `spread_gate_suspended`.
- **Changed under `limit` (default):** roll-leg fill prices per D1 (base mode DOWN by `0.75·(hs_old+hs_new)`; imminence mode by `0.25·hs − 0.05` per leg, either sign); `roll_skips` may carry the six post-placement failure reasons (D5); new fields per D6; footers per D4; `provenance.fill`, ledger `detail` and `counters` keys; `engine_version`.
- **Live-vs-replay attempt asymmetry (named, not modelled):** live's per-position and cycle budgets (`wheel_engine.py:819-827`, FC-113) can truncate a ladder or skip a position with `cycle_budget_exhausted`; the replay attempts every roll the roller wants. Replay roll counts are therefore an upper bound on live attempts, independent of the fill rule; stated in `ROLL_FILL_RULE` (4).
- **`roll_fill_mode: haircut`:** replays exactly as today's engine (only the new fields/prose/version differ) — the regression arm.
- **Symmetry:** the wheel and CC profiles share one rule; no `strategy_id` conditional anywhere on the fill path (T7).
- **Invariants that must hold on any window:** every executed roll's `net_credit ≥ min_net_credit_per_contract × contracts` (fills ≥ the invariant's limits); `rolls_executed == itm_rolls + otm_roll_outs`; `roll_net_credit == itm_roll_credit + otm_roll_out_credit`; an unfilled leg never moves cash, positions or the ledger; a resting-inside fill is never better than the far quote; `roll_legs_resting + roll_legs_marketable == 2·rolls_executed + (BTC legs of failed rolls)` under `limit` and both are 0 under `haircut`; `failed_roll_btc_debit ≥ 0` and is 0 on every model-built chain; `roll_net_credit` is pre-fee (`Σ roll_records.net_credit`, exact).

## Risks & mitigations

- **Risk:** a non-terminal order status reaches `_poll_order_fill` → the replay sleeps 120 s per leg and the Saturday battery blows its wall cap. **Mitigation:** the adapter only ever returns `filled`/`expired`; T3 monkeypatches `time.sleep` to raise.
- **Risk:** the "resting-inside fills" convention flatters imminence-mode rolls on wide-modeled names. **Mitigation:** the residual is `hs − 0.05`/share/leg — NOT bounded at $0.05 (rev 1 error); it is named per mode in `ROLL_FILL_RULE`, and MEASURED per row (`roll_legs_resting`) and per leg (`fill_rule: limit_resting`) so a reader can discount it; `pricing_mode` is on every live `call_roll_completed` event so a later FC can measure the live fill rate of resting legs and calibrate.
- **Risk:** the first battery after merge replays everything (~25–35 min per `fc-096-b.md`, more if the lake widened). **Mitigation:** known, documented cost of any `src/**` change; `BATTERY_MAX_SECONDS` override exists for a catch-up run.
- **Risk:** frontend drops the arm key (found) or the API refuses it → console users cannot run the regression arm. **Mitigation:** T9 on all three validators.
- **Risk:** a `NULL` `roll_fill_mode` row read as `limit`. **Mitigation:** resolved value persisted; NULL documented as pre-FC-116/haircut; dashboard maps NULL → `haircut`.
- **Risk:** scope creep from D6 (new metrics) muddies the golden diff. **Mitigation:** the PR body has two labelled sections — "fill-rule diff" (T5 table) and "additive fields" — and T6 proves the only price movement is on roll legs.
- **Risk:** the wheel reach truncation (Non-goals) gets bundled in by a reviewer's request. **Mitigation:** Q4 records the decision; it is one line to widen later, with its own diff.
