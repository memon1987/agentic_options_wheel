## Context

`docs/CLAUDE.md` calls writing a covered call below cost basis a CRITICAL guaranteed-loss scenario. There are supposed to be two guards. On the `/scan → /run` path production actually executes, **one is dead and the other was, until today, a single fail-open field.**

- **Dead guard (the subject of this plan).** `CallSeller.execute_call_sale` reads `opportunity['stock_cost_basis']` and `opportunity['shares_covered']` (`src/strategy/call_seller.py:317-341`). Scanner-produced opportunities — the only kind production executes — carry **`cost_basis_per_share`** and **`max_contracts`** instead (`src/data/options_scanner.py:360-385`). The key lookup returns the `0` default, so `if stock_cost_basis > 0 and strike_price > 0` is False and **the execute-time floor has never run in production.** Only `CallSeller.evaluate_covered_call_opportunity` (the `wheel_engine` path, which production does not call) populates those keys. Same scanner-vs-engine path split that caused FC-048 and FC-045.
- **Scanner guard (hardened today, still narrower than FC-029).** FC-038 added a fail-closed skip when `cost_basis_per_share <= 0`, replacing warn-and-continue. But the scanner still derives basis from **raw Alpaca `cost_basis`** (`options_scanner.py:~128`), not FC-029's resolution chain. FC-029 (2026-05-08) empirically found Alpaca returns `cost_basis = 0` for assigned positions — exactly the moment the wheel next writes a call. Live re-check 2026-07-30 refuted that for all four current positions (correct non-zero values), so the behavior is not currently reproducible — but if it recurs, FC-038's guard now **silently skips the symbol**, which is safe on money and is precisely the silent-starvation failure mode this session just spent a day eliminating.

FC-029 R2 built the correct resolver (`wheel_state → BigQuery OPASN strike → Alpaca`) and it lives on the path production never runs. This plan puts it where production can reach it and makes the execute-time gate real.

**Interaction with FC-038 (merged today, `0545aff`):** covered calls can now size to `available_shares // 100`, so multi-contract calls are reachable. `execute_call_sale`'s `shares_covered` default of `100` would then divide a *total* cost basis by the wrong share count — a latent miscalculation this plan also closes.

## Goals

- The execute-time below-basis guard **actually runs** on scanner-produced opportunities, and blocks a below-basis strike.
- Floor resolution is **one implementation**, shared by the scanner and the call seller, following FC-029's documented source order.
- When no source resolves a floor for a held position, the system **fails closed** (no call written) with a distinct, queryable event — never "no floor, proceed".
- Share-count arithmetic is correct for multi-contract calls.
- No new silent-skip path: a symbol skipped for an unresolvable floor is loudly logged and distinguishable from "no opportunities".

## Non-goals

- Changing the delta band, premium floor, DTE targets, or any other filter.
- Changing FC-038 selection logic (two-pool budgeting, drop-reason enum).
- Fixing wheel-state persistence (FC-039) — source 1 of the chain stays dead in production; this plan must work without it.
- The boundary-dataclass normalization of opportunity shape (rejected as out-of-scope in `fc-048.md`; this plan hardens the two consumers instead, and Open Question 1 records the residual).
- Backfilling or auditing historical below-basis calls (verification item below produces the evidence; any correction is its own FC).

## Proposed approach

### Phase 1 — Extract the FC-029 resolver into a shared module

New `src/strategy/cost_basis.py` exposing `CostBasisResolver`:

```
CostBasisResolver(alpaca_client, config, wheel_state=None, allow_bigquery=True)
    .resolve(symbol, stock_position, shares_owned) -> float   # per-share, 0 if unresolved
```

Move the bodies of `CallSeller._resolve_cost_basis_floor` and `CallSeller._lookup_last_opasn_put_strike` into it **verbatim in behavior** — same source order, same back-fill of wheel_state on BQ hit, same lazy BQ client caching, same `allow_bigquery` gate, same log events. `CallSeller` keeps both method names as thin delegating wrappers so FC-029's existing tests (`TestCallSellerCostBasisFloorFC029`, 27 tests) continue to exercise the same contract unchanged. This is a refactor with zero behavior delta — reviewers should be able to verify that claim mechanically.

### Phase 2 — Scanner resolves via the chain

`OptionsScanner.__init__` constructs a `CostBasisResolver` (it already holds `alpaca` and `config`; `wheel_state=None`, `allow_bigquery=True`). `scan_for_call_opportunities` replaces `float(position['cost_basis']) / shares` with `resolver.resolve(symbol, position, shares)`.

- Keep FC-038's fail-closed skip, now on the **resolved** value: `<= 0` → skip symbol, log `call_scan_skipped_cost_basis_unresolved` (existing event, unchanged shape).
- Add a distinct event when the chain resolved from a **non-Alpaca** source (`event_type="cost_basis_resolved_via_fallback"`, fields: symbol, source ∈ {wheel_state, bigquery, alpaca}, resolved_basis) so a future investigator can see the floor came from BQ rather than the broker.
- `_create_call_opportunity` must use the same resolved value (pass it in rather than recomputing from `stock_position['cost_basis']`) — one number per symbol per scan, used for the floor, `assignment_above_cost_basis`, and `total_return_if_assigned`.

Construction-site note: `OptionsScanner` is constructed at `deploy/cloud_run_server.py:160` (`/scan`) **and** at `main.py:79` (CLI `--command scan`) — the plan originally claimed only the former; corrected 2026-07-30 (builder + reviewer 1). Both are live-account paths, so `allow_bigquery=True` remains correct for both; note the CLI path will query production BigQuery from a developer machine via ambient ADC (read-only). The backtest simulator does not use the scanner, so `allow_bigquery=True` here cannot leak production BQ into a replay. `CallSeller`'s existing `allow_bigquery_cost_basis=False` backtest path (`simulator.py:326`) must keep working through the delegation.

### Phase 3 — Make the execute-time gate real and fail closed

In `CallSeller.execute_call_sale`, replace the two direct key reads with a small module-level helper in `cost_basis.py`:

```
opportunity_floor_per_share(opportunity) -> float
```

Resolution order, first positive wins:
1. `cost_basis_per_share` (scanner shape).
2. `stock_cost_basis / shares_covered` (wheel_engine shape), where `shares_covered` falls back to `contracts * 100` when absent — never a bare `100`.

Then:
- Floor `> 0` and `strike_price < floor` → block, preserving the existing `call_below_cost_basis_blocked` error event and `strike_below_cost_basis` return shape (no consumer changes).
- Floor `<= 0` → **block** with a new `error_type="cost_basis_floor_unresolved_at_execution"`, `non_retryable: False`, message naming the opportunity. This is the behavior change: previously an unresolvable floor meant "skip the check and trade". Mirrors FC-029's existing `cost_basis_floor_unresolved` block in `evaluate_covered_call_opportunity`.
- The existing put-misrouted-to-call_seller rejection (FC-045/FC-048 guard) stays ahead of this check, untouched.

**Why fail closed is safe here, not a new starvation risk:** post-Phase-2 every scanner opportunity carries a positive `cost_basis_per_share` (the scanner skips the symbol otherwise), and the wheel_engine path always sets `stock_cost_basis`. An unresolved floor at execution therefore means a malformed or third-party opportunity — the exact case that must not trade. Reviewers should attack this claim specifically.

## Risks & mitigations

- **Risk:** the refactor silently changes FC-029 behavior (source order, back-fill, BQ gating).
  - Mitigation: delegating wrappers keep the 27 existing FC-029 tests pointed at the same entry points; reviewers required to diff the moved bodies for behavior equivalence.
- **Risk:** fail-closed at execution blocks a legitimate call and re-creates starvation.
  - Mitigation: Phase 2 guarantees a positive basis on every scanner opportunity; new event is distinct and queryable; verification step below watches the first live cycles for any `cost_basis_floor_unresolved_at_execution`.
- **Risk:** scanner BQ lookups add latency/cost to `/scan`.
  - ~~Mitigation: chain short-circuits on Alpaca success in the common case; BQ path only on zero.~~ **CORRECTED 2026-07-30 (both reviewers): this mitigation was fictional and described a chain that does not exist.** Alpaca is the resolver's *last* source, not its first, and with wheel-state persistence dead in production (FC-039) **BigQuery is the de-facto primary floor source** — every held ≥100-share symbol issues one BQ query on *every* `/scan`, with the client rebuilt per request (the scanner is per-request). The real mitigation is measurement, not short-circuiting: `/scan` duration and BQ call volume must be measured post-deploy (moved to an explicit checklist item below). Consequence to note: `cost_basis_resolved_via_fallback` is misnamed — it fires on the common path, not a rare one — which is why the event now also carries Alpaca's value for comparison.
- **Risk:** a stale BQ OPASN strike resolves a *wrong* floor (e.g. after a manual share purchase at a different price).
  - Mitigation: source order puts wheel_state first and Alpaca last by FC-029's design rationale; the new `cost_basis_resolved_via_fallback` event makes a BQ-sourced floor visible rather than silent. Flagged as Open Question 2.

## Open questions

1. **Non-blocking.** Should the opportunity shape be normalized at the scanner/seller boundary (the dataclass idea deferred in `fc-048.md`) rather than hardening each consumer? This plan hardens; the class of bug recurs until the boundary is typed. Record as a follow-up FC if reviewers agree it is now the dominant residual risk.
2. **Non-blocking.** Should a BQ-resolved floor be trusted for a position whose share count doesn't match the OPASN quantity (partial manual sale, mixed lots)? Current design trusts it and logs the source. If reviewers judge that unsafe, the conservative alternative is `max(BQ_strike, alpaca_basis)` — call it out rather than silently changing FC-029 semantics mid-refactor.
3. **Blocking if reviewers disagree.** Is fail-closed at execution correct, given FC-038's fail-closed scanner skip already prevents the common case? The plan asserts yes (defense in depth on a guaranteed-loss path). A reviewer arguing it adds a starvation vector without adding safety would need to show a legitimate opportunity that reaches execution with no resolvable floor.
