## Context

The Decision Quality histogram (per-symbol page) shows the distribution of capture ratios across closed option trades. It tells the user "most trades captured 50–100%". It does **not** tell them the dollar magnitude — how much premium was actually kept versus how much was given back via early-close buybacks.

User asked for "total premium captured vs premium foregone for early close" alongside the chart.

Data accuracy was validated as part of this investigation:
- Capture-ratio formula in [bigquery.py:598-605](dashboard/backend/services/bigquery.py#L598-L605) is correct.
- UNH hand-trace (27 closed trades, raw Alpaca activity feed reconciliation 2026-05-07): $5,888 received / $4,334 captured (73.6%) / $1,554 foregone via buybacks. Held-to-outcome trades correctly fixed at 1.0. (An earlier draft of this plan listed $5,723 / $4,279 / $1,444 — those were arithmetic slips in pre-deploy back-of-envelope sums; corrected post-deploy reconciliation against the raw Alpaca feed.)
- Frontend `avg_capture` calculation in [DecisionQuality.tsx:46-48](dashboard/frontend/src/components/v2/DecisionQuality.tsx#L46-L48) is correct (nulls-contribute-0 sum divided by `counted` denominator, which excludes nulls).

No bugs to fix. The work is purely additive: surface the dollar magnitudes alongside the existing histogram.

## Goals

- Add three aggregate stats to the Decision Quality card header:
  - **Premium received** = `Σ premium_total` across all closed trades (gross top-line)
  - **Premium captured** = `Σ realized_pnl` (actually kept)
  - **Premium foregone (buybacks)** = received − captured (cash spent on buy-to-close)
- Show captured/foregone as both a dollar amount and a percentage of received.
- Disambiguate the "Foregone" label with "(buybacks)" — the term has another reasonable meaning (counterfactual: profit that *would have* materialized if held to expiry) that this number does NOT compute. The "buybacks" qualifier prevents misreading.

## Non-goals

- **Counterfactual "what if we'd held longer" analysis.** That would require option-chain snapshots at decision time (already filed as FC-017) and is out of scope here.
- **Per-bin dollar totals.** The histogram remains a count-based view; we surface dollars only at the macro level.
- **View / backend changes.** Required fields (`premium_total`, `realized_pnl`) are already on `DecisionQualityRow`; the aggregation happens client-side.

## Proposed approach

**Frontend** — `dashboard/frontend/src/components/v2/DecisionQuality.tsx`:

1. Compute three aggregates inside the existing `useMemo` (or a sibling memo):
   - `premiumReceived = Σ row.premium_total` over all `rows`
   - `premiumCaptured = Σ row.realized_pnl` over rows where `realized_pnl !== null`
   - `premiumForegone = premiumReceived − premiumCaptured`
   - `captureRatePct = premiumCaptured / premiumReceived` (top-line capture rate, distinct from `avg_capture` which is the per-trade average)

2. Render a three-stat row between the chart subtitle and the histogram:
   ```
   Received $5,888   Captured $4,334 (74%)   Foregone (buybacks) $1,554 (26%)
   ```

3. Use `fmtCurrency` for dollars and `fmtPercent` for ratios (existing utils).

4. The macro `captureRatePct` is dollar-weighted; the existing `avgCapture` is trade-weighted. Both are defensible; the new row is dollar-weighted because that's what the user asked for.

**Tests** — `dashboard/frontend/src/components/v2/DecisionQuality.test.tsx` (new):
- Asserts the three aggregate numbers render correctly given a fixture with mixed early-close + held-to-outcome trades.
- Asserts the foregone calculation is `received − captured` (not recomputed from per-row close_cost).
- Asserts the empty-state ("No closed trades to evaluate") still shows when `rows.length === 0`.

## Risks & mitigations

- **Risk:** "Foregone" label ambiguity — could be misread as the counterfactual ("how much we would've made by holding").
  - *Mitigation:* The label includes "(buybacks)" qualifier and the FC-017 counterfactual is explicitly out of scope. If user feedback signals confusion we can tweak the label later.
- **Risk:** Trades with `realized_pnl === null` (currently-open positions filtered out at the SQL level via `outcome != 'open'`, so this should never happen — but defensively handle).
  - *Mitigation:* Use `realized_pnl ?? 0` in the sum; null trades contribute 0 to captured. Same pattern as the existing `avgCapture` computation.
- **Risk:** Negative `realized_pnl` (loss-making early closes) reduce captured below received — capture rate could be a small positive or even slightly negative for symbols dominated by stop-loss buybacks pre-FC-010.
  - *Mitigation:* Keep the sign; show a negative percentage if it materializes. This is informational, not a bug.
