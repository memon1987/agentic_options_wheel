## Context

FC-096's console (Phases B–E) is only as good as the stored data under it. Today the
chain lake reaches **7-day DTE** (`universe_dte = max_dte + 1 = 8`), covers only the
14 live symbols, and grows only when a screen or sweep happens to run cold. Three
consequences Phase A removes:

1. **`put_target_dte` is allowlist-refused** (`overrides.py` `_CHAIN_REACH`) because
   every cached chain-day answers an 8-DTE request. The operator signed DTE ≤ 21 as
   a first-class knob (FC-096 D1a).
2. **Candidates can't be evaluated.** There is no second universe; a symbol not in
   `stocks.symbols` has no lake coverage and no path to get any (FC-060's unshipped
   Layer 3b).
3. **Freshness is accidental.** The lake extends only as a side effect of the
   monthly screen; a sweep submitted mid-month pays cold materialisation for recent
   days.

Facts this plan builds on (verified in-tree 2026-08-31): chains are **model-built
from bars** (`ChainBuilder`, `model_fingerprints` on `Materialised`), not
vendor-served — so historical DTE-21 chains are *recomputable* from re-fetchable
Alpaca bars; the lake's coverage-monotone replace already accepts a wider-DTE file
over a narrower one (`_covers` rejects only `narrower_dte`), while FC-091's merge
correctly refuses cross-DTE unions (`dte_mismatch`) — replacement, not merge, is the
widening mechanism; `scenarios/runner.py:509` sets `max_dte` from
`config.put_target_dte`; the monthly screen runs as a Cloud Run Job triggered by
Cloud Scheduler → `run.googleapis.com …/jobs:run` (`monthly-performance-review`,
`0 6 1 * *`) — the exact pattern the weekly Job copies.

## Goals

- A `stocks.candidates` universe beside `stocks.symbols`, invisible to the live
  scanner.
- A weekly Cloud Run Job (`data-backfill`) that keeps bars + lake current for
  live ∪ candidates at **DTE-21 reach**, weekends only.
- A one-time, resumable historical widening of the lake to DTE 21.
- A candidate onboarding path: one command/execution, ~5–20 min per symbol-year,
  idempotent.
- DTE ≤ 21 becomes sweepable (allowlist change), with the model-fidelity caveat
  forced into every report that uses it.

## Non-goals

- **No standing battery / pinning** — moved to Phase B (it needs the dedup re-key
  to avoid weekly recompute churn; running it before that lands would burn a full
  battery on every deploy).
- No sim service, no CC replay, no IAP, no console (Phases B–E).
- No change to the live scanner, sellers, or any trading path. The candidates key
  must have **zero** consumers in `src/strategy`, `src/data` (production scan), or
  `deploy/` request paths.
- No new BigQuery tables. Observability is structured logs (below).

## Proposed approach

### A1 — candidate universe

`config/settings.yaml` gains `stocks.candidates: []` (seed empty; operator adds
symbols by config PR — graduation to live is moving the symbol between lists, also
a config PR). Consumers, named per the config-discipline rule:
`main.py --command backfill` (symbol default set) and `Config.candidate_symbols`
(new accessor, returns `[]` when absent). **Not** mirrored into
`covered_call.yaml`: candidates are strategy-agnostic evaluation targets; the
backfill Job always reads the wheel profile. The FC-069 census appendix gets a row.

### A2 — DTE widening, forward + historical

- `main.py --command backfill` materialises at `max_dte=21` (constant
  `BACKFILL_MAX_DTE = 21` in `src/backtesting/data/backfill.py`, new module) →
  `universe_dte = 22` on written files.
- **Forward:** each weekly run covers the trailing `--history-days` (default 400)
  window; days already covered at ≥ 22 are skipped by the existing
  `ChainStore.get` coverage check; narrower (8-DTE) files are re-materialised and
  **replaced** via the existing coverage-monotone `put` (never merged —
  FC-091's `dte_mismatch` refusal stands untouched).
- **Historical (one-time):** the same command with `--symbols`/`--start`/`--end`
  chunks re-materialises history per symbol. Resumable by construction: every
  completed day is a lake object; re-running skips it. The operator runs it as
  Job executions over 1–3 weekends (rollout §4). Bars come from `BarStore` /
  Alpaca (re-fetchable); no vendor chain dependency.
- **Fidelity caveat (required, non-optional):** the chain model was validated
  against the 7-DTE production window. DTE > 7 quotes are model extrapolation.
  `src/backtesting/reporting/report.py` known-biases footer gains a line stating
  exactly that, emitted whenever the run's `max_dte > 7` — worded in the footer,
  not a docstring, because Phase E will render it to viewers.

### A3 — weekly Job + scheduler

- New module `src/backtesting/data/backfill.py`: `run_backfill(config, symbols,
  history_days, max_dte, chain_store, bar_provider) -> BackfillSummary`
  (per-symbol: days_checked / days_written / days_replaced_wider / bars_fetched /
  errors). Loops symbols independently; one symbol's failure logs
  `backfill_symbol_failed` and continues; exit code is non-zero if **any** symbol
  failed (fail-loud, matching the FC-039 standing rule).
- `main.py` `--command backfill` (CLI enum extended; docs/CLAUDE.md commands
  block updated) with `--symbols`, `--history-days`, `--start/--end` (historical
  mode). Env-driven in Job mode like the sweep (`BACKFILL_SYMBOLS` etc. optional;
  defaults need no env at all).
- `cloudbuild.yaml`: `deploy-backfill-job` step — same shape as
  `deploy-sweep-job`: bot image, superseded-marker check first line, `waitFor`
  behind all three promotes, `--max-retries=0`, `--task-timeout=21600` (6 h: a
  cold candidate-year plus weekly increments must fit; measured seed rate
  suggests ≤ 2 h typical), same 3 secrets + `GCP_PROJECT` + `CHAIN_LAKE_BUCKET`
  + `GIT_COMMIT`. Contract-test fixture extended; **no pre-existing step or
  `waitFor` edge changes** (must-not-change list).
- Scheduler: `backfill-weekly`, **`0 8 * * 6`** (Sat 08:00 UTC — market closed,
  zero Alpaca contention with the live bot; the FC-095 quota concern is
  sidestepped by calendar, not code). Created by the operator via the
  `monthly-performance-review` recipe (rollout §3); SIGTERM behaviour inherits
  the sweep Job's pattern: handler installed before work, terminal summary log
  in `finally`, SIG_IGN around the final log write.

### A4 — onboarding

Onboarding a candidate is: (1) config PR adding the symbol to
`stocks.candidates`; (2) `gcloud run jobs execute data-backfill` with
`BACKFILL_SYMBOLS=<sym>` (or wait for Saturday). No new endpoint — Phase B's sim
service gets the API/console affordance; Phase A ships the mechanism. Earnings
caveat: a candidate absent from the committed earnings table will replay with
`earnings_symbols_without_data` set — the existing `SimulationResult` fields
surface it; the report footer already prints it. Refreshing that table for
candidates is part of the onboarding checklist in `docs/BACKTEST_ENGINE.md`
(doc edit in this PR).

### A5 — allowlist change

`overrides.py`: `strategy.put_target_dte` moves from refused (`_CHAIN_REACH`) to
allowed with a value rule `1 ≤ int ≤ 21`; `strategy.call_target_dte`'s
may-only-be-lowered rule relaxes to `≤ 21`. The refusal reason for > 21 names
`BACKFILL_MAX_DTE`. Replay guard: `Simulator` already raises when
`materialised.max_dte != self.max_dte` — the sweep path materialises at
`max(21, config reach)` going forward (runner change at
`scenarios/runner.py:509`: `max_dte = max(int(base_config.put_target_dte), 21)`
is **wrong** — it must be the *maximum requested across arms*, computed from the
spec's DTE overrides, defaulting to `config.put_target_dte`; cold windows then
materialise wide enough for every arm, and warm windows hit the widened lake).
Dashboard mirror: `services/sweeps.py` imports the allowlist, so the API accepts
the same values with the same reasons — byte-equality tests already pin the
reason strings; they get updated fixtures.

## Reuse

- `ChainStore` put/replace/coverage/merge — **unchanged**; widening rides
  `_covers`' existing `narrower_dte` asymmetry. Do not touch FC-091 merge logic.
- `BarStore`/`CachedBarProvider` for bars; `chain_lake_seed.py`
  (tools/diagnostics) as reference for chunked seeding — the backfill supersedes
  it for future use (note added to its header, file kept).
- Sweep Job's SIGTERM/finalise pattern from `main.py` (FC-060 L3 round 2).
- `deploy-sweep-job` step shape + contract-test idioms.

## Behaviour contract

- Live scanner behaviour is byte-identical: no production path reads
  `stocks.candidates` (test: grep-style AST check, same idiom as
  `test_no_occ_substring.py`, asserting no import of `candidate_symbols` outside
  `main.py`/`src/backtesting`).
- A backfill run is idempotent: running twice on a covered window writes zero new
  objects (test with tmp lake).
- A DTE-8 lake object is replaced only by a file covering `universe_dte ≥ 22` and
  a strike window at least as wide (existing `_covers` tests extended with the
  22-over-8 case).
- Existing sweeps/backtests at DTE 7 are unaffected: their requests are covered
  by wider files (coverage check, not equality).
- `--command sweep` with a DTE-14 arm on a widened window succeeds; on an
  un-widened cold window it materialises at the max requested reach.

## Test requirements

- Unit: `run_backfill` window math, symbol-union default, per-symbol failure
  isolation + non-zero exit, summary counts (regression: a symbol error silently
  counted as success).
- ChainStore: 22-covers-8 replacement; 8-cannot-replace-22; FC-091 merge still
  refuses `dte_mismatch` (regression: widening accidentally enabling cross-DTE
  merges).
- Overrides: DTE 1–21 accepted, 22 refused with the named constant, non-int
  refused; dashboard allowlist byte-parity (regression: API/Job drift — the
  FC-060 invariant).
- Runner: `max_dte` derived from arms (spec with DTE-14 arm → materialise ≥ 14;
  no DTE arms → base config value) (regression: an arm silently replayed against
  chains that don't contain its contracts, reading as "nothing qualified").
- Report: footer line present iff `max_dte > 7` (regression: extrapolated quotes
  presented as validated).
- Cloudbuild contract: new step pinned; must-not-change list intact.

## Design decisions (made — do not relitigate in the build)

- **Replacement, not merge, widens DTE** — FC-091's `dte_mismatch` refusal is
  correct and stays; a 22-reach file strictly covers an 8-reach one, so
  coverage-monotone replace is the safe mechanism that already exists.
- **Battery deferred to Phase B** — running it before the dedup re-key would
  recompute the whole battery on every deploy.
- **Candidates in the wheel profile only** — one list, one reader; mirroring
  into `covered_call.yaml` would create the FC-069 two-profile drift hazard for
  a key the CC service never reads.
- **Saturday cadence** — quota isolation by calendar; rejected: weekday
  off-hours (still shares the day's rate budget) and a dedicated data key
  (FC-095, deferred with reasons).
- **`--task-timeout=21600`** — sized to worst-case candidate-year + weekly
  increment; the sweep Job's 10800 was sized for replay, not materialisation.
- **21, not configurable** — a knob here would let a sweep silently demand a
  reach the weekly Job doesn't maintain; the constant couples them, and the
  refusal message names it.

## Open questions

- **Non-blocking:** DTE-21 model fidelity — footer wording lands here; a proper
  validation (compare model quotes vs any obtainable real 14/21-DTE data) is a
  candidate FC, not Phase A.
- **Non-blocking:** whether the weekly Job should also refresh the committed
  earnings/dividend tables for candidates (today: manual, on the onboarding
  checklist). Revisit after the first candidate onboards.
