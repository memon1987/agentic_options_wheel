## Context

Phase A gave the data (22-reach lake, candidates, weekly refresh, DTE knob). The
operator experience is still batch-shaped: a `/sims` submit costs ~3 min of
Cloud Run Job cold start, and the replay's rich per-run detail — `DailyState`
equity curve, `LedgerEvent` audit trail, `WheelCycle`s, roll records — is
computed and **discarded** after aggregation into `ScenarioResult`'s ~30 scalar
fields (verified: `_replay_one` keeps scalars; only `evaluate.py`'s CLI path
walks `result.broker.ledger`/`result.daily`). Phase E's console (price+trade
timeline, equity/income/drawdown charts, ledger and cycle tables) cannot be
built on scalars.

Signed decision D1 (FC-096): a **scale-to-zero sim service** — ~10–30 s first
tweak of a session, ~2–5 s after, $0 idle; results persist so anything run once
is a read forever; dedup re-keyed from `git_commit` to engine identity; pinned
combos re-measured weekly.

Build-time facts this plan rides on (verified in-tree 2026-09-01): `run_sweep`
is a clean callable (`base_config, scenarios, symbols, start, end, *,
holdout_start, starting_cash, chain_store, bar_provider, quiet_logs`) returning
`SweepResult`; the replay executes **live strategy code** (sellers, scanner,
`market_data`), so an "engine-only" image is a fiction — the meaningful cold
start fix is that Cloud Run **services stream images** while Jobs pull them,
which is where the Job's ~2.5 min went; `evaluate.py` already builds cycles
from `broker.ledger` (`build_cycles`) and fitness from `daily` — the artifact
serialisers reuse those, not reimplement them; `OpportunityStore` is the
existing GCS-JSON write pattern; the sweep tables and their status/dedup
machinery (FC-060 L3) are reused wholesale.

## Goals

1. **`sim-service`**: a private Cloud Run service (scale-to-zero) that runs a
   sweep spec in-process and returns shaped results synchronously — seconds,
   not minutes, once warm.
2. **Detail artifacts**: every replay cell persists its equity curve, ledger,
   cycles, and roll records to GCS; the dashboard can serve them (rendering is
   Phase E).
3. **Engine-identity dedup**: stored results survive unrelated deploys
   (docs-only pushes stop invalidating every cached sweep).
4. **Pinning + weekly battery**: pinned specs and a small standing battery
   (base per strategy per symbol) re-measure on the Saturday Job so trend
   charts always have fresh, comparable history.

## Non-goals

- No covered-call replay (Phase C), no IAP/roles (Phase D — the submit path
  keeps the bearer token until then), no console UI (Phase E; `/sims` gets NO
  changes in this phase beyond none-at-all — the service is reachable only
  through a new dashboard proxy endpoint that Phase E will call).
- No new image. The service runs the existing bot image with a different
  command. A dedicated slim image is a measured follow-up only if streaming
  cold starts disappoint (>45 s p50), not a default.
- No change to the `backtest-sweep` Job path — it remains the fallback for
  big batteries and the API-submit path stays wired to it until Phase E cuts
  the console over.
- No `min-instances` (D1: $0 idle; warmth is a one-flag upgrade later).

## Proposed approach

### B1 — engine identity (PR-1; the re-key everything else leans on)

New `src/backtesting/scenarios/engine_identity.py`:
- `engine_identity()` → 16-hex sha256 over the **sorted relative paths +
  file contents of `src/backtesting/**/*.py`** plus `ENGINE_VERSION`
  (`screen.py`). Computed once per process (cached), deterministic per image,
  no git dependency at runtime.
- `identity.sweep_key(...)` replaces the `git_commit` component with
  `engine_identity`; `git_commit` stays **stored** on rows (provenance) but
  leaves the key. `docs/bigquery/scenario_runs.md` updated.
- **One-time cache invalidation on the record:** every pre-existing `done` row
  keys differently after this PR — the first re-submit of an old spec
  recomputes once. Accepted (that is the point: after this, only actual engine
  changes invalidate). FC-095's dedup-granularity item is hereby executed;
  strike that bullet from FC-095 at closeout.
- Both dedup predicates (persist.py Job-side, services/sweeps.py hint-side)
  and the Job/dashboard `submitted`/`running` rows carry
  `engine_identity` (additive NULLABLE column on both sweep tables).

### B2 — detail artifacts (PR-1)

- New `src/backtesting/reporting/artifact.py`: `cell_artifact(result:
  SimulationResult, meta) -> dict` — serialises `daily` (date, equity, cash,
  reserved_collateral, open_options), `broker.ledger` (every `LedgerEvent`
  field), `build_cycles(...)` rows, `roll_records`, dividends/early-assignment
  counters, and the run's provenance (hashes, reach, window, engine identity).
  Reuses `evaluate.py`'s builders; adds none.
- `_replay_one` gains an optional `artifact_sink` callback; `run_sweep`
  threads it. The **Job and the service both** write artifacts; the CLI writes
  them only under `--persist` (a local sweep stays disk-only).
- Storage: `gs://gen-lang-client-0607444019-options-data/sim-artifacts/v1/
  <run_id>/<scenario>__<symbol>__<split>.json.gz` (double underscore —
  scenario names allow single underscores). One object per cell,
  gzip-compressed JSON (~20–100 KB each). Write-through best-effort: an
  artifact failure logs `sim_artifact_write_failed` and sets a
  `artifacts_complete=false` flag on the done row (additive column) — it must
  NOT fail the sweep; the numbers in BigQuery remain the record. GCS lifecycle
  note for the operator: none needed at these sizes.
- Dashboard: `GET /api/v2/sweeps/{run_id}/artifacts/{scenario}/{symbol}/{split}`
  streams the object through the backend (the bucket stays private; the
  dashboard SA reads it). 404 when absent; no listing endpoint (the grid knows
  its cells).

### B3 — the service (PR-1)

- New `deploy/sim_service.py` (FastAPI, mirrors `cloud_run_server.py`'s
  conventions): `POST /simulate` — body is the **same spec schema** the sweep
  Job takes (reuse `services/sweeps.validate_spec` semantics by importing the
  engine's validators; the service holds a real `Config`, so validation is the
  engine's own, not the dashboard mirror). Flow: validate → `find_done_sweep`
  (engine-identity key; `force` honoured) → hit: return stored shaped results;
  miss: `run_sweep` in-process (chains from the lake via `ChainStore.from_env`,
  bars via `CachedBarProvider`) → persist rows + artifacts (status rows
  `submitted_via='sim-service'`, `running`→`done` same as the Job) → return
  shaped results in the response. `GET /health` standard.
- **Sync with a hard budget.** The request computes inline (that is the
  product); `SIM_MAX_CELLS = 48` (arms×symbols×splits) — larger specs are
  refused with "use the batch path" (the Job's 240-cap path stays for those).
  48 warm cells ≈ 15–60 s worst case; Cloud Run request timeout set to 300 s.
  Concurrency 1 (CPU-bound), `max-instances 2`, `min-instances 0`.
- **Private**: no `allUsers`; invoker = the compute SA (the dashboard backend
  calls it server-to-server with an ID token — same pattern as the sweep
  launch). The dashboard proxy endpoint `POST /api/v2/sims/run` enforces the
  existing `SWEEP_SUBMIT_TOKEN` until Phase D, then forwards. No new secret.
- Cold symbols: the service does NOT materialise cold windows (that can be
  hours). A spec whose (symbol, window, reach) coverage is not already in the
  lake is refused with a structured 409 naming the missing symbol-days and the
  remedy (onboard/backfill first). Coverage probe = `ChainStore` lake reads of
  the boundary days per symbol (cheap). The Job path keeps cold-materialise
  behaviour for deliberate long runs.
- Env: same secrets as the Job + `GCP_PROJECT`, `CHAIN_LAKE_BUCKET`,
  `GIT_COMMIT`, `STRATEGY_CONFIG=config/settings.yaml`. `@require_account_match`
  is NOT applicable (no trading) — noted explicitly so nobody adds it.
- Deploy: 4th chain in `cloudbuild.yaml` — `deploy-sim-canary` → `smoke-test-sim`
  (`/health` + one 2-cell warm `POST /simulate` against a lake symbol) →
  `promote-sim`, same marker/serialization discipline; contract-test fixture
  extended (tail-set now {sweep, backfill} preceded by four promote chains).
  The Job-failure alert policy is untouched (services are covered by the
  existing revision-scoped policies' pattern; the smoke test is the deploy
  gate).

### B4 — pinning + weekly battery (PR-2)

- New table `options_wheel.scenario_pins` (insert-only, latest-row-wins like
  the sweep tables): `pin_id`, `spec_json`, `active` BOOL, `written_at`,
  `note`. Dashboard endpoints: `POST /api/v2/sims/pins` (token-gated;
  cap **20 active** — 409 beyond), `GET /api/v2/sims/pins`,
  `DELETE /api/v2/sims/pins/{id}` (writes an `active=false` row).
- `main.py --command battery` (new): reads active pins + the standing set
  (base config per strategy per symbol over the trailing 1-yr window,
  holdout on; wheel-only until Phase C), submits each through the sweep
  machinery **with `--persist`**, engine-identity dedup making unchanged
  weeks nearly free. Runs at the END of the Saturday backfill execution
  (same Job, sequential: `--command backfill` then `--command battery` via a
  wrapper arg `BACKFILL_THEN_BATTERY=true` — one execution, data first).
- Battery rows are ordinary sweep rows; trend = query by spec identity over
  `written_at`. No new views in this phase.

## Reuse

`run_sweep`/`shape_results`/status rows/dedup wholesale; `evaluate.py`'s
`build_cycles` + fitness builders; `OpportunityStore`'s GCS-JSON idioms;
`cloud_run_server.py` conventions; the sweep Job's SIGTERM discipline is NOT
needed in the service (requests are short; Cloud Run drains on revision
replace).

## Behaviour contract

- A spec already `done` under the same engine identity returns in <2 s with
  zero replays (service and Job agree on the key).
- A pure Job-path sweep behaves exactly as today except two additive columns
  and artifact writes; `backtest_runs` untouched; CLI without `--persist`
  writes nothing anywhere (Layer-2 contract).
- Artifact absence never breaks results (grid renders from BigQuery alone).
- The service can never cold-materialise; its 409 names the remedy.
- Deploys that do not touch `src/backtesting/**` do not change
  `engine_identity` (test: identity computed twice across a docs edit).

## Test requirements

Engine-identity: deterministic across processes; sensitive to any
`src/backtesting` byte; insensitive to docs/dashboard edits; key-migration
test (old rows unreachable by new key, reachable by stored value).
Artifacts: round-trip serialise/deserialise; ledger/cycle equality with
`evaluate.py`'s builders on the same `SimulationResult`; write-failure sets the
flag and does not fail the run; gzip size sanity. Service: spec validation
parity with the Job (same refusals); dedup hit path; cell cap 409; cold-window
409 naming symbol-days; smoke-test contract; auth (no token at the proxy →
401/503; service direct-call unauthenticated → 403 by IAM, documented not
tested). Pins: cap, dedup of identical spec, inactive rows excluded.
Battery: composes backfill-then-battery; unchanged week ≈ all dedup hits.
Cloudbuild contract: 4th chain pinned; no pre-existing edge changes.

## Open questions

- **Non-blocking:** artifact retention (none proposed; ~5 MB/week worst case).
- **Non-blocking:** should the battery also run `at_the_bid` sensitivity arms?
  Default no (doubles cost; the console's fill-sensitivity view can use the
  stored `bid_fill_return` scalar).
- **Non-blocking (flag for Phase D):** the proxy keeps the token; IAP replaces
  it wholesale — no interim work.
