## Context

Phase A gave the data (22-reach lake, candidates, weekly refresh, DTE knob); the
operator experience is still batch-shaped (~3 min Job cold start per submit) and
the replay's rich detail (`DailyState` curve, `LedgerEvent` ledger,
`WheelCycle`s, roll records) is discarded after aggregation — Phase E's console
cannot be built on scalars. Signed decision D1: scale-to-zero sim service,
results persist forever, dedup re-keyed off `git_commit`, pinned combos
re-measured weekly.

**Round-1 verdicts (2026-09-01): both REQUEST_CHANGES, and they changed the
architecture.** The measured facts that killed rev 1's sync-response design:
warm-lake materialise costs 25–50 s per symbol (it dominates; replay is ~0.3
s/symbol-year), and THIS image running as a service shows a **240 s+ cold-start
tail** (14 days of live probe data: 10 startup-probe DEADLINE_EXCEEDED failures,
503s at 241–246 s, successful cold hits 23–52 s). A 300 s request budget bounded
by cell count bounds the wrong variable, and timeout-then-scale-down re-creates
the uncooperative-termination hole Phase A closed on the Job. Rev 2 is
**async-first**: the service persists and returns a handle; the console polls
the status machinery FC-060 already shipped.

## Goals

1. **`sim-service`**: private, scale-to-zero Cloud Run service. `POST /simulate`
   validates, dedups, and returns fast; results arrive via the existing
   status/results reads. Warm end-to-end for a small spec: seconds. Cold first
   hit: honest (the UI shows "warming"; measured 23 s–4 min tail), and warmth
   stays a one-flag upgrade per D1.
2. **Detail artifacts**: every replay cell persists curve/ledger/cycles/rolls to
   GCS with a pinned schema; dashboard can stream them (rendering is Phase E).
3. **Engine-identity dedup**: stored results survive deploys that cannot change
   replay output; anything that CAN change output invalidates.
4. **Pinning + weekly battery** with per-pin isolation and non-paging failure
   posture.

## Non-goals

- No covered-call replay (C), no IAP/roles (D — submit keeps the bearer token;
  the artifact endpoint's public-dashboard exposure question is explicitly
  punted to Phase D/FC-094 scope), no console UI (E). `/sims` is untouched.
- No new image (bot image, different command). A dedicated slim image only if
  rollout §2's measured cold p95 exceeds 120 s.
- No `min-instances` by default (D1); scheduled market-hours warmth stays a
  documented one-flag option (~$4–8/mo) the operator can turn on if the cold
  tail annoys in practice.
- The `backtest-sweep` Job path is unchanged and remains the big-batch route.

## Proposed approach

### B1 — engine identity (PR-a)

- `src/backtesting/scenarios/engine_identity.py`: `engine_identity()` = 16-hex
  sha256 over **sorted relative paths + file contents of `src/**` — ALL file
  types** (the replay executes live strategy code: `src/strategy/**`,
  `src/api/**`, `src/data/**`, `src/utils/**`; and the two committed data
  tables `src/backtesting/data/{earnings_dates,dividend_history}.json` are
  behaviour-bearing replay inputs). `ENGINE_VERSION` mixed in. Cached per
  process; content-only (mtime/`__pycache__`-immune — `.pyc` is not `*.py` and
  site-packages is outside the tree). Docs/dashboard/deploy/cloudbuild churn
  does not move it; a one-byte `put_seller.py` change does. **Required tests:
  sensitive to a `src/strategy/**` byte AND to a byte of either JSON table;
  insensitive to `docs/**`, `dashboard/**`, `deploy/**`, `cloudbuild.yaml`.**
- `identity.sweep_key`: `git_commit` component → `engine_identity`;
  `git_commit` stays stored (provenance). One-time cache invalidation accepted
  on the record (first re-submit of every old spec recomputes once; the first
  battery Saturday after ANY engine change is the expensive one — operator
  note). FC-095's dedup bullet is executed by this PR; strike at closeout.
- **Dashboard source of the value (rev-1 blocker):** the dashboard image cannot
  hash a tree it does not ship. `cloudbuild.yaml`'s dashboard build computes
  the hash from the same checkout (one `python - <<… engine_identity …` step
  writing a build-arg) and bakes it as `ENGINE_IDENTITY` env into the image;
  `services/sweeps.py` reads the env for its `sweep_key` hint and stamps it on
  `submitted` rows. **Parity contract test**: repo-side test computes
  `engine_identity()` and asserts the cloudbuild step's derivation script is
  byte-identical logic (shared module invoked, not reimplemented); rollout
  verifies live `/health` (service) == dashboard env. If the env is absent the
  hint path DISABLES itself loudly (log event) rather than keying wrong.
- Both sweep tables gain additive NULLABLE `engine_identity`; both dedup
  predicates require equality on it.
- **FC-092 fix (folded in, closes that FC's item 1):** `setup_logging`'s
  `cache_logger_on_first_use=True` makes every strategy logger bind the
  process's FIRST `RejectionTally` forever (measured: second in-process run
  gets `{}`). Fix at the mechanism: the tally binds through a `contextvars`/
  proxy-stable indirection instead of relying on `structlog.configure` in
  `__enter__` (exact idiom builder's choice; the CONTRACT is: N sequential
  `run_sweep` calls in one process each get their own complete tally —
  regression test with two runs asserting equal non-empty tallies). Item 2
  (ordering nondeterminism) fixed by sorting the summary; `PYTHONHASHSEED`
  no longer load-bearing for artifacts.

### B3 — the service (PR-c)

- `deploy/sim_service.py`, FastAPI, **sync `def` handlers** (an `async`
  **CPU allocation (rev-3 blocker fix): `--no-cpu-throttling` — instance-based billing.** Under default request-based billing the 202-then-background-replay design starves: CPU throttles once the request returns, and the poll never touches this service (it reads BigQuery via the dashboard). Instance-based billing is the documented mechanism for post-response work: ~$0.09/hr at 2 Gi / 1 vCPU only while an instance is ALIVE, $0 when fully idle — D1's substance ($0 idle, seconds warm) holds; its 'pay only per request' phrasing is corrected on the record. Pinned in deploy flags AND the cloudbuild contract test. Residual, accepted and documented: an idle instance can scale in mid-replay; SIGTERM terminalises the run as `failed` and the console's posture is resubmit — rare, bounded by one spec.
  handler would starve `/health` for the whole replay), `--concurrency=1`
  pinned in deploy flags AND the cloudbuild contract test (the engine's
  process-global swaps — ``_failed_symbols``, analytics singleton, log levels —
  are safe only serialized; module docstring states the invariant).
  **Correction on the record (PR-c review):** the per-process lock is NOT
  sufficient on its own. `--max-instances=2` means a second CONTAINER can
  accept the same spec a second later, and the rationale this plan gave for
  one-at-a-time — "two executions would contend on one chain cache" — is
  FALSE across containers, each having its own tmpfs. What is true is the
  waste and the confusion: two `running` rows for one question and two sets
  of cells the dedup can serve either of. PR-c therefore adds a
  cross-instance check (`persist.find_running_sweep`, bounded by the same
  liveness + grace clock the dashboard reads) which 409s naming the live run.
  It is advisory by construction: two requests inside one query round-trip
  still race, and losing that race costs a duplicate replay rather than a
  wrong answer.
  Resources: **2 Gi / 1 vCPU** (tmpfs bar/chain caches count against memory;
  512 Mi would OOM), `--timeout=120` (requests are now short), max-instances 2,
  min-instances 0.
- `POST /simulate` — same spec schema as the Job. Flow: validate (engine
  validators; the service holds a real `Config`) → coverage guard (below) →
  dedup by engine-identity key (`force` honoured) — **hit: return `200 {run_id, deduplicated: true}` — no rows; the console GETs
  the run via the dashboard, which shapes (consistent with §Who shapes)** → miss: write `submitted` +
  `running` rows (`submitted_via='sim-service'`, and the row carries
  `liveness_seconds=900` — see below) → **spawn the replay on the instance's
  single worker thread and return 202 + `run_id` immediately**; the console
  polls the existing `GET /api/v2/sweeps/{run_id}`. Persist rows + artifacts
  as cells complete; terminal row in a `finally` **with the Job's SIGTERM
  discipline copied** (handler armed, SIG_IGN around final writes) — rev 1
  waived this and the review was right that scale-down-after-timeout is
  routine, not exotic.
- **Liveness (rev-1 HIGH):** `blocking_sweep` and `is_stuck` read a new
  optional `liveness_seconds` off the row (NULL → today's Job clock), so a
  killed service instance releases the submit lock in ~25 min (900 s liveness + the existing 10-min grace), not
  3 h 10 m. Test both writers' rows against both readers.
- **Budget honesty:** the pre-flight estimates `symbols × splits ×
  MATERIALISE_SECONDS_PER_SYMBOL` (constant from rollout §2's measurement,
  asserted against it in a test) + replay seconds; a spec estimated over
  `SIM_MAX_ESTIMATE_SECONDS = 600` is refused with "use the batch path"
  (numbers in the 409 body). `run_sensitivity` counts double or is refused on
  the service path (builder: refuse; the flip flag is for the arm you finally
  choose — CLI/Job territory). Cell cap stays as a secondary bound.
- **Coverage guard, both halves (rev-1 blocker):** (a) pre-flight = one
  `list_blobs(prefix=chains/v1/<SYM>/)` per symbol (measured 0.55 s), dates
  intersected with the session calendar over the window — mid-window holes
  (corporate-action skip days are permanent-by-design) and boundary
  weekends both handled; incomplete → 409 naming symbol-days + the backfill
  remedy; (b) engine-side: the service materialises behind a
  **fetch-refusing provider wrapper** — any vendor call during materialise
  fails the run loudly (`sim_service_cold_fetch_refused`). The no-vendor
  contract is enforced, not assumed. Bars: the pre-flight does NOT probe bars
  (vendor bars are permitted — they are cheap and rate-benign relative to
  chains; stated explicitly, with the FC-095 data-key item cross-referenced).
- **Auth (rev-1 HIGH):** the proxy uses the **OIDC identity-token pattern of
  `dashboard/backend/routers/live.py`** (audience = service URL) — NOT
  `_launch_job`'s OAuth access token; the plan names the file because the two
  are easy to confuse and the repo's own docstring says so. Proxy
  `POST /api/v2/sims/run` keeps `SWEEP_SUBMIT_TOKEN` until Phase D. Service
  private: invoker = compute SA only. `@require_account_match` deliberately
  absent (no trading).
- `GET /health` returns `engine_identity` (smoke + parity verification).
- **4th deploy chain, light smoke (rev-1 HIGH):** `deploy-sim-canary` →
  `smoke-test-sim` = `/health` (identity present) + one `POST /simulate` of a

### B4 — pinning + weekly battery (PR-d)

As rev 1, plus the review's postures: pins are **revalidated at battery time**
(allowlist rules move — Phase A PR-2 proved it); an invalid/failing pin gets its
own `failed` row + loud event and the loop continues; a pin invalid 3
consecutive weeks emits a nag event. **Exit-code classes separated:** data
(backfill) failure pages via the Job policy; battery failure exits 0 with a
`battery_degraded` ERROR log watched by a 24 h-nag policy (trend staleness is
not a page — the cry-wolf principle). Battery wall-time capped
(`BATTERY_MAX_SECONDS`, refuses new sweeps past it, finishes the current one);
sized on the record: worst case (engine-change week: ~14 base + ≤20 pins,
lake-warm materialise dominated) must fit the shared 21600 s with the backfill;
the battery runs only after backfill success. `submitted_via='battery'`
(plumbing verified free-form; schema comment updated).

## Behaviour contract

- Dedup hit (service or Job, same engine identity): answer < 2 s, zero replays.
- Deploys not touching `src/**` leave every stored key valid (test).
- A killed service instance releases the submit lock in ~25 min.
- The service can never reach the options vendor: guard test with a
  hole-in-the-middle window asserts refusal, not silent fetch.
- Artifact absence never breaks results; `artifacts_complete` accounts
  non-error cells exactly.
- CLI without `--persist` writes nothing anywhere.
- N sequential sweeps in one process each get complete, sorted tallies.
