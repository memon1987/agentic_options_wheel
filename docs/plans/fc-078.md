## Design decisions

### DD-1 — "Credit-only", precisely

**Definition.** A roll is a BTC (buy-to-close the existing short call) + STO (sell-to-open the replacement). The **credit invariant** is enforced on the *limit prices actually placed*, not on marks:

```
STO_limit − BTC_limit ≥ rolling.min_net_credit_per_contract / 100   (per share; default knob 0.00 $/contract)
```

Because both legs are limit orders, actual fills can only improve on this (BTC fills at ≤ limit, STO at ≥ limit), so **a filled roll can never net a debit**. This invariant is checked at four sites: candidate screen, **immediately before BTC placement** (re-fetch the STO quote and recompute — evaluation quotes are minutes old by order time; this shrinks the staleness window to the BTC poll itself), order construction, and every fallback/retry repricing (see the fallback-path fix below). If the pre-BTC re-check fails, the roll is abandoned *before any order exists* with terminal skip `credit_gone_at_execution` — the cheap place to lose the race.

**Pricing modes.**
- **Base mode:** BTC limit = ask, STO limit = bid (conservative, near-certain fills; the credit is real at the worst case). The as-built `btc_limit_over_ask_pct` pad (limit = ask × 1.05) is deleted — a pad *above* ask makes the placed-limit worst case a debit, breaking the invariant. `stc_limit_under_bid_pct` is deleted for the mirror reason (an under-bid discount gives away credit the invariant needs).
- **Imminence mode** (DD-2 override active): BTC limit = mid + $0.05, STO limit = mid − $0.05, executed only if the invariant still holds at those limits. Rationale: bid/ask pricing double-counts the spread; when assignment is imminent, crossing half the spread to escape is worth the fill risk, and the invariant still guarantees no debit at the placed prices.

**Min-credit default = $0.00/contract.** Any non-negative roll at conservative prices executes the day it appears — this is what "transient zero-cost windows get caught the day they appear" means (FC-078 timing rationale). Marginal rolls defer *automatically* because their net is negative at conservative prices; the net improves toward expiry when the stock is still (the old call decays toward intrinsic faster than the 14-DTE replacement). The knob exists so the operator can later add a churn guard without a code change.
*Rejected:* a positive default (e.g. $5) — it would have deferred the GOOGL +$1 roll, the exact trade this FC is expedited to capture.

**Two sequential single-leg orders, BTC first.**
- *Rejected: single combo (mleg) order.* Alpaca supports multi-leg option orders, but (a) `AlpacaClient.place_option_order` is single-leg only — adding an order-class path to the shared client is new API surface on an expedited money path; (b) multi-leg requires a higher options approval level than the covered-call/CSP level this account is known to use — an unverified entitlement is a deploy-day discovery risk; (c) the two-leg exposure window (shares briefly uncovered) carries no naked-call risk. Revisit as a follow-up if leg risk ever bites.
- *BTC must be first, always.* STO-first would momentarily hold two short calls against 100 shares — a naked call Alpaca would either reject or margin. There is no acceptable STO-first sequence. (Mutation test T-9.)
- **Stranded-BTC recovery story** (BTC filled, all STO attempts failed): the shares are uncovered but *long-only* — no naked exposure. **The residual is NOT "a day's premium leak" — worst case is the full BTC debit paid in cash with nothing sold against it** (GOOGL-class: ≈ $839 BTC cash, of which ~$580 was extrinsic burned to close), followed by a re-cover that collects far less than what was closed, adversely selected: STO ladders fail on down-ticks, so the re-cover prices into a weaker tape. Recovery, stated as the composite it actually is: (1) the existing `call_roll_naked_exposure` error event fires (name kept for log continuity; message clarified to "shares uncovered — no naked position"), now **alert-wired** (DD-5); (2) no same-cycle re-entry heroics — the next `/scan` → `/run` cycle re-covers through the **entry path with all entry gates applied**: entry delta band [0.15, 0.25], `min_call_premium`, the FC-013 span gate, and the FC-029/FC-065 floor. Near a report this means the span gate can **legitimately leave the shares uncovered through the earnings event for days** — correct by doctrine (FC-013 exists to refuse exactly that new exposure), but it must be understood as a possible terminal outcome of a failed roll, not smoothed over as "self-healing"; (3) the next day's roll cycle sees no short call and skips. The alert exists so any repeated pattern gets investigated rather than absorbed.

### DD-2 — Eligibility: which short calls get evaluated

A short call is **evaluated** every cycle it exists; it is **roll-eligible** when:

1. **ITM ratio:** `stock_price / strike ≥ rolling.itm_trigger_ratio` (kept at **0.98**). OTM calls are the profit-taker's territory (`/monitor` DTE bands), not the roller's. 0.98 rather than 1.00 catches the knocking-on-the-door case where the credit window is widest.
2. **No current-DTE gate.** `rolling.max_current_dte` is **deleted**. The DTE ≤ 1 gate existed to bound *debit* escalation near expiry; under credit-only it has no protective job and is precisely what blinded the roller (a churned book's calls are 5–7 DTE on any given Friday — FC-066 cause 2). Self-timing is the credit sign, not the calendar.
   *Rejected:* raising it to 5 — excludes nothing real on a 7-DTE book but re-creates a calendar trap for any future longer-dated call.
3. **Max-rolls gate deleted.** `rolling.max_rolls_per_position` counted wheel-state rolls that were never persisted (always 0 — the gate has never bound). Its purpose was to stop debit-chasing escalation; credit-only removes the hazard, and the process terminates structurally: `validate_roll` requires strictly increasing strikes, so re-rolls are monotone and each is ≥ $0. At most one roll per position per day (one evaluation per cycle).
   *Rejected:* deriving roll counts statelessly from order history — real work, guarding against a hazard the credit invariant already removes.

**Assignment-imminence override.** When `extrinsic_per_share ≤ rolling.imminence_extrinsic_threshold` (new knob, default **$0.20**), the roller switches to imminence pricing mode (DD-1) for that position. `extrinsic = max(0, option_mid − max(0, spot − strike))`, computed from the same quotes the evaluation already fetches.
- *Threshold rationale:* early exercise of an American call is rational when remaining time value falls below the carry benefit — in practice, near-zero TV or TV below a pending dividend. $0.20 covers both the TV≈0 case and the typical quarterly dividend magnitude of this book's payers (AAPL/GOOGL/NVDA ~$0.20–0.26; AMZN pays none). At AMZN's 8/03 marks (TV ≈ $0.27 mid) the override would *not* yet fire — correct, since no credit roll exists there anyway.
- *What it overrides:* pricing aggression only. It does not relax the credit invariant (nothing does), the floor, or the span gate.
- *Best-effort, stated plainly:* the override improves the odds of escaping assignment; it does not guarantee escape. Its failure mode — mid-priced legs don't fill, position assigns — is the **pre-existing default outcome**, and assignment happens at/above the floor by construction, so the override can only add value, never subtract it. No heroic escalation beyond mid ± pad.
- *Quote quality gate:* imminence mode (and the extrinsic computation feeding it) requires a **two-sided option quote**; the stock quote must be two-sided everywhere (see the quote-guard spec in §1 — the "whichever side is positive" fallback is deleted).
- *Rejected:* having the override relax a positive min-credit — min-credit defaults to 0, there is nothing to relax; and relaxing *into debits* is out of scope by operator decision.

**Strike constraints (unchanged in direction, unified in mechanism):**
- New strike > old strike (`validate_roll`, kept).
- New strike ≥ cost-basis floor: `min_strike = max(cost_basis_per_share, current_strike + 0.01)` where `cost_basis_per_share` comes from the shared `CostBasisResolver` (FC-065 Phase 2, already in the roller), **fail-closed** — unresolved/divergent basis skips the roll with the existing `call_roll_skipped_cost_basis_unresolved`/`_divergent` events (now alert-wired, DD-5). At-floor strikes are allowed (≥, not >): floor = Alpaca `avg_entry_price`, so an at-floor call-away books ≥ $0 equity (FC-065 doctrine).
- FC-062 execute-time half: the floor must also bind at the **order site**, including the fallback-strike path — see "Fallback-path repair" below.

### DD-3 — Replacement constraints

- **Roll-out horizon — expiry-relative, not evaluation-relative (rev 2, trader BLOCKER B-1):** `replacement_expiry ≤ old_expiry + rolling.max_extension_days` (new knob, default **14** calendar days). The frame matters: roll economics extend the *existing contract's* tenor, so the horizon must be measured from the **old expiry**, not from the evaluation date. Rev 1's eval-relative `max_replacement_dte=14` would have excluded the flagship trade — GOOGL C370 8/07 rolled to 8/21 is 17–18 DTE from the 8/04 evaluation but exactly old-expiry + 14, the frame the investigation's "~14 DTE" numbers actually used. Live-verified consequence of the rev 1 drafting: first cycle would have logged GOOGL `no_credit_candidate` while C375 8/21 sat at ≈ +$248/contract credit. Two weeklies beyond the current expiry is long enough for where credits live, short enough that capital isn't parked under a month-long cap. No minimum: a same-week roll-up that nets a credit is legal (rare but harmless). Because the bound is per-position, it is passed per call as a date (`include_expiry_on_or_before`, §3), not read from config inside the shared filter.
- **Delta: entry band exempt; a generous upper rail applies.** The entry band's *lower* bound is the trap that made shallow-ITM rescue illegal (it forces far-OTM replacements exactly when the position needs near-money strikes). Deleted for rolls. An **upper** bound `rolling.max_replacement_delta` (new knob, default **0.60**) is kept: it admits every GOOGL-class target (0.35–0.48Δ) while blocking replace-ITM-with-deep-ITM churn — pinning shares under a near-certain-assignment cap for another 14 days in exchange for pennies delays the wheel's recycle for de minimis credit.
  *Rejected:* reusing the entry band (the documented trap); no bound at all (permits the pennies-for-14-days-of-cap case); 0.50 (would have excluded part of GOOGL's viable target list on 8/03 marks).
- **FC-013 span gate applies to the replacement — fail-closed.** The replacement is a *new short call*; it must not newly span a known earnings date. Mechanism: the roller calls `earnings_calendar.next_earnings_info(underlying)` (the tri-state surface) and passes `exclude_expiry_on_or_after=earnings_date` into `find_suitable_calls` — the parameter FC-013 already built. Tri-state posture:
  - `known` → candidates expiring on/after the date are span-rejected (inclusive `>=`, same semantics as the scanner);
  - `clear` → no span floor;
  - `unknown` → **the whole roll is skipped** with a structured event (`skip_reason=earnings_unknown`). A span test with no date cannot clear any candidate.
  This *replaces* the roller's old fail-open `is_earnings_within_n_days` blackout (`rolling.earnings_blackout_days` deleted): the span predicate subsumes it — any replacement sold within N days of a known report either expires before it (safe, allowed) or spans it (blocked).
  **The buyback/replacement distinction, stated cleanly:** the earnings gate exists to stop *opening* gap exposure. A defensive **buyback** (closing a short call) *reduces* exposure and is never earnings-gated — which is why `/monitor`'s early-close BTC path has no earnings check, correctly. This roller never places a buyback without a replacement plan, so the distinction manifests here as: the span gate filters **candidates**; when it empties the candidate set, the roller places **no order at all** (it does not close-and-stay-uncovered). The existing position riding to expiry is the pre-existing exposure FC-013 already accepted at sale time.
- **Premium floor (`min_call_premium`) does not apply to replacements.** The economics that matter are the *net credit*, not the standalone premium — and ITM replacements carry large premiums anyway, so the floor is inert where it isn't wrong. The liquidity check (volume == 0 and OI < 10) **is** kept.
- **Mechanism:** `find_suitable_calls` gains an optional `criteria_profile: str = 'entry'` parameter (`'entry'` = today's behavior, byte-identical; `'roll'` = no DTE check in the shared criteria — the expiry bound arrives as the `include_expiry_on_or_before` date (§3); delta ≤ `rolling.max_replacement_delta` with no lower bound; no premium floor; liquidity check kept). One filter site, no duplicated chain logic.
  *Rejected:* the roller building its own chain filter from `get_option_chain_with_analysis` — a second filter implementation is the FC-063 dict-boundary disease in new clothes.
- **Candidate selection order: maximum net credit among legal candidates (rev 2, decided).** The roller iterates the *legal* set (passed `validate_roll` + span + floor) and executes the candidate with the **largest net credit at the selected pricing mode's limits**, deterministically (ties → higher strike). At the 8/04 marks this picks GOOGL C375 8/21 (≈ +$248, +$5 strike) over C380 8/21 (≈ +$13, +$10 strike). Rationale: this is a *defensive* roll — bank the certain dollar. Choosing C380 spends $235 of certain credit to buy $500 of *contingent* strike value that only pays if the stock finishes above 380 — that is a delta bet, the roll-up-chasing instinct this FC explicitly excludes; every legal candidate already improves the strike strictly (validate_roll), so strike improvement is guaranteed and credit is the honest maximand. *Rejected:* rev 1's first-past-the-post on `return_score` order — that score (annualized premium yield × OTM preference) is entry-shaped; letting an ordering never designed for rolls silently pick the executed contract is exactly how tonight's book would have taken +$13 over +$248. *Rejected:* max strike gain subject to credit ≥ 0 — the contingent-upside preference argued against above.

### DD-4 — Cadence and wiring

- **New scheduler job `options-wheel-roll-daily`: `30 15 * * 1-5`, America/New_York**, same target URI/OIDC as the Friday job (verified live: `POST https://options-wheel-strategy-omnlacz6ia-uc.a.run.app/roll`, SA `799970961417-compute@developer.gserviceaccount.com`). 15:30 ET rationale: after the last `/monitor` (14:55 — profit-taking churn settled, the roller sees the surviving book) and after the last `/run` execute (15:15 — a freshly sold call is OTM by construction and simply skips `not_itm_enough`); 30 minutes of session left covers both legs' 120 s fill timeouts with margin; and it is the exact slot the Friday job already occupied, so roll marks stay comparable.
- **Created by:** the operator (or Claude with operator approval) via the exact `gcloud` commands in §Rollout — this repo has no Terraform; scheduler jobs are hand-created and documented here.
- **Friday job fate:** **paused** on deploy day (`gcloud scheduler jobs pause options-wheel-roll-friday`), **deleted** after the first verified week. Pause-then-delete keeps the rollback lever trivially reversible.
- **`/roll` endpoint:** the Friday-only weekday guard is **deleted**; the market-open guard and `strategy_lock` stay. `strategy_lock` already serializes `/roll` against `/monitor` and `/run`, so the two managers of the same positions cannot interleave.
- **Precedence with `/monitor` profit-taking, spec'd (rev 2 — corrected):** the two are near-disjoint by state — profit-taking fires on OTM winners (`unrealized_pl > 0` + DTE-band target), rolling on ITM positions (ratio ≥ 0.98) — and schedule order gives the profit-taker first claim (`/monitor` 14:55 before `/roll` 15:30). But schedule order alone is **not** sufficient, as rev 1 claimed: the monitor places **fire-and-forget DAY BTC limit orders with no cancel** (`deploy/cloud_run_server.py:979-1023`), so at 15:30 the roller can see a short call that still exists *with a live open buy order working against it*. If the roller then rolls it, both BTCs can fill → an unintended **long** call plus a sold replacement. **Fix — open-order guard:** before evaluating any position for rolling, the roller fetches open orders and **skips** any short call with an open order on its option symbol, terminal event `call_roll_skipped {open_order_conflict}` (test T-17). Skip, not cancel-first, deliberately: the working order belongs to the profit-taker, which has precedence by design — the roller canceling another subsystem's order inverts that precedence and races the fill anyway (a cancel can fail because it filled). Cost of skipping: one cycle's deferral at most — the DAY order dies at close and tomorrow's cycle sees a clean book. The guard also covers manual operator orders for free. No shared mutable state exists between the two paths (the `_closed_today` dedup set is `/monitor`-local and symbol-keyed; a rolled replacement is a different OCC symbol). **What must NOT change:** `/monitor` behavior is untouched by this FC.

### DD-5 — Observability

**Terminal-event contract:** every short call evaluated in a cycle emits **exactly one** terminal structured event. New/changed events (all via `log_trade_event`/`log_error_event`, flowing to BQ through the existing log sink):

| `call_roll_btc_placed/filled`, `call_roll_stc_placed/filled`, `call_roll_partial_fill` | leg lifecycle | exist, kept |

| `call_roll_naked_exposure` | BTC filled (fully or partially), all STO attempts failed — shares uncovered | exists; **alert-wired now**; message clarified per DD-1 |

| `roll_cycle_completed` | cycle summary | exists, kept |

**Terminal taxonomy, exhaustive (rev 2, execution M-7) — so T-11 ("exactly N terminal events") is writable.** Every evaluated position ends in exactly one of: `call_roll_skipped{reason}` (no order was ever placed) · `call_roll_btc_rejected` (order refused; nothing live) · `call_roll_btc_timeout_canceled` (canceled with **verified** zero fill) · `call_roll_naked_exposure` (some BTC quantity filled — including a fill discovered *after* the timeout-cancel, and the partial-fill case — and the STO ladder exhausted) · `call_roll_completed` (both legs done; on a BTC partial, `contracts` = the filled quantity actually replaced). The cancel-vs-fill disposition rule (§1) decides between the last three: **events must tell the truth about what filled**, never report `btc_unfilled`/`btc_timeout_canceled` when contracts were actually bought.

**Executed-roll notification (operator must KNOW):** a new log-match alert policy `deploy/monitoring/roll_executed_alert_policy.json` on `call_roll_completed`, delivered to the FC-030 notification channel — the established pattern. Both `jsonPayload.event_type` **and** `textPayload` clauses (Cloud Run emits plain-text severity-DEFAULT logs; a jsonPayload-only or severity-filtered policy matches nothing — the FC-030 gotcha).

**FC-066 checklist item 1:** add `call_roll_skipped_cost_basis_unresolved` and `call_roll_skipped_cost_basis_divergent` to `deploy/monitoring/cost_basis_alert_policy.json`, in both payload clauses. `call_roll_naked_exposure` goes into the new roll policy as a second condition.

Rationale: `DecisionRecorder` is scan-run-shaped — minted `run_id`s, per-symbol dedup keys, stage vocabulary, flush semantics; rolls happen outside scan runs, and forcing them into that schema is schema risk on an expedited money path. Every roll event already lands in BQ via the log sink, which is the channel FC-066's own evidence used. *Deferred, not dismissed:* file a follow-up FC on merge for a `roll` stage in decision_events (noted in §Execution when opened).

## Behavior contract (summary)

**Inputs:** live Alpaca positions (short calls + underlying stock), IEX stock quotes (`bid`/`ask`), OPRA option quotes (`bid`/`ask`/`mid_price`), `CostBasisResolver` floor, `next_earnings_info` tri-state, `rolling.*` config.

**Outputs:** at most one BTC+STO limit-order pair per ITM short call per cycle, satisfying ALL of: new strike > old; new strike ≥ floor (≥, at-floor legal); replacement expiry ≤ **old expiry + 14 days**; replacement Δ ≤ 0.60; replacement does not span a known earnings date (unknown → no order); `STO_limit − BTC_limit ≥ min_credit ≥ 0` at every placement and repricing; at most one live STO order at any instant; no position started without 600 s of cycle budget. Exactly one terminal event per evaluated position. `call_roll_completed` triggers an operator notification.

**Edge cases:** quote fetch raises or fails the quality guard → skip event, next position continues (per-position try/except in the cycle loop — one bad symbol must not kill the cycle); open order on the option symbol → `open_order_conflict` skip (DD-4); BTC unfilled at timeout → **cancel, then verify the true disposition** — filled/partial fills proceed into the ladder for the filled qty, verified-zero-fill terminates `call_roll_btc_timeout_canceled` (§1; as-built left the DAY order live and would have reported a fiction); BTC partial fill → STO qty = **BTC filled qty**, remainder canceled (as-built wrongly passed the requested qty and returned on first `partially_filled`); STO rung transitions → cancel-then-verify, at most one live STO order ever (§1); STO ladder exhausted → uncovered-shares recovery with the honest composite residual (DD-1); cycle budget insufficient to start a position → `cycle_budget_exhausted` deferral (§4); market closed → endpoint guard; `ROLLER_ENABLED=false` → cycle no-op with `rolling_disabled`; `ROLLER_DRY_RUN=true` → evaluation only.

**What must NOT change:** `/monitor` and `/run` behavior; entry-side `find_suitable_calls` results (profile default inert — pinned by test); scanner FC-013 gate; `reconcile_positions`; `allow_bigquery_cost_basis` forwarding; `require_account_match` on `/roll`.

## Risks & mitigations

- **Risk: fill-quality gap between limits and reality** (STO at bid may not fill on a moving stock). Mitigation: pre-BTC invariant re-check (shrinks staleness to the BTC poll), retry ladder with invariant-floor repricing and cancel-then-verify rung transitions (DD-1, §1). **Accepted residual, stated honestly (rev 2):** worst case is the full BTC debit paid in cash — GOOGL-class ≈ $839, ~$580 of it extrinsic — with the re-cover happening through the entry path at entry-band premiums, adversely selected on down-ticks; near a report the span gate can hold the shares uncovered through the event (DD-1 recovery, composite outcome).
- **Risk: the roller and profit-taker manage the same position on the same day.** Mitigation: schedule order + state disjointness + the **open-order guard** (DD-4 — schedule order alone is insufficient because the monitor's DAY BTC limits outlive 14:55); `strategy_lock` serializes the endpoints. Residual: none identified with the guard in place.
- **Risk: repeated daily re-rolls (churn).** Bounded: strike strictly increases per roll (monotone), each roll nets ≥ 0, Δ ≤ 0.60 rail. **Per-day bound, stated honestly (rev 2, L-9):** one roll per position per *cycle*; deploy-day step 5's manual trigger plus the scheduled run means **up to two rolls on one position in one day is possible** — each independently credit-≥ 0 and strike-increasing, so the composite is still profitable and monotone, but "one per day" is a per-cycle claim, not a hard invariant. A pathological daily-credit staircase is *profitable by construction*; the `min_net_credit_per_contract` knob exists if the operator wants friction.
- **Risk: mid-cycle kill (deadline/crash) between BTC fill and STO placement — the worst seam.** Mitigation: the cycle budget guard refuses to start any position without the full per-position worst case (600 s) of remaining budget (§4); the scheduler attempt-deadline is set explicitly to 1800 s and retries are 0 (§Rollout), so a killed request is never blindly re-entered. Residual: a Cloud Run instance crash mid-ladder still strands a BTC — the naked-exposure alert + DD-1 recovery is the backstop.
- **Risk: span gate blocks the whole candidate set silently.** Mitigation: distinct skip reasons (`earnings_unknown` vs `no_suitable_replacement` vs `no_credit_candidate`) + T-11's event contract; cost-basis skips alert-wired.
- **Risk: expedited timeline compresses review.** Non-negotiable per house rules: two adversarial reviews (fresh contexts, Fable, different personas) + confirmation pass still gate the merge. The expedite compresses idle time, not the gate.
- **Risk: 8/07 expiry passes before deploy.** Accepted: the AMZN/GOOGL 8/07 calls assign at expiry (assignment above basis is the wheel working — +$352/+$315); the roller then serves the *next* cycle. The expedite is opportunity capture, not loss prevention.
