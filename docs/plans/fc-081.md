## Context

Twice now `main` has been merged-but-undeployed for over a week with no signal: FC-031
(11 days, red build nobody saw — fixed by build-failure alerting) and FC-081 (16 days, repo
rename → trigger never fired — **a build that never starts fires no failure alert**). The
existing alert watches builds that *start*. This check watches for builds that *don't*, by
comparing what is serving against what is on `main`.

**Why a GitHub token is required.** The only authority on "what is on `main`" is GitHub.
Cloud Build's history cannot tell a quiet week from a dead trigger. The operator has agreed to
provision a fine-grained, read-only, single-repo token (`docs/plans/program-2026-08-28.md`
§Operator to-do). The check must degrade to `warn`, never `fail`, when the token is absent,
so the code can merge before the secret exists.

## Design decisions (made)

- **Where it runs:** a new check group `deploy_freshness` in
  `tools/testing/regression_monitor.py`, invoked by the existing hourly `/regression`
  schedulers on both services (`regression-hourly`, `cc-regression-hourly`). No new
  scheduler, no new endpoint. Each service checks *itself*.
- **How a service knows its own commit:** new env var `GIT_COMMIT=$COMMIT_SHA`, added to the
  `--set-env-vars` list of **all three** deploy steps in `cloudbuild.yaml` (wheel, CC,
  dashboard). These lists REPLACE the literal env set — append to them, do not add a
  separate flag. `/health` (`deploy/cloud_run_server.py`) additionally returns
  `"git_commit": <value or null>` so a human can eyeball it.
- **What it compares against:** `GET https://api.github.com/repos/memon1987/agentic_options_wheel/commits/main`
  with `Authorization: Bearer $GITHUB_TOKEN`, `Accept: application/vnd.github+json`,
  `X-GitHub-Api-Version: 2022-11-28`, timeout 10 s. Read `sha` and `commit.committer.date`.
  Repo name is a module constant `GITHUB_REPO = "memon1987/agentic_options_wheel"`, overridable
  by env `GITHUB_REPO` (the rename that caused FC-081 is exactly why this must not be buried).
- **Drift rule:** `fail` iff `head_sha != GIT_COMMIT` **and**
  `now − head_commit_date > DEPLOY_FRESHNESS_MAX_HOURS` (env, default **2**, float). A mismatch
  younger than that is a build in flight → `pass` with message "build in flight (Nm)". Match →
  `pass`. Compare full 40-char SHAs (`$COMMIT_SHA` is full-length); tolerate a short
  `GIT_COMMIT` by prefix-matching only if its length ≥ 7.
- **Status mapping (deliberate — `fail` makes `/regression` return 500 and must mean drift):**

  | Condition | status | check name / event |
  |---|---|---|
  | drift beyond window | `fail` | `deploy_freshness_drift` — emitted via `log_error_event` (sets `event_type`; `log_system_event` does not — FC-047) |
  | GitHub 404 on the repo | `fail` | `deploy_freshness_repo_unreachable` — this is the FC-081 failure mode itself (renamed/moved repo) |
  | `GITHUB_TOKEN` unset/empty | `warn` | `deploy_freshness_unconfigured` |
  | `GIT_COMMIT` unset | `warn` | `deploy_freshness_no_commit` (pre-rollout state) |
  | GitHub 401/403/5xx, timeout, malformed JSON | `warn` | `deploy_freshness_github_error` (a GitHub outage must not 500 the monitor) |
  | in flight / match | `pass` | — |

- **Alerting:** new `deploy/monitoring/deploy_freshness_alert_policy.json`, log-match on
  `deploy_freshness_drift` **or** `deploy_freshness_repo_unreachable`, matching **both**
  `jsonPayload.event_type` and `textPayload` (Cloud Run plain-text logs carry no severity —
  the duplication is required, see FC-030/FC-066 lessons). Notification channel: the FC-030
  channel (copy the channel id from `deploy/monitoring/build_failure_alert_policy.json`).
  Created via the Monitoring API by the SA (`logMatchAlertCreator` role) at rollout.
- **Rate/coupling:** ≤ 12 GitHub calls/day across both services. No caching.
- **Not a Cloud Build heartbeat, not a GitHub Action:** both were considered; neither sees a
  push that produced no build without GitHub read access anyway, and a GitHub-side check would
  need GCP credentials in GitHub — a worse secret to hold.

## Behavior contract

- Existing check groups, their names, statuses and the 500-on-fail semantics: unchanged.
- With no secret provisioned the only visible change is one `warn` row
  (`deploy_freshness_unconfigured`) in every `/regression` report — acceptable, and the
  operator to-do removes it.
- Never `fail` on a transient GitHub error; never `pass` silently when unconfigured.
- Must NOT change: `BQ_DATASET`/profile derivation (FC-082), `check_performance_baseline`
  (FC-085 owns it), any scheduler.

## Tests

`tests/test_regression_monitor_freshness.py` — stub the GitHub getter and `os.environ`
(`monkeypatch`), no network. One test per table row plus:

1. match → `pass`.
2. mismatch, HEAD committed 3 h ago, default window → `fail`, name `deploy_freshness_drift`,
   `log_error_event` called with `event_type="deploy_freshness_drift"`. *(The core regression.)*
3. mismatch, HEAD 20 min ago → `pass`, message contains "in flight". *(Regression: alert
   noise on every merge.)*
4. mismatch, HEAD 90 min ago, `DEPLOY_FRESHNESS_MAX_HOURS=1` → `fail` (env override honored).
5. 404 → `fail`, `deploy_freshness_repo_unreachable`.
6. 401, 503, timeout, non-JSON body → `warn`, `deploy_freshness_github_error` (parametrized).
7. no token → `warn`, `deploy_freshness_unconfigured`; no `GIT_COMMIT` → `warn`,
   `deploy_freshness_no_commit`. Order: `GIT_COMMIT` missing is reported before token missing.
8. `run_all_checks` report contains key `deploy_freshness` (extend the schema/contract test
   that already enumerates groups, if one exists in `tests/test_regression_monitor_schema.py`;
   otherwise add it there).
9. `GITHUB_REPO` env override is used in the request URL.

Mutation check: flip `>` to `>=`/invert the window comparison → tests 2/3 fail; drop the
404 branch → test 5 fails.

Also: `tests/test_cloudbuild_contract.py` (from FC-084) fixture for `--set-env-vars` must be
updated to include `GIT_COMMIT=$COMMIT_SHA` — that is the one intended change to the frozen
env sets.

## Rollout (ordered)

1. FC-084 merges first; rebase this branch.
2. Merge this PR. The merging build sets `GIT_COMMIT` on all three services. First hourly
   `/regression` shows `deploy_freshness_unconfigured` (warn) until step 3.
3. **Operator:** create the token + secret + bindings + service updates — exact commands in
   `docs/plans/program-2026-08-28.md` §Operator to-do. (`gcloud run services update
   --update-secrets` creates a new revision and shifts traffic immediately; secret-backed env
   vars survive later `--set-env-vars` deploys, as `ALPACA_*`/`FINNHUB_API_KEY` do today.)
4. Verify: `POST /regression` on both services → `deploy_freshness` → `pass`, details show
   matching SHAs. Then a negative drill: temporarily set `DEPLOY_FRESHNESS_MAX_HOURS=0` on
   the wheel service, push a docs commit, run `/regression` within the build window → `fail`,
   alert email arrives; restore the env var. Record both in §Execution.
5. Create the alert policy (SA), version the JSON, note the policy id in §Execution.
6. Bookkeeping: FC-081 entry → Closed; `docs/CLAUDE.md` detective table updated (in the PR).

## Open questions

- **Non-blocking:** should the dashboard service also run `/regression`? Not today — it has
  no scheduler for it and its staleness is lower-stakes. The env var lands anyway so it can be
  added later without a deploy change.
- **Non-blocking:** 2 h window. A build takes 10–12 min; 2 h absorbs a Cloud Build queue or a
  retried deploy without paging. Revisit if it ever alerts on an in-flight build.
