## Context

While shipping FC-018 (the wheel-centric dashboard rebuild) the user noticed two compound accounting gaps that made the dashboard's option-sourced P&L disagree with actual account growth.

**Symptom:** A paper account that funded $100k and grew to $120,080 (real change: +$20,080) had a "Net P&L" headline tile reading **$26,358** — sum of `realized_pnl` across closed option events. Per-symbol totals summed to a similar inflated number.

**Root cause #1:** the `wheel_cycles_from_activities` view computed `capital_gain` as `(call_strike − put_strike) × 100`. This 1:1 cycle pairing breaks when the same underlying has multiple put assignments before any are called away (overlapping share lots). AMD held a 200-share concurrent lot from 2026-01-31 to 2026-04-17 — the view computed `+$1,000` cap gain for that period while the real OPTRD net cash flow was **-$24,250**.

**Root cause #2:** `JNLC` (cash deposits/withdrawals) and `OPTRD` (share-side cash flow on assignment / called-away) were never ingested. `activities_ingestor.py` only pulled `FILL`, `OPASN`, `OPEXP`. So:
- The headline "Total Return" had to fall back to a hardcoded `BASELINE_DEPOSITS=$100,000` env var because there was no other source for the starting capital.
- The per-symbol scorecard couldn't show the share-side cash flow, which is what actually distinguishes a winning wheel from a losing one (e.g., AMD made $6,931 in option premium but lost $24,250 on share movements — the dashboard hid the loss entirely).

The user pushed for full reconciliation rather than the env-var workaround: "we need a full reconciliation. proceed through it."

## Goals

- Per-symbol scorecard reconciles to actual account growth: **sum of per-symbol Total P&L ≈ NLV − net deposits** (within fees + unrealized + Alpaca-side anomalies).
- Headline `Total Return` tile is sourced from a live JNLC sum, not an env var. The fallback path is documented and clearly labeled in the response.
- Share-side P&L (the OPTRD cash flow on assignment / called-away) is surfaced as a first-class column on the scorecard and folded into a `total_realized_pnl` that's the headline reconciliation number.
- `wheel_cycles_from_activities.capital_gain` uses real OPTRD cash flow within each cycle window, falling back to the strike-derived approximation only if OPTRD isn't ingested yet (so the view doesn't break during backfill).

## Non-goals

- **FIFO pairing of overlapping share lots.** AMD's 200-share concurrent lot still produces inflated `capital_gain` for one of the two assignment-cycle rows and treats the other as still open. Per-symbol totals are unaffected (they sum OPTRDs once), but the per-cycle drilldown breaks down. Filed as **FC-020** for a separate stateful-walk view rewrite.
- Investigating the Alpaca-side data inconsistency where AMD's OPTRDs net to +100 shares but `/v2/positions` reports 0. Confirmed via direct Alpaca API as a paper-account anomaly we can't fix from this codebase. Documented; surfaces as ~$1,600 unexplained gap on this account.
- Backfilling FEE rows. Total fees across the account's lifetime are -$24, well within accounting noise.
- Rewriting the structlog → Cloud Logging sink. FC-012 explicitly left it alone; FC-019 doesn't touch it either.
- Backfilling the legacy `options_wheel.trades` (v1) table. It's inert post-FC-012 cutover.

## Proposed approach

Three-layer change: ingest layer, view layer, dashboard layer.

### 1. Ingest layer — `src/data/activities_ingestor.py`

- Extend `ACTIVITY_TYPES` from `"FILL,OPASN,OPEXP"` to `"FILL,OPASN,OPEXP,OPTRD,JNLC"`.
- Add a `net_amount FLOAT` column to the BQ schema (for OPTRD/JNLC; nullable for the option types).
- Update `_normalize` to handle the OPTRD shape (ticker symbol, no OCC parse) and JNLC shape (no symbol, no qty). Add a fallback that synthesizes a midnight-UTC `transaction_time` from `date` for activities that have neither `transaction_time` nor `created_at`.
- Update `_read_cursor` to include the new types in its MIN-of-maxes computation. JNLC/OPTRD use `activity_date` since they don't have `transaction_time`.
- Add `run_once(after_override=...)` so a one-off backfill of newly-added types can bypass the cursor (the cursor would otherwise block a backfill, since FILL/OPASN/OPEXP rows already exist past the historical window of the new types).
- Add an `?after=YYYY-MM-DD` query parameter to `POST /ingest-activities` that wires through to `after_override`.

### 2. View layer — `docs/bigquery/fc012_views.sql` + `fc018_views.sql`

**`wheel_cycles_from_activities` (in `fc012_views.sql`):** add a new `cycle_share_cash` CTE that sums `net_amount` from `OPTRD` events within each cycle window. Replace the `(call_strike − put_strike) × 100` formula with `COALESCE(cycle_share_cash.cycle_optrd_net, <old formula>)`. The `COALESCE` lets the view continue working during the backfill window when OPTRD rows haven't landed yet.

**`fc018_per_symbol_scorecard` (in `fc018_views.sql`):** add a `share_side_agg` CTE that sums `OPTRD.net_amount` per underlying. Surface two new columns:
- `share_side_pnl` — sum of OPTRD net per symbol (the truth for share-side cash flow)
- `total_realized_pnl` — `realized_pnl + share_side_pnl` (the reconciliation number)

Default sort changes from `total_premium DESC` to `total_realized_pnl DESC` since that's the more honest ranking.

### 3. Dashboard layer

**Backend (`dashboard/backend/services/bigquery.py`):**
- Rewrite `get_account_baseline` to query `SUM(net_amount) WHERE activity_type='JNLC'` from `trades_from_activities`. Fall back to `BASELINE_DEPOSITS` env var only if no JNLC rows are ingested yet — and label the source string accordingly so operators can spot when they're seeing the fallback.
- `get_per_symbol_scorecard` includes the new view columns.
- `get_wheel_cycles_for_symbol` returns `optrd_event_count` so the cycle table can show how many share-side events were summed.

**Frontend (`dashboard/frontend/src/`):**
- `types/v2.ts` — `ScorecardRow` adds `share_side_pnl` + `total_realized_pnl`. `AccountBaseline` adds `jnlc_event_count`.
- `components/v2/SymbolScorecard.tsx` — rename "Net P&L" column header to "Option P&L", add "Share P&L" + "Total P&L" columns. Default sort by `total_realized_pnl`. Footer hint explains all four columns.

## Reuse

- The `ALTER TABLE ADD COLUMN IF NOT EXISTS` migration pattern from earlier BQ schema changes (no Liquibase / Alembic in this repo).
- The same `row_ids` idempotent insert pattern that `activities_ingestor.run_once` already uses — JNLC/OPTRD rows dedupe on `activity_id` like everything else.
- The existing `parse_option_symbol` utility for the FILL path; OPTRD/JNLC paths skip it entirely.

## Risks & mitigations

- **Risk:** the BQ schema migration could fail mid-flight, leaving `trades_from_activities` in an inconsistent state.
  - *Mitigation:* `ALTER TABLE ADD COLUMN IF NOT EXISTS` is idempotent. Manual run before code deploy so any failure is caught early. Verified via `bq show` after the ALTER.

- **Risk:** the cursor logic in `_read_cursor` could mis-identify the backfill window once new activity types are in the table, causing future scheduled runs to skip rows.
  - *Mitigation:* the MIN-of-maxes computation skips NULL values; once at least one row of each type exists, the cursor advances correctly. Tested with the `test_synthesizes_timestamp_from_date_only` and the existing pagination tests.

- **Risk:** the view rewrite could break the existing dashboard if `share_side_pnl` is null instead of zero.
  - *Mitigation:* `COALESCE(s.share_side_pnl, 0)` in the SELECT defaults to zero. The frontend additionally treats `null` as `—` rather than crashing. Verified by querying the views immediately after `bq query` re-apply, before backfill ran.

- **Risk:** the user may notice the scorecard total doesn't match account growth exactly (the AMD anomaly).
  - *Mitigation:* document the gap clearly. The reconciliation summary in the PR description shows the math; FC-020 captures the cycle-pairing follow-up.

- **Risk:** the `BASELINE_DEPOSITS` env-var fallback could silently mask a broken JNLC ingest.
  - *Mitigation:* the `account-baseline` endpoint returns `source: "BQ:..."` vs `source: "env:BASELINE_DEPOSITS fallback (no JNLC rows ingested yet)"` — operators can grep for the fallback message. The frontend doesn't surface this differentiation in v1; could add later if needed.

## Rollout

1. **Schema migration first.** `bq query --use_legacy_sql=false 'ALTER TABLE ... ADD COLUMN IF NOT EXISTS net_amount FLOAT64'` against the production dataset. Verified via `bq show` that the column exists.
2. **Code deploy.** Cloud Build auto-runs on merge of the PR.
3. **View re-apply.** `bq query --use_legacy_sql=false < docs/bigquery/fc012_views.sql` and same for `fc018_views.sql`. Views are `CREATE OR REPLACE` so safe to re-run; no downtime.
4. **Backfill.** `POST /ingest-activities?after=2025-10-01` — pulls the historical JNLC + OPTRD events. Idempotent on existing FILL/OPASN/OPEXP rows via the `activity_id` dedup check.
5. **Verify.** Query `fc018_per_symbol_scorecard` to confirm `share_side_pnl` is populated. Query `account-baseline` endpoint to confirm `source: BQ:...`. Refresh the dashboard.

**Rollback:** revert the PR. Views can be re-applied from the previous-commit version. The new BQ column stays — adding a NULLABLE column is non-destructive.

No corporate actions in the account's lifetime.
- ~~How to handle accounts where `BASELINE_DEPOSITS` was set explicitly to override JNLC?~~ **JNLC sum wins**; env var is the fallback only. The `source` field labels which is in effect.
- ~~Should `total_realized_pnl` include unrealized?~~ **No.** Unrealized lives on the open positions; the reconciliation goal is to compare realized accounting to the bank-statement number, with unrealized + fees as small residual terms. Mixing them into one column would re-introduce the fuzzy "Net P&L" labeling FC-018 already worked to clean up.
