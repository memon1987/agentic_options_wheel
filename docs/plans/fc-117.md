## Context

`main.py --command battery` (FC-096 Phase B B4) re-measures a **standing set** every Saturday after the data backfill: the base config, one sweep per live wheel symbol, trailing year (`DEFAULT_LOOKBACK_DAYS`), 90-day holdout (`BATTERY_HOLDOUT_DAYS`), re-anchored to `last_settled_day()`, `submitted_via='battery'`, plus every active pin. Phase C (`docs/plans/fc-096-c.md`, Amendment 1) gave the replay profile awareness and then **left the battery wheel-only by choice** — `battery_standing_specs` states `strategy: wheel` on every item precisely so that "flipping the set is a one-line change per item with nothing implicit left" (`main.py:810-816`).

The covered-call profile therefore has no weekly trend series: its `scenario_runs` rows exist only when an operator submits a CC sim by hand from the console (first one ever: `a5c9c5626b4148eb`, 2026-09-09). The operator's 2026-09-11 decision — *wheel and covered call should have the same underlying mechanisms* — makes the CC standing set the battery's next item.

Measured facts this plan is sized on (all from the record; re-read 2026-09-11 for rev 2 from the Job's logs and `scenario_sweeps`, read-only):

- **First composed Saturday, 2026-09-05** (`docs/plans/fc-096-b.md:898`): backfill **211 s**, handed in as `elapsed_seconds`; the logged battery `wall_seconds` = **569.4 s INCLUDES it** — `started = time.monotonic() − elapsed_seconds` (`main.py:1117`) and `wall = monotonic() − started` (`main.py:1311`). So the wheel half's own execution was **≈ 358 s for 14 items ≈ 25.6 s/item**. Per-item `sweep_completed` events: `wall_seconds` 21.3–27.1 s, `materialise_seconds` 20.4–25.5 s, `replay_seconds` 0.46–0.55 s, `provider_fetches` = 1 on twelve items, 9 on two (AMD, MSFT), **73 on PFE** (see the vendor path below). 0 failed, 0 skipped. Wall cap `BATTERY_MAX_SECONDS = 14400`; Job `--task-timeout=21600`.
- **All 14 replayed, and that is the steady state, not an engine-change artefact.** Rev 1 (and `fc-096-b.md:898`) attributed the absence of dedup hits to the two engine-identity moves that week. The structural cause is simpler: `battery_standing_specs` re-anchors `end = last_settled_day(today)` (`main.py:827`), so `window_end` — and therefore the sweep key — moves every Saturday; `docs/bigquery/scenario_runs.md:662-664` says exactly this ("`window_end` MOVES week to week"). **There is no dedup-hit week for a standing item, wheel or CC.** Dedup applies only to a console resubmission of a spec whose `end` happens to equal the battery's (see OQ-3).
- **Materialise is the cost; "~4 s per CC cell" in the FC entry is a local-hit materialisation of one split, not a replay.** Warm-lake materialise is **~20–25 s per symbol** here (25–50 s in the Phase B record, `fc-096-b.md:25`); replay is ~0.5 s per symbol-year. Per split on 09-05: the fit split (trailing year) was a lake pull at 17–21 s; the holdout split (its last 90 days, already materialised locally by the fit split) was a local hit at 3.7–8.4 s. The reliability review's read of the sim-service logs for the only CC sim so far (`a5c9c5626b4148eb`, console, 2026-09-09) is materialise 24.65 s cold, replay 1.96 s for 2 cells, `lake_hits` 251 — consistent, **not re-verified for rev 2** (the sim-service log query returned nothing under the filter tried; the number is not load-bearing, the bounds below are).
- **The CC replay's reach** is `call_target_dte + rolling.max_extension_days` capped at `MAX_SWEEPABLE_DTE` = **21** (`runner.roll_horizon_reach`, 14 + 14 → 21), so it asks the chain store for `universe_dte = 22`; the lake stores 22, so a lake object covers it on the DTE axis. The wheel replay asks for **8** (put reach 7 + buffer). `ChainStore._covers` (`src/backtesting/data/chain_store.py:1565-1596`) checks three axes: model, `universe_dte` (stored ≥ requested), and the strike window (stored ⊇ requested ± tolerance); the strike anchors are the window's max/min close (`src/backtesting/engine/simulator.py:612-650`), the same for both profiles over the same window.
- **The vendor path is live today (PFE, 09-05):** the wheel's PFE item logged 36 × `chain_lake_merge_refused reason=dte_mismatch` (existing lake object `[15.25, 35.71]@22` vs the wheel's rebuild `[17.75, 36.28]@8`) plus `chain_lake_overwrite_skipped`, `lake_rejected = 35`, `provider_fetches = 73`. Mechanism, verified against `chain_store.py:652-690` (merge requires equal `universe_dte`; only the strike axis may widen) and `:1475-1480` (a `_covers` miss on a lake pull counts `lake_rejected` and rebuilds): the strike window moved above the stored one → lake object rejected → vendor rebuild at reach 8 → merge refused (8 ≠ 22) → upload skipped (narrower) → **the local file for that day is now `@8`**. The wheel pays this every week until something builds at 22 over the wider strikes. The CC item of that symbol is what does: local file `@8` fails the DTE axis → lake pull → strike reject → vendor rebuild at reach 22 (≈ 3× the contracts of a reach-8 build) → merge **accepted** → uploaded. Per-symbol worst case for a CC item is therefore **a lake pull + a 22-reach vendor build**, and the CC half **widens the lake** for PFE-class days on its first run — a good side effect: `lake_puts > 0` on a CC sweep row is not a defect, and the wheel's PFE `provider_fetches` should drop to 1 the following Saturday.

**Two things a reader of the CC series must know (stated here, in the DD-3 SQL comment, and in `scenario_runs.md`):**

- **Rolling re-seed.** Each Saturday `start` and `holdout_start` slide with `end`; each split is its own `Simulator` (`runner._simulator`, `src/backtesting/scenarios/runner.py:1044-1055`, called per split from `_replay_one`), and `_seed_synthetic_lots` seeds the lot at the window's first traded close (`src/backtesting/engine/simulator.py:1150-1185`). So a CC point's capital base — the lot's basis and its time-weighted value — **re-bases week over week for a reason that has nothing to do with the strategy**: the seeding close moved. The wheel has no analogue (fixed `$100k` starting cash). Week-over-week deltas in a CC series are therefore partly seeding noise; the honest comparison is the same `window_end` across symbols, or a long series read for drift, not adjacent points.
- **Two different row-level numbers.** The CC row's `annualized_return` is the **equity** return — lot price move plus net premium (`SYNTHETIC_LOT_BIAS`, `src/backtesting/scenarios/report.py:242-270`; `docs/BACKTEST_ENGINE.md:923-927`). The CC **headline**, `premium_yield_on_lot` (annualized net premium over the time-weighted lot value), is **artifact-only**: `persist.py` has no such column (`docs/bigquery/scenario_runs.md:723-730`). The documented trend query therefore trends the equity return; the headline needs the cell artifact. Promoting it to a row column is **FC-118**, deliberately out of scope here (no `scenario_runs` schema change in FC-117).

**What the CC standing set is, and is not.** It is a **universe hypothesis** — "if the covered-call programme held 100 shares of each of these 14 names, what would writing calls against them have yielded" — over the wheel's live universe (DD-1). It is **not** the live CC book: the CC service's holdings today are a subset (GOOGL and UNH), and they change with assignment. The live-book view is a **query filter over the same rows**, never a second standing set: `AND r.symbol IN ('GOOGL', 'UNH')` on the DD-3 query, maintained by the reader. The hazard runs the other way: a CC holding **outside** the 14 (a name the CC account came to hold that the wheel does not trade) has **no series and no lake chains** — the backfill universe is `config.stock_symbols + candidate_symbols` of the wheel profile (DD-4). That symbol would have to be added to the wheel's list or `stocks.candidates` for the lake to hold it; the battery does not discover holdings.

## Goals

- Every Saturday the battery measures **two** standing sets: the wheel's (unchanged) and the covered-call profile's (new), one spec per live symbol each, same window shape, same dedup, same store, same `submitted_via`.
- The wheel's standing specs, sweep keys, rows, labels and log fields are **byte-for-byte unchanged**.
- The trend query and the observability events can tell the two series apart.
- The CC universe is guaranteed, by construction and by test, to be inside the backfill's lake universe.

## Non-goals

- **No dashboard battery/trend view.** There is none today (`dashboard/backend/services/sweeps.py` has no `submitted_via='battery'` query; the frontend's only battery-aware code is `PinButton.tsx` and the pins list hook in `useSweeps.ts`). The FC-117 entry's "the console's battery view segments by `strategy`" has nothing to attach to yet; a trend view is its own FC (or FC-106's layout revision). This plan changes the **documented trend SQL** only.
- No schema change: `strategy` stays in `spec_json` (Phase C decision, `docs/bigquery/scenario_runs.md` §`strategy`). No `strategy` column.
- No change to pins, the pin API, the nag, the wall cap value, the exit classes, or the `BACKFILL_THEN_BATTERY` composition.
- No `stocks.candidates` in either standing set (today's wheel set is the live universe only; the CC set mirrors it).
- No CC-specific window shape, holdout, or `starting_cash` (see OQ-3).
- No caching of the CC profile `Config` across items (see Found-while-planning #4).

## Design decisions (made — do not relitigate in the build)

### DD-1 — the CC symbol list is the wheel's live universe, `config.stock_symbols` of the process profile

**The FC entry's premise is wrong and this plan corrects it.** `config/covered_call.yaml` has **no `stocks:` section at all** — by design: the CC service's live universe is holdings-derived (`src/utils/config.py:152-160` requires `stocks` only when `strategy_id == 'wheel'`; `Config.stock_symbols` returns `[]` on the CC profile, `config.py:669-677`). A CC sweep already iterates the wheel's live universe (`main.py:1930-1933`: "the covered-call profile has no `stocks:` section at all … so a CC sweep iterates the wheel's live universe"), and so does every console CC sim.

So: the CC standing set = one spec per symbol in `config.stock_symbols` of the **process** config (the wheel profile the `data-backfill` Job runs under — it passes no `--config` and no `STRATEGY_CONFIG`, `main.py:96` → `Config(DEFAULT_CONFIG_FILE)`), with `strategy: covered_call`. Today that is the same 14 symbols as the wheel set.

Why this and not the alternatives:

- **Rejected: add `stocks.symbols` to `config/covered_call.yaml`.** It is a config-schema change on the **live** CC trading service: `stock_symbols` would stop returning `[]` there, and its read-only callers (`/config`, `/backtest/screen`, `get_market_overview`) would start reporting a universe the service does not trade. It also creates a second symbol list that the backfill (DD-4) does not read, so a symbol added there and not to the wheel's list would produce a `failed` battery row every week until someone widened the lake by hand.
- **Rejected: a new `battery:` config block with its own list.** A third universe list, same lake-gap failure mode, and a standing set that no longer says "the live universe, measured weekly".
- **Rejected: holdings-derived (the CC service's actual book).** The battery has no account access and should not; and a standing set that changes with what happens to be held is not a trend series.

Consequence for a symbol in both sets (today: all 14): **two specs, two keys.** `identity.canonical_spec` writes `strategy` into the canonical form for any non-wheel value and omits it for the wheel (`identity.py:400-417`), so `sweep_key(cc_spec) != sweep_key(wheel_spec)` for the same symbol and window. Second belt, already in place: `base_config_hash` differs between the two profiles by construction (`scenario_runs.md` §`strategy`), so even a caller that dropped `strategy` could not dedup a CC run into a wheel run.

### DD-2 — same Saturday execution; order = wheel standing → CC standing → pins

**Same execution.** Budget arithmetic against the record (rev 2 — every number from §Context's 09-05 read; `wall_seconds` is the execution-wide figure that includes the backfill):

| Component | Measured / bound | Notes |
| --- | --- | --- |
| Backfill (handed in as `elapsed_seconds`) | 211 s (2026-09-05) | up to ~66 min on a widening week (`main.py` B4 header) |
| Wheel standing, 14 items | **≈ 358 s** (= 569.4 − 211) | ≈ 25.6 s/item: fit split lake pull 17–21 s + holdout local hit 3.7–8.4 s + replay ~0.5 s. **Every Saturday** — there is no dedup-hit week (the window re-anchors, §Context). PFE-class vendor days add ~4 s at reach 8 (26.3 s vs ~22 s). |
| **CC standing, 14 items, best case** | **≈ 3–4 min** (≈ 12–18 s/item) | both splits local-hit the wheel item's `@22` lake-pulled files (`_covers`: 22 ≥ 22 on DTE, same strike anchors over the same window): 2 × (4–8 s) materialise + 2 × ~1 s replay |
| **CC standing, 14 items, worst case** | **≈ 12 min** (≤ ~50 s/item) | PFE-class symbol: the wheel item left a local `@8` rebuild → DTE miss → lake pull (17–21 s) → strike reject → **22-reach vendor build (≈ 3× a reach-8 build's contracts; bounded at ~20 s)** → merge accepted + upload → holdout local hit (4–8 s) → replay ~2 s. On 09-05 one symbol of 14 was on this path; bounding all 14 there is the ceiling. |
| Total, no pins | ≈ 211 + 358 + 720 = **≈ 21.5 min** worst case | against a 240 min cap; the 20-pin worst case (+16 min per pin) is unchanged by this plan and was never sized to fit in full — the cap bounds it and the skip list names it |

**Measuring the CC half's actual cost on the first Saturday** (there is no dedup-hit week to isolate it, so it is read off the rows). Rev 3 said to difference `sweep_completed` timestamps by item label — **that recipe does not work**: `sweep_completed` (`runner.py:1044-1055`) carries no label, no `run_id`, no symbol and no strategy, so the operator cannot tell a CC item's event from a wheel item's. Read it from `scenario_sweeps`, which stores both timestamps and the spec:

```sql
-- the CC half's cost, per strategy, for one execution's window
SELECT IFNULL(JSON_VALUE(s.spec_json,'$.strategy'),'wheel') AS strategy,
       COUNT(*) AS items,
       MIN(s.started_at) AS first_start,
       MAX(s.finished_at) AS last_finish,
       TIMESTAMP_DIFF(MAX(s.finished_at), MIN(s.started_at), SECOND) AS span_seconds,
       SUM(TIMESTAMP_DIFF(s.finished_at, s.started_at, SECOND)) AS item_seconds
FROM `gen-lang-client-0607444019.options_wheel.scenario_sweeps` s
WHERE s.submitted_via = 'battery' AND s.window_end = DATE '<the run's window_end>'
GROUP BY strategy ORDER BY first_start;
```

`span_seconds` on the `covered_call` group is the half's wall cost; `item_seconds` is the sum of its items (equal to the span while the battery is serial, which it is). Cross-check that the two groups' spans plus the pins account for `wall_seconds − elapsed_seconds`. Record both in §Execution against this table.

A separate execution (a second scheduler + Job) was **rejected**: it would double the lake-freshness coupling the battery exists for (measured minutes after the backfill), add a scheduler, a policy filter, and a second `elapsed_seconds` story, to buy room the cap does not need.

**Ordering: wheel standing → CC standing → pins. Closed (OQ-2, program owner 2026-09-11).** Rationale:

- Under a cap hit, later items are the ones skipped. The wheel series is the project's baseline and must be the last thing sacrificed; the CC series is new; pins are experiments the cap was designed around (`BATTERY_MAX_PIN_CELLS` exists because pins are the variable-size items) and every skip is named in `skipped_labels`.
- **A complete wheel series plus a missing CC series is a better partial than two half series.** A cap hit mid-execution under wheel→CC ordering leaves the wheel's 14 points intact and the CC series absent for the week — one series missing one point. Interleaving would leave both series with holes for the same week, and a hole in a rolling series is the defect the series exists to avoid.
- Pins keep their existing position — *after the standing set* — which is the documented contract (`docs/CLAUDE.md` "a standing set … plus every ACTIVE pin").
- **Rejected: interleave by symbol (wheel:X, cc:X, wheel:Y, …).** Cache locality is a wash: the local chain cache is a filesystem directory that lives for the whole execution — the CC item for X finds the wheel item's files whether it runs second or fifteenth. Interleaving would put CC cells ahead of wheel cells under a cap hit for no gain.
- **Rejected: pins before the CC standing set.** Symmetry is the operator's stated principle; a standing set that is skipped in favour of experiments is not standing.

### DD-3 — `submitted_via='battery'` unchanged; segmentation reads `spec_json.strategy`

`BATTERY_SUBMITTED_VIA` stays `'battery'` on every row of both sets. Segmenting on `submitted_via` (e.g. `'battery-cc'`) was **rejected**: it would make every existing consumer of `submitted_via='battery'` (the alert policy's triage query, the docs' trend query, `scenario_runs.md`'s column contract) silently wheel-only, and it would duplicate a fact the row already carries in `spec_json`.

The trend query in `docs/bigquery/scenario_runs.md` §Useful queries becomes:

```sql
-- the weekly trend series, per strategy, excluding smoke rows and ad-hoc runs.
-- `strategy` lives in spec_json (no column — FC-096 Phase C); absent means
-- wheel, so IFNULL, never a bare equality. `window_end` MOVES every week for
-- both strategies (the standing set re-anchors to the last settled day).
-- Never compare annualized_return ACROSS strategies: a wheel ratio is over
-- starting_cash; a covered-call ratio is the EQUITY return of a synthetic
-- 100-share lot (price move + net premium). The covered-call HEADLINE,
-- premium_yield_on_lot, is artifact-only (no column; FC-118 would add one).
-- Covered-call points also RE-BASE week to week: each Saturday's window
-- seeds its lot at that window's first traded close, so adjacent points
-- differ partly for a non-strategy reason. The wheel has no analogue.
-- engine_identity: a step in one series that coincides with a change here is
-- an engine change, not a market one (the covered-call profile rolls at 1.00
-- and is the more roll-sensitive series — FC-116 lands ahead of FC-117).
SELECT
  IFNULL(JSON_VALUE(s.spec_json, '$.strategy'), 'wheel') AS strategy,
  r.symbol, s.window_end, r.split, r.measured, r.verdict,
  r.annualized_return, s.engine_identity
FROM `gen-lang-client-0607444019.options_wheel.scenario_sweeps` s
JOIN `gen-lang-client-0607444019.options_wheel.scenario_runs` r
  USING (run_id)
WHERE s.submitted_via = 'battery' AND s.status = 'done'
  -- AND r.symbol IN ('GOOGL', 'UNH')   -- the live covered-call BOOK is a
  --                                    -- filter over these rows, not a set
ORDER BY strategy, s.window_end DESC, r.symbol, r.split;
```

`r.measured` is selected, not filtered, so an `insufficient` symbol shows as a row with `measured = false` rather than vanishing from the series (a reader who wants only measured points adds `AND r.measured`). `s.engine_identity` is a `scenario_sweeps` column (`src/backtesting/scenarios/persist.py:269`).

**Pins may already carry either strategy.** `validate_spec` accepts `strategy` (`sweeps.py:552-560`), the pin store keeps the normalised spec verbatim, and `battery_pin_spec` re-anchors the window without touching `strategy`; `run_sweep_cmd` then resolves the profile from it. Nothing changes for pins; the plan states it so nobody adds a "CC pin" feature that exists.

### DD-4 — the backfill already covers the CC universe; add a structural guard

`backfill_symbols` (`main.py:509-533`) defaults to `[*config.stock_symbols, *config.candidate_symbols]` of the **same process config** the CC standing set is now drawn from. Coverage is therefore by construction, not by coincidence. Verified read-only against the live lake on 2026-09-11: `gs://options-wheel-chain-lake/chains/v1/` holds exactly the 14 prefixes `AAPL AMD AMZN F GOOGL IWM KMI MSFT NVDA PFE QQQ SPY UNH VZ` = `config/settings.yaml` `stocks.symbols`; `stocks.candidates` is `[]`.

No widening is needed and **the Job keeps reading the wheel profile**. The guard: a test that `set(sym for spec in cc_specs for sym in spec['symbols']) ⊆ set(backfill_symbols(args, config))` with no CLI/env override, so a future divergence between the two lists (someone taking the rejected DD-1 alternative) fails a test rather than a Saturday.

### DD-5 — wheel-neutrality is a byte contract

`battery_standing_specs(config, *, today=None)` keeps its name, signature and output **byte-identical** (a frozen-literal test enforces it, §Tests). The wheel labels stay `standing:<SYMBOL>`; wheel rows, keys, and the wheel's log fields (`standing=`, `measured=`) keep their meaning. The CC set is a **new** builder and a **new** item label; `run_battery_cmd` composes them.

### DD-6 — observability: per-strategy counts, existing events, no new event types

- `battery_started` gains `standing_wheel`, `standing_cc` (ints); `standing` stays the total (no consumer parses it, but its meaning "items in the standing set" survives).
- `battery_completed` and `battery_degraded` gain `measured_wheel`, `measured_cc` — counts over **everything measured** (standing + pins), attributed by each item's own strategy. `measured` stays the total.
- The console print lines become `Weekly battery: 14 wheel + 14 cc standing + P pinned spec(s), wall cap …` and `battery: 28 measured (14 wheel + 14 cc), 0 failed, 0 skipped in 640.2s`. The `battery_degraded` message string embeds `summary` and so carries the split for free.
- CC standing labels: `standing:cc:<SYMBOL>` (wheel stays `standing:<SYMBOL>`; `pin:<pin_id>` unchanged). The alert policy's content string, which names the label forms, is updated (§Critical files).
- `reason` derivation (`terminated` / `pin_too_large` / `wall_cap` / `items_failed`) is unchanged.
- **`measured_*` count COMPLETED SUBMISSIONS, not measured cells.** `measured += 1` fires on `rc == 0` (`main.py:1299`), whatever the verdicts inside: a run whose two cells are both `insufficient` is one measured item. `measured_cc = 14` on a Saturday where several CC symbols are unmeasured (F/PFE/KMI/VZ as `low_activity`, §Rollout step 2 — `insufficient` means something else on a CC cell) is therefore the **expected** shape, not a bug — the per-cell truth is `r.measured`/`r.verdict` in `scenario_runs` (§Rollout step 2). Never "fix" a low measured-cell count by trimming the CC list: that breaks the DD-1 symmetry and the DD-4 guard's premise.
- **Label truncation on `battery_degraded`: `[:20]` → `[:40]`** for `failed_labels` and `skipped_labels` (`main.py:1331`, one line; decision (iv)). With 28 standing items a cap hit between the halves would otherwise name 20 of the 28+ skipped. `oversized_labels[:20]` (line 1332) is pin-only and bounded by `MAX_ACTIVE_PINS`, unchanged. Residual: 28 standing + 20 pins = 48 can still exceed 40; the `skipped`/`failed` **counts** are always complete, only the label list is capped.
- **`battery_terminated` is unchanged** — `measured`, `failed`, `not_started` stay totals; no per-strategy fields (it is the SIGTERM path and the arithmetic uses the total).

**Rejected:** a `strategy` field on `battery_pin_failed` — it is derivable from the label and from the row's `spec_json`; adding fields to the per-item event is scope creep with no reader.

## Proposed approach

All production changes are in `main.py`; everything else is tests and docs.

### `main.py`

1. **Extract** the body of `battery_standing_specs` into a private builder
   `_standing_specs(config: Config, *, strategy: str, today=None) -> list` — same loop over `config.stock_symbols`, same `end`/`start`/`holdout_start`, same `starting_cash`, `run_sensitivity: False`, `scenarios: []`, and `'strategy': strategy`. Dict key order must be exactly today's (the byte test compares `json.dumps(..., sort_keys=True)` so order is not load-bearing for the store, but keep it anyway).
2. `battery_standing_specs(config, *, today=None)` → `return _standing_specs(config, strategy=WHEEL_STRATEGY, today=today)`. Keep its docstring's first paragraphs; **replace** the "Still wheel-only, now by CHOICE" paragraph with a pointer to FC-117 and `battery_covered_call_specs`.
3. **New** `battery_covered_call_specs(config, *, today=None) -> list` → `_standing_specs(config, strategy=COVERED_CALL_STRATEGY, today=today)`. Docstring states DD-1 (the CC profile has no `stocks:` section; the list is the process profile's live universe; the lake covers it by construction, DD-4) and that the replay profile is resolved per item by `resolve_replay_config` from the spec's `strategy` — the process context (dataset, store) stays the wheel's, which is the FC-075 DD-4 exception argued in Phase C.
4. `BatteryItem` gains a `strategy` slot (`str | None`): extend `__slots__ = ('label', 'spec', 'pin_id', 'note')` (`main.py:955`) to `(..., 'strategy')` — the class uses `__slots__`, so a bare attribute assignment without the slot raises `AttributeError`. Set by the constructor from the spec: `spec.get('strategy') or WHEEL_STRATEGY` when `spec` is a dict, else `None`. Used only for counting; validity is still `run_sweep_cmd`'s job.
5. `run_battery_cmd`:
   - `wheel = battery_standing_specs(config)`; `cc = battery_covered_call_specs(config)`;
     `items = [BatteryItem(label=f"standing:{s['symbols'][0]}", spec=s) for s in wheel] + [BatteryItem(label=f"standing:cc:{s['symbols'][0]}", spec=s) for s in cc]`, then pins appended exactly as today (DD-2 order).
   - Replace the scalar `measured` with a per-strategy counter (`measured_by = {'wheel': 0, 'covered_call': 0}`; `measured = sum(...)` where the total is used). A measured item increments `measured_by[item.strategy]`.
   - `battery_started`: add `standing_wheel=len(wheel), standing_cc=len(cc)`; `standing=len(wheel)+len(cc)`.

### Behaviour contract

- **Inputs:** the process `Config` (wheel profile), `today` (tests only), the pin store.
- **Outputs, per Saturday:** `2 × len(config.stock_symbols)` standing items + pins, submitted in DD-2 order, each through `run_sweep_cmd(spec_override=…, submitted_via='battery', run_id=…, pin_id=…, writer_override=…)`.
- **A CC standing spec** is identical to the wheel spec for the same symbol in every field except `strategy: 'covered_call'`. `canonical_spec` of it carries `strategy`; its `sweep_key` differs from the wheel's; `spec_json` on its row carries `"strategy": "covered_call"` (via `spec_payload`, `main.py:1997`).
- **Must not change:** every wheel standing spec (bytes), every wheel `sweep_key`, `BATTERY_*` constants, `submitted_via`, the pin path, exit code (always 0), the exit-class separation, the SIGTERM handling and the `battery_terminated` event's fields (no per-strategy fields), the `reason` enum, `oversized_labels[:20]`, the `scenario_runs`/`scenario_sweeps` schemas (no column for `premium_yield_on_lot` — FC-118), and every `cloudbuild.yaml` line other than the one `--memory` flag.
- **Failure isolation** is inherited: a CC item that fails or is refused costs one `failed` row and one `battery_pin_failed` event (label `standing:cc:<SYM>`, `invalid=` as today) and the loop continues. A CC refusal never nags (`_battery_nag` is pin-only, unchanged).
- **Wall cap:** with the cap already passed, CC items are skipped **after** all wheel items were given their chance and **before** pins — i.e. `skipped_labels` for a cap hit between the sets lists `standing:cc:*` then `pin:*`.

## Risks & mitigations

- **Risk:** the CC replay hits a per-symbol failure the console never exercised (only one live CC sim exists, `a5c9c5626b4148eb`, one symbol).
  - **Mitigation:** per-item isolation is inherited — a failing CC symbol costs its own `failed` row and `battery_pin_failed` event, never the wheel half. The first composed Saturday is watched (§Rollout). This is the "first covered-call measurements this project has ever taken" argument in Phase C, now with an operator watching.
- **Risk:** the CC half is slower than sized (every symbol on the PFE-class vendor path, §DD-2 worst case).
  - **Mitigation:** even the worst case is ~12 min against a 240 min cap; the CC half's cost is read off `scenario_sweeps.started_at`/`finished_at` grouped by strategy (DD-2) and the table is re-checked against it in §Execution.
- **Risk (R4): out-of-memory is the one failure the battery cannot isolate.** 28 materialisations in one container at the Job's 1 GiB, with the tmpfs chain cache counting against memory (`cloudbuild.yaml:1068`), a 40 % peak already sampled on 09-05 with 14 items, and the only CC replay so far run at 2 GiB. An OOM is a SIGKILL: no `battery_degraded`, no `failed` row, and the backfill's exit code is lost with it (`main.py:685-690`) — a successful data run reads as a page.
  - **Mitigation:** `--memory=2Gi` in this PR (decision (ii)); a mandatory manual execution after merge with peak memory recorded before the first Saturday (§Rollout); if the peak exceeds 75 % of 2 GiB the first Saturday waits for a follow-up (per-item cache eviction or a wider Job), filed then.
- **Risk (Q6): committed-table horizon drift biases the CC series more than the wheel's, silently.** Two tables in `src/backtesting/data/` are frozen snapshots: `dividend_history.json` has `until = 2026-07-18`, so every trailing-year window ending after that is `window_exceeds_table` (`src/backtesting/data/dividends.py:194-216`: "dividends after {covers} are missing from both legs") — and the CC benchmark, the lot held, is dividend-inclusive (`src/backtesting/metrics/fitness.py:74-79`), so B&H and the strategy both understate income after 07-18. `earnings_dates.json` was generated 2026-08-03; its last known dates are already **past** for AMD (2026-08-04), PFE (2026-08-04) and NVDA (2026-08-26), and the replay's earnings gate **fails open** past a symbol's horizon (`src/backtesting/engine/historical_earnings.py:111-119`: "returns … `symbols_past_horizon` … rather than reading a biased number") — the CC replay writes calls across earnings the live FC-013 gate would have blocked, and the wheel replay sells puts across them. Both are stamped only in the cell artifact's `data_quality` (`simulator.py:400, 1084` → `fitness.py:140, 707`), never on the row. As the standing windows roll forward every Saturday, more symbols cross the horizon and more of the dividend window falls past `until`; the bias grows weekly with nothing on the row to show it.
  - **Mitigation in this PR:** the first-Saturday checklist reads both stamps per CC item and records the symbol list (§Rollout). **Refresh cadence is FC-119** (decision (v)) — the tables need a re-fetch before the CC series is read for decisions; this plan does not refresh them (a refresh moves `src/**` and therefore the engine identity, which is its own event).
- **Risk:** a reader of the existing trend query mixes wheel and CC `annualized_return` in one series (different denominators).
  - **Mitigation:** the documented query gains the `strategy` column and the warning (DD-3) in the same PR; there is no dashboard consumer to mislead (Non-goals).
- **Risk:** the frozen wheel literal (test 3) is captured from a `main.py` already edited.
  - **Mitigation:** the PR body states the commit the literal was generated from; the reviewer regenerates it from `main` and diffs.
