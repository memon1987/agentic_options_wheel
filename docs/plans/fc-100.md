### DD-1 — The `rolling:` block: seven keys identical to the wheel, one stated Symmetry difference (operator decision D-A)

Add to `config/covered_call.yaml` (after `earnings:`, before `risk:`, mirroring `settings.yaml`'s placement) the full eight-key block:

```yaml
rolling:
  enabled: true
  itm_trigger_ratio: 1.00               # DIFFERS from the wheel (0.98) — see docs/plans/fc-100.md DD-1
  max_extension_days: 14
  max_replacement_delta: 0.60
  min_net_credit_per_contract: 0.00
  imminence_extrinsic_threshold: 0.20
  btc_fill_timeout_seconds: 120
  fallback_strike_attempts: 2
```

| `max_replacement_delta` | `0.60` | `0.60` | `risk_manager.py:96`; `market_data.py:813` | same entry band on both profiles, same deep-ITM churn to block |

*Rejected:* a minimal block (`enabled: true` + `itm_trigger_ratio` only, defaults for the rest). Defaults equal the wheel's values today, but a wheel-side retune would then silently diverge the profiles; T-1 pins each key's expected value per profile so any divergence is a reviewed edit on both files.

*Rejected:* `enabled: false` in the PR with the enable done by env. Env wins whenever set (`config.py:735-747`), which would make the yaml key a corpse on the service, and a deploy wipes the env (`--set-env-vars` replaces the set), silently disabling the roller at the next merge.

**Runbook line (FC-110), in the yaml header and `docs/gates.md` §roll path:** the roll path does not read `universe.excluded_symbols` — *to opt out of a symbol that has an open short call, also pause `cc-roll-daily` or close the call.*

### DD-2 — Env levers: **no** `ROLLER_ENABLED`; `ROLLER_DRY_RUN` for one supervised session, race closed

- **`ROLLER_ENABLED` is not added anywhere.** Mirroring the wheel means yaml enables, env kills. Putting `ROLLER_ENABLED=true` in the `deploy-cc-canary` env would (a) be the 11th fixture-ledger deviation for a value that changes nothing, (b) make `rolling.enabled` unread on that service (env wins), so the durable kill would then require a deploy-config PR instead of a one-line yaml PR. The kill switch stays `gcloud run services update covered-call-engine --region=us-central1 --update-env-vars ROLLER_ENABLED=false` — and, as on the wheel, it survives only until the next merge's `--set-env-vars`; the durable off is `enabled: false` in the yaml.
- **Shadow = one supervised dry-run session, same day, with the scheduler paused.** `ROLLER_DRY_RUN=true` applied with `--update-env-vars`, removed with `--remove-env-vars` the same session (§Rollout step 5). The promote guard (`cloudbuild.yaml:504-530`) tolerates an env-only revision on the current image, so this cannot strand a build.
- **The race, and how it is closed (reliability R3).** A merge landing between "dry-run is serving" and the triggered run re-deploys with `--set-env-vars` (`cloudbuild.yaml:584`), wipes `ROLLER_DRY_RUN`, and the trigger then fires **live** against the two real short calls. Required, all three: **(a) a merge freeze for the session** — no push to `main` by anyone (the operator and every agent session) from the env update until `--remove-env-vars` has been confirmed; **(b) the trigger is fired only from one command chain** that, immediately before `jobs run`, asserts the *serving* revision's env contains `ROLLER_DRY_RUN=true` **and** `gcloud builds list --ongoing --format="value(id)"` is empty (§Rollout step 5 gives the chain); **(c) before `--remove-env-vars`**, assert zero `call_roll_btc_placed` (`call_roller.py:611`) on `covered-call-engine` in the session window — if one exists, dry-run was not what ran; stop and read.
- **Alternative considered (reliability R3): skip the env mutation and run one supervised LIVE cycle, the way FC-078 launched.** Not adopted. With 1.00 and today's prices the likely first cycle is `not_itm_enough` ×2 either way, so a live cycle proves no more about pricing than dry-run does — but it is the first time the roll path executes on this profile, and if a position *is* through its strike a live cycle places a BTC on a path with the FC-107 ceiling still in force. Dry-run costs one env mutation whose race is closed by (a)–(c); a live first cycle costs an order if anything about the profile plumbing is wrong. FC-078's precedent was on a profile whose scan/execute path had run for months; this one's roll path has never run.
- **Why not N sessions:** an out-of-band `ROLLER_DRY_RUN` is wiped by the next deploy in the unsafe direction (dry-run → live), and the FC-096 Phase C build merges right behind this PR. A multi-session shadow would have to live in `cloudbuild.yaml` (deviation 11) and be removed by a second deploy-config PR (deviation 12). *Operator override, non-blocking:* if an extended shadow is wanted, it is the cloudbuild-carried form, never the out-of-band one.

### DD-7 — FC-107 is a precondition: `cc-roll-daily` is not resumed until `--timeout` ≥ the roll budget on both bot services (operator decision D-B)

The measured facts. Wheel `/roll` durations with **instant paper fills**, 2–4 positions: 14, 141, 140, 150, 124, 26 s — about **35 s per position of chain fetch and evaluation** before any order. CC arithmetic with two positions: ≈70 s evaluation; one BTC poll to timeout (`btc_fill_timeout_seconds: 120`) + cancel settle (15 s) = **205 s before any STO is placed**; one STO rung to timeout (+120 s poll + 15 s settle) ≈ **340 s > 300 s**. The cycle-budget guard (1500 s, 600 s/position) assumes an 1800 s request and refuses nothing at 300.

What the cut does, precisely: Cloud Run returns **504 to the scheduler** (a job failure no alert policy watches; retries are 0). The handler thread is not killed — it is **CPU-throttled** (neither bot service has `--no-cpu-throttling`; `--concurrency=10`) and **resumes when the next inbound request wakes the instance** (`/monitor` at :55, `/regression` at :45, an ingest), placing the remaining STO rungs on limits computed minutes earlier, under a `strategy_lock` the waking request then queues behind. `call_roll_naked_exposure` is the dying thread's job, so the one alert wired for a stranded BTC never fires. FC-107 carries this text and the fix (`--timeout=1800` on both bot canary steps, fixture re-freeze, wheel-scope PR).

Consequence for this plan: the CC job is created paused (DD-3), the dry-run session runs with it paused (an evaluation-only cycle is ~70 s), and **resume is gated on FC-107 merged + deployed, verified by `gcloud run services describe <svc> --region=us-central1 --format="value(spec.template.spec.timeoutSeconds)"` → `1800` on both services**. *Rejected:* resuming on the paper account before FC-107 because "paper fills are instant" — the 205 s pre-STO path needs only one non-marketable BTC, and the alert that would tell us is the one the cut suppresses.

## Risks & mitigations

- **Risk: the Cloud Run 300 s ceiling (FC-107).** Measured: 35 s/position evaluation; one BTC timeout path = 205 s before any STO; one STO rung timeout ≈ 340 s > 300 s. On the cut: scheduler 504 nobody watches, thread throttled and resumed by the next request on stale limits, `call_roll_naked_exposure` never fires (DD-7). *Mitigation:* **the job is not resumed until FC-107 is deployed on both services** — verified by `timeoutSeconds`, not assumed. Until then the dry-run session (evaluation only, ~70 s) is the only `/roll` traffic. *The rev-1 "realistic cycle is seconds" claim is withdrawn.*
- **Risk: a cut cycle is invisible** — a scheduler 504 that no policy or `/regression` check watches (DD-5, FC-108/111). *Mitigation:* §Rollout step 7's first-cycle check is `roll_cycle_started` **with** `roll_cycle_completed` and `httpRequest.latency < 300 s`; a `roll_cycle_started` without its `completed` is the signature of a cut.
- **Risk: the dry-run race** (a merge wiping `ROLLER_DRY_RUN` before the triggered run). *Mitigation:* DD-2 (a)–(c): merge freeze, assert-then-run in one chain, zero-`call_roll_btc_placed` assertion before the env is removed.
- **Risk: the kill switch is wiped by the next deploy** (`--set-env-vars` replaces the env set). *Mitigation:* documented in the yaml header and §Rollout; the durable off is `enabled: false` in the yaml (one-line PR) or pausing `cc-roll-daily`.
- **Risk: UNH ex-dividend early assignment while an ITM call rides** (FC-109). *Mitigation:* none new; DD-1's safety reasoning — a roll never makes early exercise worse, and the miss case equals no roller.
- **Risk: an operator excludes a symbol that has an open short call; the roller still rolls it** (FC-110). *Mitigation:* the runbook line (DD-1) — pause `cc-roll-daily` or close the call.
- **Risk: `roll_position_error` on one symbol.** Per-position isolation keeps the cycle alive; the CC roll policy's error group now carries it (DD-6).
- **Risk: two rolls on one position in one day** if a manual live run coincides with the 15:30 fire. *Mitigation:* the manual run is dry-run and the job is paused throughout.

**Real-money preconditions on this profile (not paper blockers, on the record):** FC-107 (already gated above); FC-088 — the roller's BTC/STO limits are rounded to the cent, not to tick, and never pass through `limit_pricing.round_to_tick`, so above $3.00 they are off-tick on GOOGL and UNH (both are in `VERIFIED_PENNY_PROGRAM_ROOTS`, `src/strategy/limit_pricing.py:127-130`, verified `ppind=True` 2026-08-28 — the tick class is known; the roller just does not apply it); FC-089 (socket timeouts under `strategy_lock`); OPRA agreement for non-indicative quotes (`docs/CLAUDE.md` §Strategy Configuration).

## Amendment (2026-09-08, from the FC-107 plan reviews — binding on the build's PR body and the rollout)

- **DD-7's mechanism paragraph inherited a false premise.** A request cut by Cloud Run at the service timeout does NOT stall and resume on the next inbound request: on 2026-08-13 an orphaned `/scan` thread kept emitting for ten minutes with no request in flight (CPU throttling slows an I/O-bound poll loop; it does not park it). After a cut the ladder keeps running roughly on schedule and its terminals and `call_roll_naked_exposure` still fire if the instance lives; what is lost is the scheduler's view (a silent 504) and the `/roll` response. The dangerous residual is instance scale-in mid-ladder. The FC-107 precondition stands for the right reason: the guard was sized against 1800 s and the 300 s flag silently undid it.
