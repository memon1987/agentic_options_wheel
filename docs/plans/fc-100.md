## Goals

- The covered-call service evaluates every short call daily at 15:30 ET and executes credit-only up-and-out rolls under exactly the wheel's gate set.
- The roll is observable on the CC service the way it is on the wheel: alert on `call_roll_completed` / stranded-BTC / unknown-disposition events, and on roll-path cost-basis skips.
- The wheel is provably untouched: `settings.yaml`, `src/`, `cloudbuild.yaml` and the frozen deploy flags are byte-identical.
- Hand Phase C (`docs/plans/fc-096-c.md`) the named gate list its CC replay must share (§Phase C hand-off).

## Non-goals

- No change to roller behaviour, pricing, or knob semantics on either profile (FC-088 tick snapping, FC-089 socket timeouts, dividend-aware imminence — all stay filed).
- No `cloudbuild.yaml` / `tests/fixtures/cloudbuild_contract.json` change. The Cloud Run `--timeout=300` vs 1500 s cycle-budget mismatch (§Found while planning, item 1) is a **shared** defect that bites the wheel first and is filed, not fixed here.
- No `/regression` code change (§DD-5).
- No decision on the CC profile's entry-side tunables (`call_target_dte`, bands — FC-086/OQ-1 own those).

## Design decisions

### DD-1 — The `rolling:` block: identical knobs, identical values, on the record as a *deliberate* non-difference

Add to `config/covered_call.yaml` (after `earnings:`, before `risk:`, mirroring `settings.yaml`'s placement) the full eight-key block, values byte-equal to the wheel's:

```yaml
rolling:
  enabled: true
  itm_trigger_ratio: 0.98
  max_extension_days: 14
  max_replacement_delta: 0.60
  min_net_credit_per_contract: 0.00
  imminence_extrinsic_threshold: 0.20
  btc_fill_timeout_seconds: 120
  fallback_strike_attempts: 2
```

Every key has a live consumer on this profile the moment `enabled: true` (Config discipline): `rolling_enabled` (`wheel_engine.py:722`), `rolling_itm_trigger_ratio` (`call_roller.py:199,278`), `rolling_max_extension_days` (`:387`, and `RiskManager.validate_roll` via `max_expiry`), `rolling_max_replacement_delta` (`risk_manager.py:96`, `market_data.py:813` roll profile), `rolling_min_net_credit_per_contract` (`call_roller.py:411,424` + execute-time re-check), `rolling_imminence_extrinsic_threshold` (`:343`), `rolling_btc_fill_timeout_seconds` (`:1102`), `rolling_fallback_strike_attempts` (`:978`). All four bounded keys validate under `Config._validate_config` (`config.py:329-358`) for any profile.

Why identical, knob by knob (Symmetry principle: a difference must be stated and justified; so must a non-difference where one was plausible):

- `itm_trigger_ratio: 0.98` — a moneyness test; profile-independent.
- `max_extension_days: 14` — **expiry-relative** (`old_expiry + N`, FC-078 DD-3), so it does not interact with the CC profile's 14-DTE entry target vs the wheel's 7. *Rejected:* 21 for CC "because its calls are longer" — the frame is the old contract's tenor, not the entry DTE; two weeklies beyond the current expiry is where credits live on either book.
- `max_replacement_delta: 0.60` — both profiles enter at the same band `[0.15, 0.25]`; the rail exists to block deep-ITM churn, same hazard both sides.
- `min_net_credit_per_contract: 0.00` — the credit-only invariant is the whole design; a positive floor would defer the GOOGL-class +$1 roll on this book exactly as on the wheel.
- `imminence_extrinsic_threshold: 0.20` — **the one plausible difference, kept identical deliberately.** FC-078 DD-2 sized $0.20 to "this book's payers (AAPL/GOOGL/NVDA ~$0.20–0.26)". The CC book holds UNH, which pays ≈$2.21/quarter, so early exercise becomes rational at extrinsic well above $0.20 near its ex-date. But the threshold is a *pricing-mode switch* (bid/ask → mid ± $0.05), not a gate, and the roller has **no ex-dividend-date input on either profile** — raising the number for CC would cross half-spreads more often on every symbol without modelling the actual hazard. Stated difference deferred to a shared follow-up FC (dividend-aware imminence; §Found while planning, item 7).
- `btc_fill_timeout_seconds: 120`, `fallback_strike_attempts: 2` — execution mechanics; same broker, same paper simulator.

*Rejected:* a minimal block (`enabled: true` only, defaults for the rest). Defaults equal the wheel's values today, but a future wheel-side retune would then silently diverge the profiles; the census test in §Tests pins the two mappings equal so any divergence is a reviewed edit on both files.

*Rejected:* `enabled: false` in the PR with the enable done by env. Env wins whenever set (`config.py:735-747`), which would make the yaml key a corpse on the service — the exact defect Config discipline names — and a deploy wipes the env (`--set-env-vars` replaces the set), silently disabling the roller at the next merge.

### DD-2 — Env levers: **no** `ROLLER_ENABLED`; `ROLLER_DRY_RUN` for one supervised session only

- **`ROLLER_ENABLED` is not added anywhere.** Mirroring the wheel means yaml enables, env kills. Putting `ROLLER_ENABLED=true` in the `deploy-cc-canary` env would (a) be the 11th fixture-ledger deviation for a value that changes nothing, (b) make `rolling.enabled` unread on that service (env wins), so the durable kill would then require a deploy-config PR instead of a one-line yaml PR. The kill switch stays `gcloud run services update covered-call-engine --region=us-central1 --update-env-vars ROLLER_ENABLED=false` — and, as on the wheel, it survives only until the next merge's `--set-env-vars`; the durable off is `enabled: false` in the yaml.
- **Shadow = one supervised dry-run session, same day, before the scheduler is live** (`ROLLER_DRY_RUN=true` applied with `--update-env-vars`, removed with `--remove-env-vars` the same session — §Rollout step 4). The promote guard (`cloudbuild.yaml:504-530`) already tolerates an env-only revision on the current image, so this cannot strand a build.
  *Why not N sessions:* an out-of-band `ROLLER_DRY_RUN` is wiped by the next deploy **in the unsafe direction** (dry-run → live, with no operator flip), and the FC-096 Phase C build merges right behind this PR. A multi-session shadow would have to live in `cloudbuild.yaml` (deviation 11) and be removed by a second deploy-config PR (deviation 12) — two reviewed ledger entries for a shadow that can observe nothing until a CC short call exists and goes ITM (as of RELEASE_2026-09-01 the account had no written call; verify at rollout). The wheel launched with no log-only gate at all (FC-078 DD-8, operator). One supervised cycle proves the profile plumbing on real positions (interlock → engine → positions → per-position terminal events, and would-be limits if anything is ITM); the deeper proof is the unit test through the real `CallRoller` on the real CC profile (§Tests, T-3).
  *Operator override, non-blocking:* if an extended shadow is wanted, it is the cloudbuild-carried form above, not the out-of-band one.

### DD-3 — The scheduler: `cc-roll-daily`, field-for-field the wheel's job (operator step)

```sh
gcloud scheduler jobs create http cc-roll-daily \
  --location us-central1 --schedule "30 15 * * 1-5" \
  --time-zone "America/New_York" \
  --uri "https://covered-call-engine-omnlacz6ia-uc.a.run.app/roll" \
  --http-method POST \
  --attempt-deadline 1800s \
  --oidc-service-account-email 799970961417-compute@developer.gserviceaccount.com
```

Verified against `gcloud scheduler jobs describe options-wheel-roll-daily` (2026-09-08): schedule `30 15 * * 1-5`, `timeZone: America/New_York`, `httpMethod: POST`, `attemptDeadline: 1800s`, `oidcToken.audience` = the URI (gcloud's default), SA `799970961417-compute@…`, no retries (`retryConfig` has no `retryCount`; `maxRetryDuration: 0s`). The CC jobs (`cc-monitor-hourly` described) use the same SA and audience form, so no extra header/auth is needed. The 15:30 slot sits after the CC service's last `/monitor` (14:55), last `/scan` (15:00) and last `/run` (15:15) — the same ordering FC-078 relied on (profit-taking churn settled; a freshly sold call is OTM and skips `not_itm_enough`).

**Retries stay 0, deliberately** (FC-078 rollout §5): a scheduler retry after a deadline kill re-enters a cycle whose partial order state it cannot see; the daily cadence is the retry.

### DD-4 — No code change: `/roll` on the CC profile is already end-to-end (every site, by reading)

- `deploy/cloud_run_server.py:1288-1322` — `/roll` is `@require_api_key` + `@require_account_match` (CC interlock `PA37XLNWDLB3`), takes `strategy_lock` (serialises against `/monitor` and `/run` on the same instance), market-open guard, then `WheelEngine(strategy_config()).run_rolling_cycle()`. **No `strategy_id` branch on this path** — unlike `/run`'s `reconcile_positions` gate (`:591`) there is nothing wheel-shaped to skip: the cycle emits `call_roll_*` events only, writes no BigQuery row, and the FC-075 Seam 4 write interlock was lifted for every endpoint (`tests/test_fc075_phase2.py:309` already proves `/roll` reaches its handler on the CC profile).
- `src/strategy/wheel_engine.py:53-95, 708-883` — `WheelEngine.__init__` builds `AlpacaClient(config)` (CC secrets), `MarketDataManager`, an empty `WheelStateManager`; `run_rolling_cycle` gates on `config.rolling_enabled`, builds `RiskManager(config)`, `EarningsCalendarService(config)` (CC `earnings.enabled: true`, `FINNHUB_API_KEY` bound — the CC scan already constructs it), `CallRoller(...)`, lists positions, keys stock by OCC root, pairs short calls with shares, runs the open-order guard (`get_orders`, FC-043-fixed), cycle budget, per-position isolation. Nothing reads a wheel-only key.
- `src/strategy/call_roller.py` — `CostBasisResolver(alpaca_client, config)` (`:128`) resolves the floor from Alpaca `avg_entry_price` with the divergence cross-check against **`config.bigquery_dataset`** (`cost_basis.py:366-380`, FC-075 DD-4 fix) → `covered_call.trades_from_activities`. This is the same resolver call the CC scan path has made on every scan since go-live (`below_cost_basis` decisions prove it resolves on this account). `find_suitable_calls(criteria_profile='roll', min_strike_price=max(basis, old+0.01), include_expiry_on_or_before=old_expiry+14, exclude_expiry_on_or_after=span_floor)`.
- `src/api/market_data.py:392-700, 798-815` — the `'roll'` profile applies **only** the delta rail and the basic liquidity check; it does *not* read `call_target_dte`, `min_call_premium`, `call_delta_range`, `universe.min_open_interest` or `universe.max_spread_pct` (those run on the `entry` branch, `:823-860`). So the CC profile's 14-DTE ceiling and suspended OI floor are inert on rolls, exactly as on the wheel. `get_option_chain_with_analysis` → `get_stock_metrics` hard-indexes `min_stock_price`/`max_stock_price`/`min_avg_volume`, present on the CC profile since PR #107.
- `src/risk/risk_manager.py:44-110` — `validate_roll`: strike > old, strike ≥ basis, delta ≤ `rolling_max_replacement_delta`, expiry ≤ `max_expiry`. Profile-independent.
- `src/utils/config.py:325-358, 717-818` — validation and the eight accessors are profile-independent; `earnings_blackout_days` (wheel-only key) is read by the put leg only, not by the roller.
- Writers: **none on the roll path.** `log_trade_event` / `log_terminal_skip` are structlog only. Fills reach `covered_call.trades_from_activities` through `cc-activities-ingest` (:07 hourly) — the same route as CC call sales.

Conclusion: config + scheduler + observability. The build touches no `src/` file.

### DD-5 — `/regression` mirror: nothing to change, on the record

`tools/testing/regression_monitor.py` has **no roll-specific check on either profile**: `check_risk_parameters` (`:978`) reads `max_position_size`, duplicate underlyings, naked calls, cost-basis floor; it resolves the profile via `STRATEGY_CONFIG` (FC-082, `:1044`) so `cc-regression-hourly` already reads `covered_call.yaml` and the new block changes nothing it consumes. `check_logs` counts error-severity entries generically, so `roll_position_error` / `call_roll_execution_error` on the CC service would raise its error rate like any other error. The roll's detective layer is the alert policies (DD-6). A roll-cadence check ("last `roll_cycle_completed` older than 1 trading day") is a shared gap on both profiles — filed, not built here (§Found while planning, item 6).

## Risks & mitigations

- **Risk: Cloud Run `--timeout=300` on `covered-call-engine` (live-verified) vs the roller's 600 s per-position worst case.** A BTC that fills followed by a slow STO ladder can outlive the request; Cloud Run cuts it at 300 s — the worst seam (shares uncovered, ladder frozen). Same on the wheel today (§Found while planning, 1). *Mitigation:* on paper, marketable limits fill immediately so the realistic cycle is seconds; `call_roll_naked_exposure` is alert-wired (DD-6) and the next `/scan → /run` re-covers through the entry gates (FC-078 DD-1). *Accepted for the paper account; the shared FC is a precondition before real money on either profile.*
- **Risk: the kill switch is wiped by the next deploy** (`--set-env-vars` replaces the env set) — an operator who "turned it off" with env finds it on again after the next merge. *Mitigation:* documented in the yaml header and §Rollout; the durable off is `enabled: false` in the yaml (one-line PR).
- **Risk: UNH ex-dividend early assignment while an ITM call rides** (dividend ≈$2.21/qtr, threshold $0.20). *Mitigation:* none new — assignment realises `strike ≥ avg_entry_price` + premium (FC-075 accepted-risk entry); filed as a shared follow-up (item 7).
- **Risk: off-tick limits above $3 rejected on a live account** (FC-088). GOOGL/UNH options are well above $3. *Mitigation:* paper simulator ignores increments; FC-088 is a real-money precondition on this profile too.
- **Risk: `roll_position_error` on a symbol raises the CC `/regression` error rate.** Expected behaviour; the per-position isolation keeps the cycle alive.
- **Risk: two rolls on one position in one day** if the supervised manual run is done live (not dry-run) on the same day the scheduler fires. *Mitigation:* the supervised run is dry-run and the job is paused until it is done (§Rollout).

## Phase C hand-off — the gates the CC replay must share (by name)

The replay already runs `engine.run_rolling_cycle()` once per decision day after the normal cycle (`src/backtesting/engine/simulator.py:735`), and the cycle gates itself on `config.rolling_enabled`; `persist.py:1287` and `overrides.py:279` map `rolling.*` keys. So **after FC-100 merges, a `strategy: covered_call` replay loading `config/covered_call.yaml` rolls with no further change** — the "one-line profile change" fc-096-c §Roller anticipated. Phase C must pin these, by name, so replay == live:

| Gate (live site) | Config key / value | Replay must supply |
|---|---|---|
| ITM trigger `stock/strike ≥ ratio` (`call_roller.py:199`) | `rolling.itm_trigger_ratio: 0.98` | two-sided stock quote with `ask/bid ≤ 1.05` (else `stock_quote_unusable` skips — a one-sided model quote silently disables the roller) |
| Cost-basis floor `min_strike = max(basis, old+0.01)` (`:389`) | none — `CostBasisResolver` on `avg_entry_price` | the synthetic lot's position dict **must carry `avg_entry_price`** (`alpaca_adapter.py:189,211` do for wheel lots); an absent field → `cost_basis_unresolved` on every position = roller inert with no error |
| Earnings span on the replacement (`:357-385`) | `earnings.enabled: true` (CC) | `HistoricalEarningsCalendar.next_earnings_info` must answer KNOWN or CLEAR for CC symbols; UNKNOWN fails closed (`earnings_unknown`) — a CC symbol missing from the earnings table never rolls in the replay |
| Extension horizon `expiry ≤ old_expiry + N` (`:387`; `validate_roll`) | `rolling.max_extension_days: 14` | **chain reach ≥ `call_target_dte + max_extension_days` = 28 DTE** for CC cells. The lake is built at 22-reach (fc-096-a); `simulator.py:172` documents that the roller's candidate set is bounded by the reach shown, not the arm's DTE. Phase C must either widen the CC lake reach or label the truncation in the footer — otherwise the replay's roll credits are systematically lower than live |
| Delta upper rail (`market_data.py:813`, `risk_manager.py:96`) | `rolling.max_replacement_delta: 0.60` | model-chain deltas present on every candidate |
| `'roll'` criteria profile (`market_data.py:798-815`) | — | no DTE cap, no premium floor, no entry band, **`min_open_interest` / `max_spread_pct` not applied** on rolls (Phase C's spread-gate suspension is moot here); liquidity check `volume==0 and OI<10` applies |
| Credit invariant on **placed limits** (`:411-424`, `:567-590`, ladder rungs) | `rolling.min_net_credit_per_contract: 0.00` | BTC limit = old ask (or mid+0.05 in imminence), STO limit = candidate bid (or mid−0.05); the broker model must fill at those limits, not at mid — filling at mid would manufacture credit the live roller never sees |
| Imminence pricing mode (`:343`) | `rolling.imminence_extrinsic_threshold: 0.20` | extrinsic from the old call's two-sided quote |
| Max-credit selection, ties → higher strike (`_legal_candidates`) | — | the full legal set (the `'roll'` profile returns all suitable calls, not top-5) |
| Open-order guard (`wheel_engine.py:790`) | — | adapter `get_orders()` returns the day's resting orders (a BTC from the monitor leg blocks the roll, as live) |
| Cadence | daily after the cycle | already `simulator.py:735` |
| Execution knobs | `btc_fill_timeout_seconds`, `fallback_strike_attempts` | not sweepable (`overrides.py` exposes six keys); replay uses the profile's |

Phase C should **not** override `rolling.*` for CC cells (the replay measures live policy), and its footer should name the reach decision above.
