## Context

Owner requirement, 2026-08-01, verbatim:

> "We want the ability to write covered calls in a separate account that lives separately from our options wheel account. We want to reuse mechanical components to make the overall engine extensible vs creating two duplicate mechanisms. The new covered call engine will have its own user-tunable parameters given it's a different strategy (with a different target outcome). We'll also want to run and simulate separate backtests for the standalone covered-call strategy."

Four firm requirements:

1. Covered calls run in a **separate Alpaca account**, isolated from the wheel.
2. **Reuse mechanical components** — extensibility, not a duplicate engine.
3. The covered-call engine has **its own user-tunable parameters** (delta, DTE, premium, floor, exclusions) distinct from the wheel's.
4. **Separate backtests/simulation** for the standalone strategy.

The architecture (separate account, one image, config-selected services) was validated by two adversarial reviews in the prior effort and is carried forward as settled. What has changed since then — and what makes this plan mostly a *reuse* plan rather than a *build* plan — is that main has independently shipped the hardest mechanical pieces: two-pool share-ledger selection (FC-038), the shared cost-basis resolver with an execute-time gate (FC-050), the broker-authoritative floor (FC-065 P1), and canonical OCC parsing (FC-045/FC-052). See §What's already solved on main.

## Goals

- A second Cloud Run service, from the **same container image**, trading covered calls in paper account `PA37XLNWDLB3` with zero shared mutable state with the wheel service.
- Every strategy-scoped parameter (delta band, DTE, premium floor, exclusions, sizing) read from a per-strategy YAML; nothing strategy-specific hardcoded.
- The covered-call floor policy is the **already-decided production policy**: hard `strike >= avg_entry_price` via `CostBasisResolver`, no drawdown pause. This plan does not design a floor.
- A covered-call backtest that replays the same live strategy code through the existing fake broker (post-FC-068 pipeline).

## Non-goals

- **Position tagging / single-account multi-strategy.** Settled against — see §Why not tagging.
- **Rolling.** Out of initial scope (see Phase 2 policy decisions). Early-close + re-write next cycle carries the value; the roller is broken (FC-062/FC-066) and heavily `wheel_state`-coupled.
- **A `Strategy` protocol / plugin abstraction for the backtester.** The engine replays live production code through a fake broker; building an interface for a single second implementor is premature. The covered-call backtest depends on the covered-call engine existing, not on an abstraction.
- **Changing any wheel behavior.** The wheel's config, blob layout, `client_order_id` scheme, and BQ dataset stay byte-identical. Phase 1 must be a no-op for the wheel service.
- **Automated stock purchase.** Stock enters the covered-call account manually via the Alpaca UI; the bot adopts holdings whenever they appear.

## Why not tagging (condensed — settled, do not reopen)

Two adversarial reviews upheld separate-account isolation on four grounds, re-verified against this tree (HEAD `643fd05`):

- **Alpaca nets positions per symbol per account.** There is no broker-side tag; two strategies holding the same underlying are indistinguishable at the position level.
- **Assignments arrive as OPASN/OPTRD activities with no `client_order_id`** — attribution breaks exactly at the event that matters most to a wheel.
- **The wheel adopts everything it sees.** `WheelEngine.reconcile_positions()` (`src/strategy/wheel_engine.py:712`; adoption block at :1127–1161) inserts ANY untracked Alpaca position into wheel state (`untracked_position_found` → `symbol_states[symbol] = {...}`). In a shared account the wheel would hijack covered-call shares by design.
- **Risk sizing is account-wide** (buying power, equity) — no per-strategy partition exists at the broker.

Consequence: isolation comes from the account boundary, and the code's job is to make cross-account mistakes structurally impossible (Seams 1–2), not to attribute positions.

### Seam 1 — strategy-key the GCS opportunity store (BLOCKING; do first)

**Defect:** `src/data/opportunity_store.py:18` hardcodes `bucket_name: str = "options-wheel-opportunities"`, and blob paths have no strategy scoping (`_blob_path` → `opportunities/{date}/{time}.json` at :340; read prefixes at :124, :229; cleanup lists `opportunities/` at :371). All three server call sites construct `OpportunityStore(config)` with the default bucket: **store** in `/scan` (`deploy/cloud_run_server.py:182–186`), **read** in `/run` (:303–339, `get_pending_opportunities`), and **mark_executed** (:472). Two services from one image would read each other's scan output and place orders in the wrong brokerage account. **No second service may deploy before this lands.**

**Change:**

- `Config` gains `gcs.opportunity_bucket` (default: `options-wheel-opportunities`) and `OpportunityStore.__init__` reads the bucket from config instead of the keyword default. **Isolation is bucket-per-strategy** — the covered-call profile sets its own bucket (`covered-call-opportunities`, created in Phase 3). The wheel's bucket, blob layout, and in-flight blobs are untouched: zero migration, no dual-read window.
- **Defense in depth:** `store_opportunities` writes `strategy_id` (from config, Seam 3) into the blob payload; `get_pending_opportunities` and `mark_executed` assert the payload's `strategy_id` matches the running service's and **fail closed** (skip + `event_type="opportunity_strategy_mismatch"` error event) on mismatch. This converts a future mis-configured bucket into a loud no-op instead of a wrong-account order.
- Blobs written before this lands have no `strategy_id`; treat **absent** as `wheel` for one deploy cycle (blobs are same-day ephemeral), then require the field.

*Rejected alternative:* strategy-prefixed blob paths in a shared bucket (`opportunities/{strategy_id}/{date}/…`). Works, but requires migrating the wheel's live path or a dual-read window, and one IAM boundary per strategy is cleaner than path discipline inside one bucket.

### Seam 2 — single config accessor + account-number startup interlock

**Defect:** `deploy/cloud_run_server.py` constructs bare `Config()` **13 times** (lines 152, 299, 664, 976, 1011, 1037, 1063, 1160, 1289, 1345, 1398, 1443, 1753), each resolving the hardcoded default path `config/settings.yaml` (`src/utils/config.py:46`). There is no way to point a service at a different profile.

**Change:**

- Add one module-level accessor in `deploy/cloud_run_server.py` — **name it `strategy_config()`**, NOT `get_config`: `get_config` already exists as the `/config` HTTP endpoint handler (`cloud_run_server.py:1059`) and shadowing it is a latent bug. The accessor resolves `os.environ.get("STRATEGY_CONFIG", "config/settings.yaml")` once (cache the `Config` instance; the 13 call sites each currently re-parse YAML per request — replacing them with the accessor is also a small win). Replace all 13 call sites.
- **Account interlock:** on first use (cached thereafter), assert `alpaca.get_account().account_number == config.expected_account_number`, where `expected_account_number` is a new **required** YAML key (`PA3D36DVXSZ2` in `settings.yaml`, `PA37XLNWDLB3` in `covered_call.yaml`). On mismatch: log a `risk`-category error event and **refuse all order/write endpoints** — `/scan`, `/run`, `/monitor`, `/roll`, and the three `/ingest-*` endpoints return 503; `/health` reports `account_interlock: mismatch` and flips to `unhealthy`, while `/` (Cloud Run liveness) stays 200 with an `account_interlock` field so a mismatch cannot loop-restart the instance. This is the single control that makes "right code, wrong credentials" impossible. `/account` and `/positions` (read-only, no persistence or orders) are intentionally **not** guarded — they only display data to the dashboard.
- Implementation note: do the interlock lazily on first request with a cached verdict rather than import-time (Cloud Run cold-start; an import-time network call would fail deploys during Alpaca outages). **A genuine mismatch latches** for the process lifetime; a **check failure** (Alpaca unreachable, or `account_number` absent) does **not** latch — it returns False for that request and retries next request, so a transient outage self-heals.
- **Follow-up (not Phase 1):** the interlock guards HTTP routes, not the order-placing layer — `main.py` and any future Cloud Run Job bypass it. A structural check inside `AlpacaClient` would protect every entry point. File as a follow-up FC.

### Seam 3 — config namespacing + the covered-call profile (requirement #3 lives here)

**Defects / gaps:**

- `_validate_config` hardcodes `required_sections = ['alpaca', 'strategy', 'risk', 'stocks', 'monitoring']` (`src/utils/config.py:115`). The covered-call profile has no `stocks` universe — it is holdings-derived — so validation must be profile-aware.
- No `strategy_id` concept exists anywhere in config.
- The Secret Manager fallback in `_load_secret` reads `GOOGLE_CLOUD_PROJECT`/`GCP_PROJECT_ID` (`config.py:33`) but Cloud Run sets `GCP_PROJECT` — it has **never executed in prod** (also flagged in FC-058). Credential delivery MUST stay env-var based via `--set-secrets`. Do not build Seam 3 on the fallback; leave it as-is (FC-058's problem).

**Change:**

- Add top-level required key `strategy_id` (values: `wheel`, `covered_call`). `settings.yaml` gains `strategy_id: wheel` + `expected_account_number: PA3D36DVXSZ2`.
- Make `stocks` required only when `strategy_id == wheel` (or: required sections become a per-profile map keyed by `strategy_id`). All other sections stay required for both.
- Create **`config/covered_call.yaml`** — the covered-call profile, carrying its own tunables (initial values are operator-tunable defaults, flagged as OQ-2):
  - `strategy_id: covered_call`, `expected_account_number: PA37XLNWDLB3`
  - `strategy:` — `call_delta_range` (own band, default `[0.15, 0.25]` to start), `call_target_dte` + `profit_taking.dte_bands` (own copy), `min_premium`, and `floor_mode: avg_entry_price` (the only supported value today; the key exists so the mode is explicit and auditable, not to invite alternatives)
  - `universe:` — `excluded_symbols: []` (opt-out list) + inventory-validator thresholds (min open interest / max spread width / earnings-proximity window) — consumed by Phase 2
  - `risk:` — `sizing_basis: equity` (NOT buying power — 4× margin account), `max_long_market_value_pct_of_equity` alert threshold
  - `gcs:` — `opportunity_bucket: covered-call-opportunities`, `bigquery.dataset: covered_call`
- **Credentials:** same env-var names (`ALPACA_API_KEY`/`ALPACA_SECRET_KEY`) in both services; each Cloud Run service binds them to its own secrets via `--set-secrets` (wheel → existing, covered-call → `alpaca-api-key-cc`/`alpaca-secret-key-cc`). No code change; per-service env is the boundary, and the Seam 2 interlock catches any mis-binding.

### Seam 4 — BigQuery dataset threading — **DEFERRED to Phase 3**

**Defect:** five writers default `dataset_id="options_wheel"`: `src/data/trade_journal.py:68`, `src/data/analytics_writer.py:118`, `src/data/activities_ingestor.py:92`, `src/data/portfolio_history_ingestor.py:66`, `src/data/stock_history_ingestor.py:75`.

**Deferred to Phase 3 (build-time decision, 2026-08-02).** Two implementation realities moved this out of Phase 1:
1. The `strategy_id` STRING column requires an **ALTER on the live wheel BigQuery tables** — BQ streaming inserts fail on unknown fields against an existing table, so adding the field to the schema without the ALTER would break live wheel writes. That is a schema migration, not code threading, and must not ride in the isolation-seams PR.
2. `AnalyticsWriter` is a **process-global singleton** (`get_analytics_writer()`, `analytics_writer.py`) with no config in scope; routing its dataset needs a per-process source that is cleanest to wire when the covered-call service is provisioned.

Neither has an active consumer until the covered-call service writes (Phase 2/3), so both belong with dataset/table provisioning in Phase 3, where the `covered_call` tables are created fresh **with** the column and the wheel-table ALTER is a deliberate, separately-verified step. Seams 1+2 are what make cross-account **order** placement impossible; Seam 4 is analytics **routing**.

**Phase 1 did land the config surface** (`Config.bigquery_dataset`, `bigquery.dataset` in `covered_call.yaml`) so Phase 3 has it ready — but it is **NOT yet consumed** (marked NOT WIRED in both the yaml and the property docstring). **Consequence — hard Phase 3 gate:** the covered-call service must **not** run `/ingest-*` or any analytics-writing job until Seam 4 lands, or it would write covered-call rows into the wheel's `options_wheel` dataset. The `/ingest-*` endpoints are interlock-guarded (Phase 1) as defense-in-depth, but the interlock does not prevent a *correctly-configured* covered-call service from writing to the wheel dataset — only Seam 4 does.

### client_order_id — decided, mostly deferred

`AlpacaClient._generate_client_order_id` (`src/api/alpaca_client.py:117`) is the wheel's **live idempotency key** — deterministic per (symbol, qty, side, price). **Keep the wheel's id UNPREFIXED permanently**; rotating it would break retry-idempotency against open orders. Since accounts are separate, `client_order_id` collisions across strategies are impossible at the broker; prefixing only matters under single-account consolidation, which is out of scope. **Defer** any prefixing to a future strategy that shares an account (none planned). No Phase 1 change.

## Phase 2 — covered-call engine (DESIGN INTENT ONLY — gated, see §Sequencing)

**Do not write final file:line specs for this phase yet.** FC-068 deletes `run_strategy_cycle` and everything beneath it; FC-069 (17 cards, operator-signed 2026-08-01) rewrites the surviving control surface. Both rewrite the exact reuse surface this phase builds on. A **required design pass** (Fable, fresh context) re-derives the file-level spec once both land; what follows is the binding design intent and the operator policy decisions it must honor.

**Shape:** new `src/strategy/covered_call_engine.py` — a thin orchestrator over existing machinery, mirroring the production wheel's *stateless* architecture (no `WheelStateManager` analog; state is emergent from Alpaca positions — `STATE_STORAGE_BUCKET` persistence has never worked and FC-068/069 are deleting the fictional layer, so a new stateful manager would repeat the original sin). Scan derives candidates from **holdings**, not a configured stock list; select/execute go through `ExecutionEngine` (call pool only); `/monitor` early-close reuses the existing close path.

**Policy decisions already made by the owner — state, don't reopen:**

- **Strike floor:** hard `strike >= avg_entry_price`, resolved through `CostBasisResolver` with the covered-call config. **Drawdown pause disabled** (FC-065 OQ-3 precedent). No new floor design.
- **No symbol selection criteria.** Universe = every equity position in the account. Blanket adoption + `excluded_symbols` opt-out + an inventory **validator** (optionability, chain liquidity, spread width, earnings proximity) that flags-or-skips, never picks. **Operator invariant, to be stated in the engine's module docstring and the runbook:** *this account holds nothing you are unwilling to have called away.*
- **Sizing from uncommitted shares** via the FC-038 share ledger — partial coverage of a lot is correct behavior, not a binary reject. Inherits FC-061's blindness to open unfilled short-call orders; the broker's share-lock is the accepted interim backstop (see §Risks).
- **4× margin discipline:** size against `equity`, never `buying_power` (which is 4× equity in this account); alert when `long_market_value > equity`. This is config (`sizing_basis: equity`) + one monitor check, not new machinery.
- **Rolling: OUT of initial scope.** `CallRoller` takes `wheel_state` as a required positional and reads it at 11 sites including decision gates (`src/strategy/call_roller.py`), AND has never executed a roll in production (FC-066: quote-key bug, Friday/DTE eligibility gap, stateless premium) AND its floor fails open, bypassing the FC-050 guard (FC-062). Early-close + re-write next cycle covers most of rolling's value at zero of its risk.

**Prerequisite defect:** FC-067 (trade journal labels every covered call a put — `trade_journal.py:148` defaults `option_type` to `"put"`) must be fixed before this engine writes journal rows, or the new strategy's analytics are poisoned from day one. Hard prerequisite for Phase 2, not for Phase 1.

## Phase 4 — separate covered-call backtest (requirement #4; gated with Phase 2)

The backtest engine (read `docs/BACKTEST_ENGINE.md` first) **replays live production strategy code through a fake broker** — there is deliberately no Strategy protocol. Today the simulator still replays the dead engine path (`src/backtesting/engine/simulator.py:372` calls `run_strategy_cycle()`); **FC-068 repoints it to the real `scan → select → execute` pipeline.** Therefore:

- The covered-call backtest depends on **(a)** `covered_call_engine.py` existing (Phase 2) and **(b)** FC-068's repoint having landed — not on any new backtester interface.
- Design intent: the simulator grows a **config-profile parameter** — run with `config/covered_call.yaml`, seed the fake broker with an initial equity inventory (the manual-purchase analog), replay the covered-call engine's scan/select/execute + early-close. Output through the existing metrics/reporting stack into covered-call-scoped result artifacts.
- **Accuracy caveat to state in every covered-call backtest report: FC-056 is OPEN — the engine prices covered calls ~0.676× live (~32% low) on identical contracts** (`docs/BACKTEST_ENGINE.md`, fidelity table). Call-side backtest returns are a **conservative floor**, not an accurate estimate. Fixing FC-056 is not in this plan's scope; a backtest that understates the strategy is usable for go/no-go, not for parameter fitting of premium-sensitive knobs.

## Design decisions (made — with rationale)

| Decision | Rationale | Rejected alternative |
|---|---|---|
| Separate account per strategy | Broker nets per symbol; OPASN has no client id; wheel adopts untracked positions; account-wide sizing | Tagging/attribution in one account — fails at assignment, the event that matters |
| One repo, one image, N services, config-selected | Mechanical reuse (req #2); one build pipeline; divergence impossible at the image level | Fork/second repo — guarantees duplicate mechanisms, the thing the owner explicitly rejected |
| Bucket-per-strategy for opportunity blobs + embedded `strategy_id` fail-closed check | Zero wheel migration; IAM-enforceable boundary; mis-config becomes a loud no-op | Path-prefix in shared bucket — needs a wheel migration or dual-read window |
| Account-number interlock pinned in YAML | The one control that makes right-code/wrong-credentials impossible; trivially auditable | Trusting `--set-secrets` bindings alone — silent until the first wrong-account fill |
| Floor = hard `strike >= avg_entry_price` via `CostBasisResolver`, no pause | Already the operator-decided, deploy-verified production policy (FC-065 P1); resolver fail-closes on missing/divergent basis | Designing a covered-call-specific floor — re-opens a settled decision |
| Universe = holdings; validator, not selector | Owner decision; the account boundary IS the selection ("hold nothing you won't have called away") | Screening/scoring universe — rebuilds wheel machinery a manual-entry strategy doesn't need |
| Size against equity in a 4× margin account | `buying_power` = 4× equity here; sizing on it quadruples intended exposure | Trusting `buying_power` uniformly across accounts with different margin multipliers |
| Rolling excluded from v1 | Roller is broken (FC-066), floor-unsafe (FC-062), 11-site `wheel_state`-coupled; early-close + re-write covers the value | Porting `CallRoller` — imports two open defect families into a new strategy on day one |
| No backtester Strategy protocol | Engine replays live code by design (FC-048 lineage); one extra implementor doesn't justify an abstraction | Interface-first — speculative generality, and FC-068 is about to move the ground under it |
| Stateless engine (no covered-call state manager) | Production wheel is stateless; the stateful layer never worked and is being deleted (FC-068/069) | New state manager — repeats the exact fiction being decommissioned this week |

## Risks & mitigations

- **Risk: wrong-account order despite everything** (mis-bound secret + matching config error). Mitigation: two independent controls must both fail — Seam 2 interlock and Seam 1 `strategy_id` check; both fail closed with alert events.
- **Risk: FC-061 — ledger blind to open unfilled short calls** → transient over-write attempts. Mitigation: broker rejects on share-lock (accepted interim backstop, per FC-061); revisit if rejects appear in monitoring.
- **Risk: OCC-substring recurrence** — three live sites remain (`wheel_engine.py:923/:925/:1027`, `options_scanner.py:611`); the family is at six historical instances. Mitigation: covered-call code uses `option_symbols.py` exclusively; add the repo-wide grep gate as a test (Verification) rather than waiting for FC-069 item 12.
- **Risk: analytics poison via FC-067** (calls journaled as puts). Mitigation: hard prerequisite for Phase 2 — engine does not ship journal writes until FC-067 lands.
- **Risk: 4× margin amplification.** Mitigation: `sizing_basis: equity` in config + `long_market_value > equity` alert; interlock pins the account so the multiplier is known.
- **Risk: `/monitor` silent skip (FC-053)** carries into the new service — an adjusted contract in the CC account would be silently unmanaged. Accepted; FC-053 owns the alert fix.
- **Risk: backtest false confidence** — FC-056 makes call returns ~32% conservative. Mitigation: caveat mandatory in every report; no premium-sensitive parameter fitting from backtests until FC-056 closes.
- **Risk: Phase 1 lands, FC-068/069 churn stalls, half-built feature.** Mitigation: Phase 1 is independently valuable (config hygiene, interlock, dataset threading benefit the wheel service alone) and wheel-neutral by test.
- **Risk: leaked paper credentials promoted to live habits.** Mitigation: rotation is a named LIVE GATE in §Sequencing; paper exposure accepted meanwhile.
