## What runs in parallel (subagent guidance)

**Per PR (fixed shape):** 1 Opus builder in its own worktree → when it reports, **2 Fable reviewers concurrently** (different personas, fresh contexts, never the builder's context) → I disposition → fixes by a builder → **1 Fable confirmer** → merge.

**Across PRs:**
- **Builds are fully parallel** when the PRs touch disjoint files (that is how the waves were cut — see the overlap map in the 2026-08-28 conversation / below). Up to **4 builders at once** is the practical ceiling — not for compute, but because each finished build produces two review verdicts I must disposition honestly, and a fifth stream turns dispositions into skimming.
- **Reviews are parallel across PRs too** (2 per PR → up to 8 concurrent).
- **Plans are written serially by me** (Fable session), typically the next wave's plans while the current wave's builders run.
- **Merges are serial** — see rules above.

## Staging PRs, then merging in sequence — does it help?

**Yes, for two of the three collision types; no for the third.**

1. **Deploy collisions (the FC-084 race):** staging + sequenced merges avoids them *if* merges are spaced ≥ one build apart. After FC-084 lands, even overlapping merges are safe (pinned promote + superseded guard).
2. **Build-time collisions (agents editing the same files at once):** avoided entirely — each builder works in its own worktree; nothing touches `main` until merge.
3. **Code collisions (two staged PRs changed the same file):** **not avoided by staging.** They surface at the second merge as a conflict or — worse — a clean auto-merge that is semantically wrong (FC-068's post-train merge caught exactly this via a test). Rule: after each merge, **rebase the next staged PR onto `main`, run the full suite, and if the rebase touched a file the previous PR also changed, run a scoped Fable confirmation on the rebased diff** before merging. The file-overlap map above is what keeps this rare.

So: stage freely, merge in the order the map dictates, rebase-and-retest between merges. The two-review gate is passed on the PR's original diff; the confirmation on the rebased diff is what keeps that verdict valid.
