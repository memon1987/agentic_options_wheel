## Context

FC-029 R3 gave the bot a drawdown pause: when held shares sit >5% below their assignment strike, covered-call writes stop (every in-band call would lock in a share loss below the cost-basis floor). Correct short-term; expensive if it silently persists — AMZN's 62-day implicit pause (Feb 6 → Apr 10, 2026) cost an estimated $1,500–3,000 in foregone premium and was only found in a post-hoc review. FC-029's second reviewer flagged the observability gap (LOW-8) → FC-030.

FC-031 shipped the *seeing* half: the Bot Health drawdown-pause card (paused symbols, assignment strike, pause floor, consecutive trading days, threshold live from bot `/config`). What remains is the *acting* half: nobody is notified unless they happen to open the dashboard. As of 2026-07-17, AMZN (5.9% below $262.50) and GOOGL (6.3% below $370.00) are both in day-1 pauses — live subjects for verification.

This plan is **alerting only**. The escalation question (allow a below-floor call after an extended pause) is deliberately split out to **FC-033** — it is a strategy change that reverses part of FC-029 R2's hard floor and deserves its own plan, two-reviewer scrutiny, and the empirical pause-duration data this alerting will start collecting.

This is also the project's **first notification path**. The channel choice below (Cloud Monitoring log-based alerting) is reusable for future alerts (reconciliation `warn`, critical bot-health anomalies) without new dependencies.

## Goals

- Operator is emailed within one trading day of any symbol's pause crossing the threshold (default **7 trading days**).
- One email per day maximum (single digest line per check run, rate-limited policy) — no per-symbol spam.
- Zero new application dependencies: GCP-native (structured log → log-based alert policy → email notification channel).
- The channel and pattern are documented so future alerts reuse them.

## Non-goals

- **Escalation** (below-floor call writes after N days) — FC-033.
- Any bot-side behavior change. The pause itself is untouched.
- Alerting for other conditions (reconciliation warn, anomaly flags, ingest failures) — natural follow-ups on this channel, out of scope here.
- Intraday alerting — pause state is computed from daily closes (bars land ~17:00 ET); a daily post-close check matches the data's cadence.
- Slack/SMS/push channels — email via Cloud Monitoring first; revisit if it proves too quiet.

## Proposed approach

Three pieces: an endpoint that evaluates and logs, a scheduler job that triggers it, and a monitoring policy that emails.

### 1. Dashboard backend — `POST /api/v2/bot-health/pause-alert-check`

New endpoint in `dashboard/backend/routers/v2.py`:
- Reuses the existing helpers exactly as `/bot-health/drawdown-pauses` does (`_live_positions()`, `_drawdown_pause_threshold()`, `get_drawdown_pauses`).
- Filters `paused` rows where `trading_days_paused >= PAUSE_ALERT_THRESHOLD_DAYS` (env, default `7`).
- If any qualify, emits **one** structured WARNING log line for the whole run with a stable marker: `DRAWDOWN_PAUSE_ALERT` plus `symbols=[{symbol, trading_days_paused, pct_below_strike}]` — single line ⇒ single email.
- If the live-positions proxy is unavailable, logs `DRAWDOWN_PAUSE_ALERT_CHECK_FAILED` at WARNING (a silent evaluator is the FC-006 failure mode again) and returns `{"status": "degraded"}`.
- Returns the evaluation payload either way so the check is manually invokable for verification.

### 2. Cloud Scheduler — `drawdown-pause-alert-daily`

Weekdays **17:45 ET** (after the 17:00 ET stock-history ingest that refreshes closes), OIDC (default compute SA, same pattern as the eleven existing jobs), targeting the **dashboard** service URL. Note: existing jobs target the bot service; the compute SA needs `run.invoker` on `options-wheel-dashboard` (grant documented below; it may already hold it project-wide).

### 3. Cloud Monitoring — channel + policy

- Email notification channel → `zeshan@tkzmgroup.com`.
- Log-based alerting policy: match `resource.type="cloud_run_revision" AND resource.labels.service_name="options-wheel-dashboard" AND textPayload:"DRAWDOWN_PAUSE_ALERT"`, notification rate limit 1 per 24h, auto-close 1 day.
- All three created via `gcloud` commands documented in a new `deploy/monitoring/drawdown_pause_alert.md` (following the existing `deploy/` doc pattern), so the setup is reproducible.

### Threshold decision

**7 trading days** (~1.5 calendar weeks). Rationale: the alert is a nudge, not an alarm — cheap to ignore, and the AMZN precedent shows the cost curve of waiting is convex. Env-overridable (`PAUSE_ALERT_THRESHOLD_DAYS`) without redeploy of the policy. Escalating cadence (re-alert at 14, 21…) falls out for free: the condition keeps logging daily and the policy re-notifies at most daily; the message carries the day count.

## Reuse

- `get_drawdown_pauses` + `_live_positions` + `_drawdown_pause_threshold` (FC-031) — the alert is a consumer of the existing computation, not a second implementation.
- Existing Cloud Scheduler OIDC pattern (`activities-ingest-market-hours` et al).
- Cloud Run stdout → Cloud Logging (already flowing); no logging changes needed.

## Risks & mitigations

- **Alert fatigue** → single digest line per run + policy rate limit 1/24h; threshold at 7d means a healthy account emails rarely.
- **Silent evaluator failure** (scheduler dies, proxy down) → the `CHECK_FAILED` marker is logged on degraded runs; the existing bot-health anomaly card already flags scheduler-wide outages via the SPY-bar calendar. An alert-on-absence policy is deliberately out of scope (v2 if warranted).
- **Stale closes** (stock-history ingest failed) → the check runs on last-known closes; ingest staleness is separately flagged by the FC-031 anomaly card. Accepted.
- **Email lands in spam** → fire drill (below) verifies end-to-end delivery before relying on it.

## Rollout

1. PR: endpoint + tests (production code path → branch + PR per standards).
2. Deploy via Cloud Build on merge.
3. Create channel, policy, scheduler job per `deploy/monitoring/drawdown_pause_alert.md`.
4. **Fire drill:** invoke the endpoint manually with `PAUSE_ALERT_THRESHOLD_DAYS=1` override (AMZN/GOOGL currently qualify) → confirm the email arrives → restore threshold. This validates the whole chain on day one instead of waiting weeks for a natural ≥7d pause.
5. Rollback: pause/delete the scheduler job (endpoint is inert without it); delete the policy.

### Two things the fire drill caught that testing could not

1. **CI had no FastAPI** — the new test imported `routers.v2` and the merge
   build went red. Fixed by moving pure logic to a service module. The obvious
   patch (module-level `pytest.importorskip`) was tried and rejected: verified
   it aborts collection of the whole file, silently skipping the 10 pure tests
   too — CI green while testing nothing.
2. **The alert policy matched nothing.** The filter carried `severity>=WARNING`,
   but Python `logging.warning()` writes plain text to stdout and Cloud Run only
   assigns severity to *structured JSON* logs, so entries land as `DEFAULT`. The
   endpoint reported `alerted: true` while the policy could never fire. Filter
   corrected to match on the marker string alone; documented in the runbook so
   it is not reintroduced.

   This is the whole argument for the drill: both the code and the endpoint
   response said "working". Only end-to-end verification found the gap.
