## Context

The dashboard is world-readable (`allUsers` run.invoker, `ingress=all` —
live-verified) and writes are guarded only by the pasted `SWEEP_SUBMIT_TOKEN`
— the UX the operator explicitly wants gone. D3 (operator-signed
2026-08-31, extended 2026-09-01): IAP + Google SSO over the whole dashboard;
invited accounts are read-only VIEWERS; an OPERATORS allowlist gets the write
paths; inviting/revoking = one IAM grant; the token dies; the scheduler's
`pause-alert-check` SA keeps working; FC-094 closes. Assumption stated at
signing: viewers see the whole dashboard read-only (a sims-only guest gate is
a later app-level addition).

Mechanism fact (verified 2026-09-02): this project's gcloud (578.0.0)
supports **direct Cloud Run IAP** (`--iap` on `run services update`) — no
load balancer required. The exact IAM role for admitting principals through
direct IAP and the consent-screen/brand prerequisite are the two facts the
plan review must verify against current docs (flagged, not assumed).

## Goals

1. Every dashboard request authenticates via Google SSO (IAP); anonymous
   access dies, including the artifact endpoint (the FC-094 exposure).
2. In-app authorization: OPERATORS (allowlist) may write (sweep submit,
   sims/run, pins POST/DELETE); every other authenticated identity is
   read-only (403 with a clear message on writes).
3. The pasted token is retired — UI and backend — with a safe two-step
   cutover (no window where writes are open or the operator is locked out).
4. The scheduler's `pause-alert-check` POST keeps working (SA through IAP).
5. FC-094 closes; the FC-096 entry records Phase D.

## Non-goals

- No sims-only viewer gate (assumption on record; later app work if wanted).
- No changes to bot / CC / sim services (already IAM-private; the proxy's
  OIDC path is untouched).
- No frontend redesign — the token input is removed in PR-2, nothing else.
- No IAP on non-dashboard services.

## Two PRs + the operator session (cutover order is the design)

**PR-1 — the roles layer, deployable BEFORE IAP flips (safe both sides):**
- `dashboard/backend/services/auth.py` (new): validates the
  `x-goog-iap-jwt-assertion` header — signature against Google's IAP public
  keys, audience = this service's IAP audience (env `IAP_AUDIENCE`), issuer,
  expiry — returning the verified email; NEVER trusts the plain
  `X-Goog-Authenticated-User-Email` header alone. `OPERATORS` env: comma-
  separated emails (seed: the operator's).
- Write-path gate becomes a chain: IF a valid IAP assertion is present →
  operator-email check decides (403 for viewers, allow for operators, token
  ignored); ELSE (no IAP yet / direct access) → the EXISTING token gate
  applies unchanged. This makes PR-1 a no-op until IAP flips, and makes the
  flip itself the cutover — no coordinated deploy.
- Read paths: unchanged in PR-1 (IAP itself will gate them at the flip).
- Env: `IAP_AUDIENCE`, `OPERATORS` added to the dashboard deploy flags
  (contract fixture re-freeze); `google-auth` already present (verify — it
  ships transitively; pin if the CI-venv check says otherwise).
- Tests: JWT validation (valid/expired/wrong-audience/garbage/absent),
  operator-vs-viewer on every write route, token-fallback preserved when no
  assertion, CI-equivalent venv (the ambient-env standing rule).

**Operator console session (one sitting, commands provided at rollout):**
1. Configure the OAuth consent screen/brand if absent (one-time; IAP
   prerequisite — the review verifies whether direct Cloud Run IAP still
   requires a brand).
2. `gcloud run services update options-wheel-dashboard --iap` (+ the
   documented principal grants: the operator's account, any invitees, AND
   `799970961417-compute@…` so the scheduler's OIDC-bearing POST passes IAP —
   exact role per the review's doc check; expected
   `roles/iap.httpsResourceAccessor` or the Cloud Run IAP equivalent).
3. Remove `allUsers` from run.invoker; IAP's service agent becomes the
   invoker (the review verifies the direct-IAP invoker model — who invokes
   the service when IAP fronts it).
4. Verify: anonymous → Google sign-in; invitee sees dashboards, gets 403 on
   a write with the friendly message; operator submits a sweep with NO
   token; the scheduler's next `pause-alert-check` run succeeds; the
   artifact endpoint anonymous → sign-in.

**PR-2 — retirement (after the operator session verifies):**
- Backend: token gate removed from the chain (IAP assertion REQUIRED on
  writes; absence → 401 naming IAP, not the token); `SWEEP_SUBMIT_TOKEN`
  env/secret wiring removed from deploy flags (fixture re-freeze); the
  `sweep-submit-token` secret deletion is an operator step (listed).
- Frontend: the token input/sessionStorage handling removed from `/sims`
  (`SubmitSweep`, `useSweeps`); `tsc`/vitest/build green.
- Docs: `docs/CLAUDE.md` auth table, FC-094 closed in the index,
  `scenario_runs.md` exposure notes updated (artifact endpoint now
  authenticated).

## Behaviour contract

- PR-1 deployed, IAP not yet flipped: byte-identical behaviour (token gate
  rules; probed).
- IAP flipped, PR-1 live: operator writes tokenlessly; viewer 403 on writes
  with a message naming the OPERATORS mechanism; token still accepted as
  fallback only where no assertion is present (i.e., never, once IAP fronts
  everything — stated for completeness).
- PR-2: no token code path remains; writes require a valid assertion.
- The scheduler's POST works before, during, and after (its SA passes IAP).
- No service other than the dashboard changes behaviour.

## Test requirements

PR-1 no-op probe (no assertion → existing behaviour byte-identical);

i.e., its 401 message is honest either way — a doc/test note, not a deploy

## Design decisions (made — do not relitigate in the build)

- Verify the SIGNED assertion, never the plain header.
- The PR-1 chain (assertion-if-present, token-else) is the cutover safety —
  no flag-day coordination between deploy and console.
- OPERATORS as an env allowlist (one operator today; growing it is an env
  edit, not a schema).
- Viewers see everything read-only (signed assumption; no page gating).
- Token retirement is a separate PR gated on the verified operator session.
