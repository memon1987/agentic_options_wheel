# Release Notes — 2026-09-01 (session 2026-08-31 → 09-01)

## Summary

Answered "why does the covered-call engine still write nothing?" and shipped the fix in one session. The operator's par-reset had re-bought **1 share** per symbol (an order-entry slip), but behind that sat three code/config defects that would have kept the engine at zero regardless: a `KeyError` that priced every symbol as `{}` on every scan since go-live, an open-interest floor evaluated against a hardcoded `open_interest: 0`, and a STAGE 8 log line that hid exactly the buckets that mattered. All three landed in **PR #107** (`c0dc2fd`) under a `[no-plan]` override with two adversarial reviews + a confirmation pass. The operator has 99-share buys pending on GOOGL and UNH; the first `stage_8_complete_found` → `call_opportunity_found` on the next scan with `positions_with_100_shares=2` is the proof.

## Changes

### Bug Fixes (PR #107, `c0dc2fd`)
- **`get_stock_metrics` KeyError on the CC profile.** `MarketDataManager.get_stock_metrics` hard-indexes `strategy.min_stock_price` / `max_stock_price` / `min_avg_volume`; `config/covered_call.yaml` had none. The call path reaches it on every chain fetch (`get_option_chain_with_analysis`) and again in `_create_call_opportunity`; the broad `except` turned the KeyError into `{}` and `stock_metrics_error` on 52/52 CC symbol-scans (08-24 → 08-31). Had any candidate reached the builder it would have died as `call_scan_skipped_quote_unavailable`. Fixed with three non-binding keys (wide bounds; only `current_price` is consumed on the call path) and **load-time validation hoisted to every profile** — a future profile missing them now fails at `Config()` instead of at scan time inside an except.
- **OI floor vs hardcoded OI=0 (found by the trader-persona review).** `AlpacaClient.get_options_chain` (snapshot endpoint) hardcodes `open_interest: 0`; the CC profile's `universe.min_open_interest: 500` runs **last** in `_check_call_criteria_detailed`, so it rejected every strike that survived basis/DTE/premium/delta — the ~114 GOOGL / ~86 UNH per-scan gap on 08-28. **Disposition:** `min_open_interest: null` (config-only, reversible) — the OI half of the FC-075 DD-3 inventory validator is suspended, the spread half (`max_spread_pct: 0.10`) stays. A test pins the suspension to the hardcode and skips loudly once OI is sourced (FC-097).
- **STAGE 8 log under-summed `rejected=`.** `open_interest_too_low` / `spread_too_wide` were counted but never emitted; `_validate_option_data` failures had no bucket at all. Added `data_validation_failed`, emitted all 10 buckets on both STAGE 8 lines, and a test that asserts the emitted set is the closed set of 10 **and** `sum == rejected`. (Decision records in `covered_call.decision_events` already carried OI/spread in `reason_counts` — the gap was log-only.)

## Key Decisions & Rationale
- **Suspend the OI floor rather than leave the engine at a known zero.** The alternative (keep 500, file the FC, tell the operator to expect nothing) contradicts the stated goal of testing the call seller now. Config-only, one-line revert, and the test makes "restore without sourcing OI" a CI failure. It *is* a suspension of a signed design decision (FC-075 DD-3) and is recorded as such in the plan.
- **Config keys, not `.get()` defaults, for the screening knobs.** Defaults on the `Config` properties would make the *next* missing key silent; requiring presence on every profile and validating at load keeps failures loud. The durable shape (a price-only helper so the call path never touches put-screening keys) is named in the FC as the long-term fix.
- **Two reviews + confirmation even under `[no-plan]`.** The change touches the CC scan path and a signed operator decision; the reviews earned their cost — the OI finding was theirs, not the investigation's.

## Discoveries
- **`docs/BACKTEST_ENGINE.md` (FC-060, 08-28) already documented that `get_options_chain` hardcodes OI=0 and that "any floor ≥ 1 rejects every call"** — for the *sim* allowlist. Nobody cross-checked the live CC config against it. Lesson: a "this knob is meaningless" finding in one context is a bug report for every other context that sets the knob.
- **A `level=error` structlog line on Cloud Run arrives with LogEntry `severity=DEFAULT`** (plain-text stdout) — 52 errors in a week matched no `severity>=ERROR` alert. Same family as the FC-030 gotcha; FC-098 owns it.
- **`gcloud logging read` on these services: the app payload is `jsonPayload`, not `textPayload`.** `textPayload:"..."` / `textPayload=~` filters silently return nothing; use an unqualified global term (`"STAGE 8 COMPLETE"`).
- **Verification trap for the next session:** with `positions_with_100_shares=0` every scan terminates at `insufficient_shares` before any of this code runs. Zero calls after deploy is meaningless until both symbols show 100 shares in the 10:00 ET scan.
